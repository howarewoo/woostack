The canonical implementation rules live in the
[artifact contract](https://github.com/howarewoo/woostack/blob/main/shared/references/artifact-backends.md#direct-publication-and-recovery)
and the [GitHub profile](https://github.com/howarewoo/woostack/blob/main/shared/references/artifact-providers/github.md#scope).

Whiteboard owns direct issue publication and reads every write back before claiming success.
Orchestrate is read-only when interpreting a tracker: a complete readable implementation index can
establish declared membership when native child links are absent, partial, or unavailable, provided
every selected issue is independently readable.

## Scope and access

Resolve repository and owner identity from the request and verified Git/GitHub evidence. Read the
actual visibility of an explicitly selected Project. No Woostack configuration is required.

Credentials belong in the host secret store. Custom HTTP clients, credential reads, and token
forwarding are forbidden. Host-native GitHub tools are preferred; host-authenticated official `gh`
is supported.

### Transport capabilities and boundaries

Preflight only the capabilities needed by the selected operation through the authorized GitHub
interface. Each requested operation requires only its own capabilities:

| Operation | Required capability | Required input | Read-back verification |
| --- | --- | --- | --- |
| Issue publication | Issue create and update | Exact resolved repository and approved content | Independent read-back of issue body and requested relationships |
| Native relationship links | Sub-issue or blocked-by links | Exact endpoints and requested relationships | Confirmed read-back of relationship graph |
| Project membership | Project item create | Caller-supplied Project URL and exact issue | Verified project item presence |
| Spec README update | `ProjectV2.readme` update | Canonical Project URL | Verification of content within spec markers |
| Project Status update | Project field update | Explicitly requested change, actual field/options, and unambiguous target value | Read-back of updated field value |

Native relationship writes are requested separately. If unavailable, retain verified issue URLs
and readable prerequisites, and report missing relations; an explicitly required native graph
remains incomplete. Writes preserve human and unrelated content. Unknown writes are rediscovered
using the same exact identity or Project-bound marker before retrying, never creating blind duplicates.
README mutation updates only `readme`, preserves outside bytes, and retains its bound recovery marker.

Unsupported capabilities, unauthorized scopes, or partial responses stop the relevant GitHub
operation. No test mutation is used to probe publication permissions.

## Identities, hierarchy, and graph

Accepted canonical URL forms:

- Projects: `https://github.com/orgs/<owner>/projects/<N>` or `https://github.com/users/<owner>/projects/<N>`.
- Issues: `https://github.com/<owner>/<repo>/issues/<N>`.

GitHub's internal GraphQL node IDs and Project item IDs are kept separately for API calls.
Explicit Project operations resolve one exact caller-supplied Project URL, never inferred from
historical settings. The specification may be stored in `ProjectV2.readme` between markers
`<!-- woostack-spec-start -->` and `<!-- woostack-spec-end -->`, preserving unrelated README bytes.

### Issue publication

`--project` is the explicit destination selector for requested publication:

```text
/woostack-whiteboard <goal-or-existing-plan> --project <exact canonical GitHub Project URL>
File the resulting plan as issues. Do not implement it.
```

Without `--project`, the destination comes from the request and repository context. Whiteboard asks
instead of choosing when multiple destinations are plausible.

Publication groups implementation checkpoints into coherent issue outcomes, reuses existing issues,
and creates only missing ones. It writes only requested relationships. After every write, Whiteboard
reads affected issues back independently; a mutation response alone proves nothing.

Native hierarchy, `blocked-by` relationships, and Git branch ancestry are separate facts.
These labels are illustrative, not a real project's graph:

| Graph | Example relationship | What it records |
| --- | --- | --- |
| Issue hierarchy | Issue A contains Issue B | Group membership. |
| Prerequisite | Issue B is blocked by Issue A | Issue A is a prerequisite for Issue B. |
| Git branch ancestry | Branch Y is based on Branch X | A branch-parent relationship to verify against Git and the approved plan. |

Do not infer any of these relationships from another. Hierarchy alone does not establish a
prerequisite, implementation order, authorization, or branch parent. Native stack registration
still follows [Orchestrate's conditional delivery rules](/docs/skills/woostack-orchestrate#coordinate).

## Lifecycle and closure (retired Execute reference)

> **Retired.** Execute no longer performs GitHub Project/issue lifecycle transitions, project/run
> controller reads, closure, or `--project`/`--run`/`--recheck` scope. It accepts an authorized
> bounded task and may read a selected exact issue for context. See
> [Execute retired inputs](/docs/skills/woostack-execute#retired-inputs).

Explicit Project lifecycle operations use only the exact selected Project and its verified current
fields and options. Ask when the requested target value is ambiguous.
Whiteboard does not change issue or Project lifecycle state, with or without a Project selection.

## Workflow matrix

| Skill | GitHub behavior |
| --- | --- |
| [woostack-whiteboard](/docs/skills/woostack-whiteboard) | Plans work; writes issues only when requested. Reuses existing issues, writes requested relationships, and reads every write back. `--project` adds membership in one exact existing Project for requested publication. |
| [woostack-orchestrate](/docs/skills/woostack-orchestrate) | Coordinates multi-task work and verifies requested delivery without closing issues or merging. Local-only work requires no GitHub publication; explicitly selected remote issue or Project reads still need access. |
| [woostack-execute](/docs/skills/woostack-execute) | Accepts bounded tasks; retired `--project`, `--run`, and `--recheck` are rejected. Explicit Execute requests deliver draft PRs unless narrowed to local edits. |
| [woostack-init](/docs/skills/woostack-init) | Authors project guidance without GitHub access or Woostack setup. |

See the [GitHub profile contract](https://github.com/howarewoo/woostack/blob/main/shared/references/artifact-providers/github.md)
for exact capability, identity, and recovery requirements.
