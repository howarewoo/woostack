---
title: Verification
description: What different checks establish, when their results remain valid, and how missing evidence affects completion.
---

A check supports a particular claim under the conditions it tested. A passing build establishes
buildability. It does not establish that instructions are accurate, an interaction works in a
browser, or a PR was published.

## Match the evidence to the claim

| Evidence | What it can establish | What it does not establish |
| --- | --- | --- |
| Source and diff inspection | Current behavior or instructions, changed scope, and preserved safeguards. | What actually happened at runtime. |
| Behavioral tests | The tested contract under the supplied inputs and environment. | Every interaction or untested combination. |
| Browser observation | The rendered behavior observed in that session. | Full accessibility conformance or every user's environment. |
| Skill parser and asset tests | Files load and bundled links resolve. | An agent followed the workflow. |
| An actual host/model run | What the agent did in that run. | How every future run will behave. |
| GitHub read-back | The remote PR identity, content, and state read back. | Implementation acceptance. |

Review can find problems these checks missed. It cannot replace a required test or observation.
Test counts and coverage percentages help locate gaps, but their value depends on what failures
the assertions detect.

## Requirements and risk determine the checks

User requirements, task acceptance, repository policy, and the active workflow determine required
checks. For ordinary reversible work, Woostack favors existing relevant checks and the smallest
practical observation of the changed behavior. Extra checks need an applicable requirement or a
concrete failure risk with a stated consequence.

For example, a wording correction needs its claims and links inspected. A changed interaction
may need a browser observation. Running a build cannot settle either question on its own.
Consequential changes involving authorization, privacy, destructive effects, migration, recovery,
or financial operations need stronger targeted evidence.

Test-first work, coverage collection, and independent review apply when requirements or relevant
risks call for them. They are not universal stages. The [shared testing guidance](https://github.com/howarewoo/woostack/blob/main/shared/references/tdd.md)
and [Execute verification policy](/docs/skills/woostack-execute#implement-and-verify) define the rules.
The [verification how-to](/docs/guides/verification) shows how to apply them to a task.

## Evidence can remain valid

Results remain useful while the relevant source, tests, fixtures, dependencies, configuration,
and environment remain equivalent. A handoff, new commit identifier, or unrelated prose edit
alone does not invalidate them.

Changed inputs or uncertain equivalence require affected checks to run again. Components that
pass separately may fail when integrated.

## Completion and publication need different proof

| Outcome | Required evidence |
| --- | --- |
| Implementation accepted | The selected acceptance checks support the authorized outcome. |
| Draft PR published | Git and GitHub confirm the intended commit and PR, with publication safeguards satisfied. |
| Dependent work can begin | Its required prerequisite content and contract evidence are verified. |
| Merge or release ready | The applicable merge or release requirements are satisfied. Local checks alone cannot prove remote readiness. |

These outcomes need not happen in this order. A draft PR can disclose unfinished acceptance when
its publication rules permit it. Dependent work may begin before PR publication if its prerequisites
are verified. Only humans merge; see [authority boundaries](/docs/concepts/workflows#authority-boundaries).

A failed, unavailable, timed-out, cancelled, or unrun required check leaves the affected outcome
unverified. A pre-existing failure remains a failure. A useful report names the missing evidence
and what must change to obtain it. Optional coverage gaps stay visible without becoming new
acceptance requirements. See [reporting results](/docs/guides/verification#4-report-results-at-the-affected-boundary).
