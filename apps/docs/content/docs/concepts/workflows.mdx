The right entry point depends on what you want done. A clear, bounded task can go straight to
implementation. A goal with unresolved choices benefits from planning. Several executable tasks
may need coordination.

## Planning and implementation are separate choices

[Whiteboard](/docs/guides/whiteboard) explores requirements, develops plans, or reviews an existing
specification. Requirements-only work can stop before choosing an architecture. A plan stays in
the conversation unless you ask to save it or [publish issues](/docs/guides/plan-work); neither
action starts implementation.

[Execute](/docs/guides/ship-change) implements one authorized outcome. It can diagnose a bounded
bug fix inline, so a separate Debug session is optional. A natural-language implementation
request permits local edits and checks. An explicit `/woostack-execute` request also requests a
draft PR unless you narrow it to local work.

[Orchestrate](/docs/guides/coordinate-work) groups executable tasks and delegates implementation
to isolated workers. It proposes the grouping before execution and normally waits for your
approval. You can explicitly delegate bounded planning decisions to a named coordinator; choices
outside that delegation still come back to you.

The [command index](/docs/skills/using-woostack#command-routing) covers other tasks, including
read-only investigation with Debug and behavior-preserving code reduction with Simplify.

## Authority boundaries

The user sets the scope and grants permission. A plan, issue, agent role, or worker message cannot
expand it. An issue URL alone supplies context, not permission to implement or publish.
Reversibility is not permission to invent consequential behavior.

Whiteboard resolves material ambiguity during planning, using repository facts before user
questions. Authorized read-only scouts can supply evidence and recommendations, not decisions or
implementation authority. A material question stays open only for explicit user deferral, necessary
bounded investigation, or an honest draft when the user stops or is unavailable. Dependent work
remains unready, while independent ready work can be authorized separately.

Execution does not turn a missing requirement into an assumed default. Execute and Orchestrate park
only affected work and keep safe independent work, required review, healthy checks, and eligible
requested delivery moving. Nonblocking questions belong in the final handoff with affected
acceptance, a recommendation, and a resume condition. Workers escalate to their coordinator without
host-blocking questions; an execution owner uses such a question only when the answer blocks all
remaining useful authorized work. An accurate blocked result is valid, but cannot claim unmet
acceptance as complete. Existing safety and publication gates still apply.

| Source | What it establishes |
| --- | --- |
| User instructions | Authorized actions, decisions, and limits. |
| A plan | Intended behavior, constraints, and open decisions. |
| A published issue | The issue content and relationships actually read back. |
| Git and GitHub | Source, commits, PR state, checks, reviews, and merge evidence. |
| QA and review reports | Observations to assess within their stated limits. |

A closed issue or an agent's success message cannot prove that code landed. Likewise, a draft PR
can expose unfinished work for review without proving acceptance passed. [Verification](/docs/concepts/verification)
explains which evidence supports each claim.

Only humans merge, enable auto-merge, or queue PRs for merge. Standalone Git maintenance, including
rebasing, restacking, and readiness changes, belongs to [Deliver](/docs/skills/woostack-deliver)
when explicitly requested.

## Older installations and retained records

Retired commands have no compatibility aliases. The [troubleshooting guide](/docs/guides/troubleshooting#a-command-has-been-retired)
points to current commands. New work uses current repository and host evidence; old run records
remain historical user data. Nothing automatically migrates or deletes them. The
[local artifacts reference](/docs/configuration/artifacts/local) covers preservation and recovery.
