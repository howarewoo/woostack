These pages explain how the workflows relate to each other. The [task guides](/docs/guides) carry
the procedures; the [command index](/docs/skills/using-woostack#command-routing) lists the skills,
and each skill's own reference page owns the exact contract, evidence rules, and recovery behavior.
Start from the result you need rather than from a required
sequence. An issue URL supplies context, not permission to implement or publish, and Git and GitHub
show what was implemented and delivered.

## Routing by work shape

One authorized outcome is enough to begin. A bounded enhancement, refactor, test task, or
authorized correction goes to [Execute](/docs/skills/woostack-execute) with no planning stage
first, and tests for a bounded target are ordinary Execute input under the
[testing guidance](https://github.com/howarewoo/woostack/blob/main/shared/references/tdd.md).

The other workflows answer different questions. [Plan](/docs/skills/woostack-plan) suits a feature,
a defect whose cause is already proved, a request to file issues, or a product that does not exist
yet. [Ideate](/docs/skills/woostack-ideate) explores requirements and
[Harden](/docs/skills/woostack-harden) reviews a specification or candidate issue plan against
repository evidence when you want that check. [Debug](/docs/skills/woostack-debug) is for
root-cause investigation that changes nothing. [Orchestrate](/docs/skills/woostack-orchestrate) is
for several approved tasks with real prerequisites between them.

When the shape is still unclear, [Plan work and file issues](/docs/guides/plan-work) starts from a
goal, and [Troubleshoot a blocked workflow](/docs/guides/troubleshooting) starts from a symptom.

## Plan

```text
inspect relevant source when it exists → identify unresolved decisions →
draft a coherent plan → publish issues when the request asks for it →
read back actual content and relationships → stop
```

Plan inspects the relevant source, settles the decisions that still change the outcome, and
returns a few reviewable increments. It publishes GitHub issues only when the request asks for it,
and publication does not start implementation: what happens next stays the user's decision. A
planning-only request makes no GitHub write.

Planning a product that does not exist yet is the same workflow. With no checkout or source, Plan
works from the supplied goal, constraints, and authoritative research, resolves only the material
unanswered decisions, and writes nothing unless the request asks for issues. Settled technology
choices are reused rather than re-asked, and no questionnaire or extra approval stands between a
planning request and its plan.

Each issue carries its outcome, the constraints that matter, what is out of scope, acceptance and
verification, and its real prerequisites. Native sub-issue and dependency links are used when they
are available and requested. Otherwise the written issues and a readable index are preserved, the
missing relationships are reported, and an explicitly required native graph is never called
complete. An unknown defect cause stays with [Debug](/docs/skills/woostack-debug).

[Plan work and file issues](/docs/guides/plan-work) is the procedure, and
[Plan's reference](/docs/skills/woostack-plan) owns destination resolution and read-back.

## Orchestrate

```text
approved work context → read outcomes, source, and PR evidence → propose orchestration plan →
pause for user approval or revisions → delegate each group to a task owner →
reconcile verified task results → deliver draft PRs, stacked in order → verify delivery
```

Orchestrate works from approved tasks: published issues, a tracker, or other complete readable
context. Readable context is valid input, and a native issue hierarchy is not universally
mandatory. A readable tracker plus independently readable tasks is enough to coordinate work, so a
missing administrative link is not a blocker while missing task scope is.

Draft visibility, prerequisite readiness, group completion, and external merge/release acceptance
answer different questions. The approved plan distinguishes their gates and sets a wall-clock
reassessment interval under [Orchestrate's proposal rule](/docs/skills/woostack-orchestrate#coordinate),
preserving the user's chosen interval. Authorized drafts can disclose unmet implementation acceptance
without separate unfinished-draft approval. Explicit publication gates and safety protections still
bind; draft visibility proves neither completion nor consumer readiness. Eligible groups can publish
independently of the whole chain.

The change plan comes before any implementation: which tasks group into which pull request, the
required changes, the intended parent and landing order, cross-task interfaces, and safe parallel
groups. Prerequisites are discovered from source and PR evidence, not from a missing dependency
field. Small related tasks share a PR when their implementation/verification path is inseparable,
not just because they are adjacent or share a controller. Every task keeps its acceptance, and a
user-requested issue-to-PR mapping is preserved. Orchestrate presents this proposal and stops for
approval or revisions; it allocates no workspaces and dispatches no workers before approval.

Each group has a native task owner, normally running installed Execute, that chooses its
implementation decomposition and specialist handoffs. Orchestrate owns coordination between tasks;
the task owner integrates and verifies contributions within its task. Contribution needs do not
automatically create separate agents or PRs. Without Execute, the owner uses Orchestrate's bundled
procedures under the same approved limits, so independent installation remains supported. A host
may let only the root launch contributors; relaying the owner's assignment does not transfer
implementation ownership or bypass host limits.

Each group is implemented in an independently owned task worktree, including a run that groups
everything into one PR, and every task starts from a base that actually contains the changes it
requires. That is a content question answered by current Git and PR facts, not by an assumed
ancestor or a similar branch name. Two writers never share one physical workspace, and a prior
writer whose exit is unproved blocks reuse of its workspace while other safe work continues.

Root pull requests target the approved trunk, each dependent pull request targets its planned
predecessor's head branch, and native stack registration is required for those dependent PRs and
read back after publication. Landing order is distinct from implementation order: sufficiently
complete immutable prerequisite checkpoints can enable dependent work before PR publication or
landing. Missing capabilities or host capacity can still require sequential dispatch.
Routine in-scope diagnosis, repairs, checks, and authorized draft updates use standing authority.
Exploratory corrections stay with their task owner in the canonical allocation; changes affecting
other tasks or shared contracts return to Orchestrate. Dependents reconcile at verified contract
checkpoints rather than after every hypothesis. Reassessment compares elapsed preparation, builds,
replay, and coordination with new behavioral evidence and stays live during native-worker waits.
Diagnosis without new product-relevant or required-safety evidence parks affected verification and
dependents. Reopening requires relevant changed product inputs or evidence, an actual prerequisite,
capability or permission change, or explicit scoped user direction, not just a new diagnostic method.
[Orchestrate's coordination policy](/docs/skills/woostack-orchestrate#coordinate) owns those boundaries.
Independent authorized work continues, as do demonstrably healthy long checks. With neither runnable
work nor healthy pending work, the result is a final blocked disposition. Progress messages and
notifications do not restart the cadence, and delivered notifications need not wait for a checkpoint.
Applicable child results carry forward under the canonical [testing
guidance](https://github.com/howarewoo/woostack/blob/main/shared/references/tdd.md#when-evidence-still-applies);
the coordinator independently verifies the canonical tree, cumulative diff, and new interactions.
Aggregate capacity includes descendants. Only conflicting heavy checks share a concurrency limit;
light checks can proceed. There is no persisted execution forest, lock service, or cross-harness
replay guarantee.

[Coordinate several tasks](/docs/guides/coordinate-work) is the procedure, and
[Orchestrate's reference](/docs/skills/woostack-orchestrate) owns admission, base selection, and
recovery.

## Execute

```text
one authorized outcome → admit the workspace, or a new empty target → implement and integrate
useful contributions → verify the task → return or deliver within the assigned limits
```

Execute owns one bounded implementation, whether called directly by the user or run by a native
worker delegated from Orchestrate. Contributions follow unresolved questions, implementation
boundaries, acceptance criteria, and material risks, not a fixed specialist roster. Domain guidance
can be used inline; delegation needs a concrete benefit from separate context, parallel work,
restricted tools, or independent assessment. Execute supplies each contributor's context and limits
and verifies the integrated result. Small or tightly coupled work stays with the task owner;
required review remains independent.

An ordinary user request to implement authorizes local edits and checks, while an explicit Execute
request delivers a reviewable draft PR unless narrowed. A bare issue URL outside that command
authorizes no implementation. A delegated assignment inherits the coordinator's approved limits;
it is not a fresh command granting publication authority or restarting planning. By default the
worker returns verified changes and evidence, while Orchestrate owns commits, PRs, and stacks.
Explicit delegation can assign a particular Git/PR operation to the worker, with one publication
owner and coordinator read-back. [Deliver one change](/docs/guides/ship-change) shows the standalone
draft-PR path.

A correction needs cause evidence from reproduction or adequate source and runtime facts. A
proposed fix is not proof, and a separate [Debug](/docs/skills/woostack-debug) session is an option
rather than a required handback. A failure found after publication is a correction of the same
outcome on the same branch and PR. Cross-task work belongs to Orchestrate; Execute does not
reorganize sibling tasks or change their shared contracts unilaterally.

An authorized request to create a project that does not exist yet is ordinary Execute input: it
reuses the settled product and technology decisions and asks only about unresolved material
choices, so no planning step and no document step is a prerequisite. [Creating a project that does
not exist yet](/docs/concepts/repository-rules#creating-a-project-that-does-not-exist-yet) covers
target admission, the scaffold, and its delivery boundaries.

## Simplify

[Simplify](/docs/skills/woostack-simplify) starts from an existing implementation whose complexity
is the problem. Execute can also refactor, but Simplify has a narrower objective: preserve required
behavior while reducing the code and concepts that need maintenance. A useful simplification may
replace a whole internal flow rather than produce the smallest diff.

Simplify applies changes unless the request is analysis-only. Even an explicit Simplify invocation
stays local unless a commit or PR is requested. It bundles the same least-code engineering
reference Execute consumes without invoking that workflow, and neither Plan nor Execute is a
prerequisite.
An implementation that is already simple enough can remain unchanged.

## Shared execution boundary

Implementation workflows report the same way. An existing targeted test can serve as the
smoke for a change, and required repository checks and reviews cannot be waived by an agent's
success sentence. Unmet acceptance prevents completion; unmet publication gates block publication.
[Execute's publication policy](/docs/skills/woostack-execute#requested-commit-and-publication)
distinguishes authorized draft visibility from completion and consumer release.

The assigned delivery owner performs authorized operations under the
[delivery procedures](https://github.com/howarewoo/woostack/blob/main/shared/references/delivery.md)
and the
[source-control safeguards](https://github.com/howarewoo/woostack/blob/main/shared/references/source-control.md):
staging, the push, the PR body, and the read-back of head, base, state, and preserved human text.
Applicable observed results are reused under the canonical [testing
guidance](https://github.com/howarewoo/woostack/blob/main/shared/references/tdd.md#when-evidence-still-applies).
Required hooks and configured commands still run. New PRs are drafts, and unavailable requested
delivery remains incomplete. Native stack registration is conditional on an explicit
request or a repository requirement, so its absence does not invalidate verified code. An unknown
commit, push, or PR outcome is rediscovered from current Git and PR facts before anything is
retried, which is what keeps a duplicate writer or duplicate PR from appearing. An explicit
commit-only request, or rebase, restack, and readiness maintenance, is
[Commit's](/docs/skills/woostack-commit) own operation.

Separate concurrent writers need independently owned workspaces, and a possibly active prior writer
blocks reuse until its exit is proved. An approved existing workspace need not be replaced. Retired
run, project, and recheck inputs select no executable scope, and retained records stay unchanged.
When a write or a check leaves an uncertain state, [Troubleshoot a blocked
workflow](/docs/guides/troubleshooting) lists the symptom and the safe way to resume.

## Upgrading from a pre-cutover release

Prepare and the custom execution controller's command line and protocol are retired. Nothing
installs, invokes, or emulates them, and no compatibility layer stands in for them.

- New work never resumes from a retained record. It starts from fresh task, source, and host
  context, and recovery is proved from current evidence instead of assumed to repeat on another
  host.
- Retained `.woostack/tmp/runs/<run-id>/` records, installed old copies, and existing worktrees
  stay exactly as their owner left them. Migrating or removing them is optional, manual, and
  user-initiated.
- A recorded run that still needs the old controller replays from the pre-cutover installation
  recorded with it. Retained checkpoints are not converted, and no automatic cleanup runs.

Retained-data authority and recovery belong to the
[local artifacts reference](/docs/configuration/artifacts/local) and
[Orchestrate's coordination contract](/docs/skills/woostack-orchestrate#coordinate).

## Review and corrections

Review is independent evidence, not an automatic extra gate for ordinary reversible work. Existing
relevant checks and the smallest practical observation are the default. Additional runtime work,
comparisons, or independent review need an explicit requirement or a named material risk.
[Execute's verification policy](/docs/skills/woostack-execute#implement-and-verify) and
[Orchestrate's coordination policy](/docs/skills/woostack-orchestrate#coordinate) own evidence selection
and stronger targeted evidence for consequential use or release. Where runtime semantics matter,
controlled outputs alone cannot prove them. Unresolved privacy evidence stays HOLD; lost private
evidence is not reconstructed or cleared by a replacement run.

Deferred acceptance remains unmet even when an authorized draft is published. A group finishes only
after its completion requirements, verified publication, and required stack membership are satisfied.
Neither coordinator nor workers monitor new CI/reviews or reopen completed groups on incoming events.
Later corrections require a separate explicit request; remote checks and merge approval remain
distinct from implementation evidence.

Depending on the request, the result is a verified local change, a scaffold, a plan with requested
issues, a reviewable PR, or a blocker reported at the first safe resume boundary. Existing retained
records remain unchanged. No woostack workflow merges, enables auto-merge, or queues a PR for merge;
those decisions stay with the human. An explicit request to rebase, restack, consolidate, or mark
ready applies to the selected pull requests only.
