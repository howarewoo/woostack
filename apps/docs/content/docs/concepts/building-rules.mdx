---
title: Building rules
description: Who authorizes work, and which evidence proves it landed.
---

woostack keeps two questions apart: what the user decided to build, and what the repository
actually contains. The user decides the product and authorizes each workflow. Git and GitHub own
source, branches, commits, pull requests, checks, reviews, and merge evidence. A plan, an issue, a
status board, a retained record, or an agent's success sentence is context for those facts, not
proof of them.

## Where the detail lives

The workflows are documented where they run, not summarized here.

- [Plan](/docs/skills/woostack-plan) plans a change and publishes GitHub issues only when the
  request asks for it.
- [Coordinate several tasks](/docs/guides/coordinate-work) covers plan-first grouping, one
  delegated worker per group in its own task worktree, the draft pull requests a requested
  delivery produces, and the native stacks that dependent pull requests require.
- [Deliver one change](/docs/guides/ship-change) covers one bounded task, its checks, and its
  draft pull request.
- [Workflow maps](/docs/concepts/workflows) compare the workflows by the shape of the work.
- [Troubleshoot a blocked workflow](/docs/guides/troubleshooting) lists observable symptoms and
  the safe way to resume.

No workflow merges anything, enables auto-merge, or queues a pull request; those stay with a human.
A request to rebase, restack, or consolidate selected published pull requests authorizes the scoped
maintenance, publication, and readiness transition it names. An ordinary commit or correction request
carries none of it. [Commit's reference](/docs/skills/woostack-commit) owns the safeguards.

## Authority boundaries

| Surface | What it proves |
| --- | --- |
| A plan, or a recorded user decision | intent and constraints; no source or issue authority |
| A published issue | its verified identity and content, plus only the relationships actually read back |
| Git and GitHub | source, ancestry, commits, pull requests, checks, reviews, and merge evidence |
| Audit, QA, or response reports | sanitized, non-authoritative observations |

A closed issue or a finished status never proves that code landed, was reviewed, or was merged. An
issue URL supplies context, not implementation permission, and a partial publication keeps the
confirmed part while reporting the unproved part.

## Retained records

Existing `.woostack/tmp/runs/<run-id>/` artifacts stay readable historical user data and authorize
nothing. A record becomes evidence only after its exact identity, complete content, and freshness are
validated. The [local artifacts reference](/docs/configuration/artifacts/local) owns their
preservation and recovery, and the [Hermes guide](/docs/hermes) shows how an external engineer
reviews harness evidence without receiving implementation authority.
