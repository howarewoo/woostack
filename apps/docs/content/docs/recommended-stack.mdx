This stack is a starting point for a TypeScript product with a public website, a signed-in
web application, and an API. It favors static public content and a client-rendered app,
released together on Cloudflare Workers. Native mobile is an optional later addition.

These are recommendations, not requirements for using Woostack. Existing repositories keep
their selected technologies and conventions. This documentation site itself uses Next.js
and Fumadocs; its implementation and deployment are described in the
[docs app README](https://github.com/howarewoo/woostack/blob/main/apps/docs/README.md).

For deployment steps, see [Deploy a full-stack Cloudflare Worker](/docs/guides/deploy-cloudflare).
For the engineering principles behind application boundaries, see
[Repository structure and rules](/docs/concepts/repository-rules).

## Stack

The core web stack separates public content, interactive application screens, and server-side
work. Optional tools address specific needs rather than becoming dependencies of every project.
Package versions belong in the consuming project's manifests and lockfile; this list is not a
certified compatibility matrix.

| Responsibility | Recommendation | Role |
| --- | --- | --- |
| Language and tooling | TypeScript, ES modules, Node.js | Node runs local tooling and Node deployments; Workers has its own runtime. |
| Workspace | pnpm workspaces | Keeps app dependencies separate. Turborepo is optional when cross-app task orchestration and caching help. |
| Public site | Astro | Prerenders marketing pages, blog posts, and other public content. |
| Web application | React, Vite, standalone TanStack Router | Provides client-rendered screens, typed navigation, and URL state. TanStack Start is not part of this recommendation. |
| Remote data | TanStack Query, oRPC | Query manages remote-data caching; oRPC supplies typed API calls. |
| API | Hono, oRPC, Zod | Handles HTTP requests, procedures, and runtime input validation. |
| Database | Neon PostgreSQL, Drizzle ORM, Drizzle Kit, pg | Stores application data; Drizzle Kit owns migrations. Hyperdrive pools Workers connections. |
| Authentication | Managed Neon Auth | Provides managed authentication; the API still verifies sessions and enforces authorization. |
| Web UI | Tailwind CSS, shadcn/ui with Base UI primitives | Supplies styles and reusable web controls. |
| Documentation | Fumadocs with Astro | Adds documentation layouts, MDX content, and static search to the public site. |
| Deployment | Cloudflare Workers, Wrangler, GitHub Actions | Releases public assets, app assets, and the API as one unit per environment. |

Supporting tools depend on what the product needs:

| Need | Recommendation |
| --- | --- |
| Native mobile | React Native, Expo, Expo Router; DOM components for selected web screens |
| Component catalog | Storybook with React/Vite |
| UI utilities | Recharts, date-fns, Embla Carousel, or React Day Picker where needed |
| Translated application UI | i18next and react-i18next |
| AI features | TanStack AI with direct provider adapters |
| App and component tests | Vitest, React Testing Library with a DOM environment |
| Critical browser journeys | Playwright |
| Standalone Node script tests | Native Node.js test runner and tsx, without duplicating Vitest suites |
| Linting and formatting | Oxlint, @shadcn/lint, Oxfmt |
| Local infrastructure | Docker Compose, PostgreSQL, a local HTTPS Better Auth fixture, Wrangler |

A local auth fixture supports development without proving managed-auth integration. Trusted
preview checks cover the production provider, callbacks, and cookie behavior.

## Application boundaries and rendering

The public site and signed-in app have different readers and rendering needs. Separate workspace
apps let each use an appropriate renderer while sharing UI or contracts where there is real reuse.

Astro owns public routes such as `/`, `/pricing/`, `/blog/`, and `/docs/`.
[Static generation](https://docs.astro.build/en/guides/on-demand-rendering/) produces their HTML
at build time. Readers and crawlers receive the main content without waiting for client JavaScript.
[React islands](https://docs.astro.build/en/guides/framework-components/) add interactive sections,
such as a pricing calculator, without making every page a single-page application (SPA).

The React/Vite app uses
[standalone TanStack Router](https://tanstack.com/router/latest/docs/framework/react/installation/with-vite)
for navigation. After loading the app shell, the browser renders screens and requests data from the
API. This suits signed-in workflows that do not need search indexing. TanStack Query caches server
data in the client; it does not replace server-side authorization or database consistency.

Request-time server-side rendering (SSR) is a separate choice for public pages whose initial HTML
needs fresh or request-specific data. It adds an adapter and server-handler integration. A different
client router alone does not supply SSR, and static public content does not need SSR on every request.

### Blogs and documentation

Git-backed Markdown in [Astro Content Collections](https://docs.astro.build/en/guides/content-collections/)
is the blog default. Posts live with the public site and produce complete article HTML under
`/blog/`. MDX is useful when a post needs embedded components; plain Markdown keeps ordinary writing
independent of component imports.

A small content schema can require `title`, `description`, and `pubDate`, default `draft` to `false`,
and leave update dates, tags, and cover images optional. Shared layouts own article styling and
metadata. Filename-derived content IDs can supply URLs, but a renamed published URL needs a redirect.

Publication filters matter at every output boundary. A draft excluded only from the index can still
have a published page. Routes, indexes, RSS, sitemaps, and search must agree on which posts are public.
Future-dated posts need the same treatment when scheduling is supported. Static output changes only
after a build and deployment; a publication date alone cannot trigger a release.

[Fumadocs with Astro](https://www.fumadocs.dev/docs/manual-installation/astro) brings documentation UI
and MDX components into the same public-site build under `/docs/`. Prerendered articles and a
[static search index](https://www.fumadocs.dev/docs/deploying/static) avoid a separate documentation
server. The search index belongs on the public host, outside the app-only `/api` namespace.

A CMS becomes useful when authors need browser editing, media management, or editorial releases
independent of repository changes. That changes the authoring workflow without necessarily changing
static rendering.

## Runtime architecture

The proposed deployment uses **one Cloudflare Worker per environment** with
[two Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/):

| Host | Responsibility |
| --- | --- |
| `example.com` | Astro public site, including blog and documentation |
| `app.example.com` | React app at `/` and Hono API at `/api` and `/api/*` |

<StackRuntimeDiagram id="stack-runtime" />

A visitor opens a public page on the root host, then follows a link to the app subdomain.
The app loads its shell and calls `/api/*` on its own origin. Hono verifies the session and
authorization before accessing protected data. Database credentials stay on the server.

Sharing a Worker does not make the hostnames the same browser origin. Public-site browser calls
to the app API require an explicit CORS policy. Host-scoped application cookies avoid sharing
sessions with every subdomain; authentication callbacks must match the intended app origin.

The [ASSETS binding matches pathnames, not hostnames](https://developers.cloudflare.com/workers/static-assets/binding/#runtime-api-reference).
The Worker therefore selects the host before looking up a file in the internal `/site/` or `/app/`
asset namespace. Only app-host HTML navigation can fall back to the SPA shell. Missing public pages,
API routes, and static files remain 404 responses.

Worker-first dispatch also invokes code for asset requests. The benefit is one release unit; the
cost is shared deployment timing and Worker configuration for both apps. It is a deliberate topology,
not a Cloudflare requirement for every product.

### Source apps and releases

The diagram uses example paths for a downstream application, not this repository's layout.

GitHub Actions builds the separate sources, assembles both asset namespaces, and verifies the Worker
before release. The Worker and both frontends deploy together. Database migrations remain an explicit
release step with their own compatibility and recovery requirements. A Worker rollback does not
undo a database migration.

## Mobile apps

A React/Vite web app, with PWA capabilities where needed, is the starting point. App-store distribution
and native interaction can justify a separate React Native app with Expo. When React Native is the
long-term target, using Capacitor as an intermediate platform adds another migration.

[Expo Router](https://docs.expo.dev/router/introduction/) owns native stacks, tabs, and modals.
TanStack Router stays in the browser app.
[Expo DOM components](https://docs.expo.dev/guides/dom-components/) can reuse selected web screens
inside the native shell while high-value workflows move to native controls.

| Boundary | What can be reused | What remains separate |
| --- | --- | --- |
| Shared source | Business logic, types, validation, API contracts, translation catalogs | Platform initialization and device integrations |
| DOM component | Browser UI, CSS, and shadcn/ui controls, marked with `'use dom'` | Runs in a WebView, not as native controls; native views cannot nest inside it |
| Native-to-DOM connection | Serializable props and asynchronous native actions | React context, global state, and query caches are not automatically shared across runtimes |

Expo CLI and Metro bundle reused source; an unchanged Vite build is not the input. DOM components
make incremental replacement possible, but do not themselves improve native performance. Frequent
workflows, keyboard-heavy forms, lists, and gestures are stronger candidates for native UI than
infrequently used content screens.

Mobile calls the existing backend through an absolute HTTPS URL rather than same-origin `/api`.
Authentication, redirects, and session persistence need platform-specific integration. Login,
session restoration, authenticated requests, and logout on a real target device are the early
feasibility checks before a broad screen migration.

Native binaries have a separate release lifecycle. [EAS Build](https://docs.expo.dev/deploy/build-project/)
and [EAS Submit](https://docs.expo.dev/deploy/submit-to-app-stores/) are the preferred build and upload
tools; web and API releases remain on Cloudflare. Apple's
[minimum-functionality guideline](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality)
still applies. A native navigation bar around a website does not guarantee store approval.

## Internationalization

For multilingual React web and native UI, i18next with react-i18next allows translation catalogs,
supported locales, and fallback rules to be shared. Initialization, language detection, and
persistence stay in each app. Private app routes do not need locale prefixes simply to translate
interface text. Bundled startup translations keep mobile UI available offline; a hosted translation
service is optional.

Public content has a different concern: stable localized URLs.
[Astro's i18n routing](https://docs.astro.build/en/guides/internationalization/) owns those paths,
while translated articles and documentation belong in the content layer. i18next core can supply
interface strings through an [explicit page locale](https://www.i18next.com/overview/api#getfixedt).
Changing a shared global language during rendering risks mixing concurrent pages' locales.

## AI provider library

[TanStack AI](https://tanstack.com/ai/latest/docs/getting-started/overview) is the recommended
TypeScript library for streaming and typed tool calling through direct provider adapters, such as
`@tanstack/ai-openai` and `@tanstack/ai-anthropic`. No AI gateway is required for this design.

Clients call an authenticated Hono endpoint, which invokes the selected adapter. Provider code and
API keys stay on the backend in Worker secrets, never in `VITE_*` or `EXPO_PUBLIC_*` variables.
React clients use `@tanstack/ai-react`; the
[React Native guide](https://tanstack.com/ai/latest/docs/getting-started/quick-start-react-native)
covers an absolute backend URL and XHR streaming transport.

Provider and model capabilities vary. Adoption depends on verifying the chosen adapter in Wrangler
and the mobile transport on target devices, not just on the library exposing a common API.

## SEO

Public content benefits from meaningful HTML before JavaScript runs.
[Prerendering or server rendering](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)
also serves crawlers that do not execute JavaScript. Static Astro output meets that need without
request-time SSR. Private application screens have no equivalent search requirement.

| Concern | Public-site expectation |
| --- | --- |
| Page identity | Descriptive title, meta description, canonical production URL, semantic headings, and crawlable links |
| Link previews | Open Graph metadata in the page HTML |
| Structured data | Relevant types, such as `Article`, matching visible content; rich results are not guaranteed |
| Discovery | Sitemap entries for indexable public pages only, using the root domain without internal asset prefixes |
| URL changes and misses | HTTP redirects for moved pages; HTTP 404 for missing pages rather than a successful app shell |

Each hostname has its own `robots.txt`; the root domain's file does not control the app subdomain.
The app shell and previews are non-indexable by default, using `noindex` in initial HTML or an
`X-Robots-Tag` header. A deliberately public app page needs a separate indexing decision. Crawlers
must be able to fetch a URL to see its `noindex` directive, so blocking that URL in `robots.txt`
prevents the directive from being read. Neither mechanism protects private data; authentication does.
Production public pages must not inherit preview indexing restrictions.

Limited client JavaScript, sized images, and stable layouts support loading and interaction quality.
[Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals) measure those
outcomes; a rendering choice alone does not establish performance or ranking. The
[deployment checks](/docs/guides/deploy-cloudflare#2-verify-the-built-application) cover raw HTML,
metadata, search, and status codes. Search Console and PageSpeed Insights supply production evidence.

## Scaling the stack

A distributed stateless API does not give PostgreSQL unlimited throughput or make writes local to
every user. Useful evidence includes slow queries, CPU and I/O, lock waits, connection-pool waits,
and API tail latency. Registered-user counts alone do not identify the bottleneck.

Indexes, bounded results, fewer SQL round trips, and short transactions are the first improvements.
External calls inside a transaction occupy connections while doing no database work. Increasing a
pool can worsen overload. [Hyperdrive pooling](https://developers.cloudflare.com/hyperdrive/configuration/tune-connection-pool/)
reuses origin connections, but its budget must leave room for other clients and configurations.
[Neon autoscaling](https://neon.com/docs/introduction/autoscaling) adds compute within configured
bounds; it cannot remove contention on a frequently updated row.

### Different workloads need different additions

These services are options for a measured bottleneck, not baseline dependencies.

| Workload | Option | Consequence |
| --- | --- | --- |
| Repeated public HTTP responses | [Cloudflare cache](https://developers.cloudflare.com/workers/reference/how-the-cache-works/) | Avoids SQL on a hit. Cache API entries and deletion are data-center-local; shared responses must not leak personalized data. |
| Infrequently changed configuration or derived values | [Workers KV](https://developers.cloudflare.com/kv/concepts/how-kv-works/) | Eventually consistent; changes can take 60 seconds or more to appear elsewhere. Unsuitable for immediate permission revocation or strict counters. |
| Repeated SQL reads that tolerate stale data | [Hyperdrive query caching](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/) | Caches eligible reads. Writes do not invalidate results. |
| Strict quotas, rooms, or per-resource coordination | [Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) | Strong coordination within each object; one global object can become a bottleneck. |
| Best-effort abuse limits | [Workers Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) | Approximate, location-local limits rather than a strict worldwide quota. |
| Write bursts, notifications, or imports | [Cloudflare Queues](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) | At-least-once delivery needs idempotent effects. Bounded consumer concurrency protects the database; a queue cannot fix sustained overload. |
| Reads or reporting exhausting primary compute after tuning | [Neon read replicas](https://neon.com/docs/introduction/read-replicas) | Adds read-only compute with explicit routing and eventual consistency, not more write capacity. |
| Expensive recurring reports | Precomputed summaries or separate analytics | Reduces transactional work at the cost of freshness and pipeline complexity. |
| Hot-row writes or a dominant tenant | Data-model changes, tenant isolation, then sharding if justified | Addresses write contention; sharding adds routing, migration, and cross-shard query costs. |

### Freshness determines the read path

Hyperdrive query caching is enabled by default. A cache-disabled binding retains pooling while
providing the fresh-read path for authorization, billing, and read-after-write behavior. Separate
cached and uncached database clients make that boundary explicit. Replica reads also cannot serve
flows that require the latest committed primary state.

For example, a public catalog may tolerate cached results. A permission check after access has been
revoked cannot use the same stale read path. Tenant-scoped cache keys, authorization checks, expiry,
invalidation, and bounded cache-miss concurrency protect private data and recovery under load.

KV is not an atomic Redis substitute. Durable Objects can own coordinated state, but their consistency
does not extend into a PostgreSQL transaction. Making both systems authoritative for the same value
creates a synchronization problem. Redis remains useful for its specific structures, atomic operations,
or existing integrations, at the cost of another network dependency.

### Geography still matters

Edge execution does not eliminate distance to the database writer. Fewer sequential SQL calls and
cached reads help global users; writes still reach the primary. Neon read replicas are in the primary's
region. Cross-region replicas require a separate project and logical replication. Regional tenant
placement or a different write architecture is a larger decision driven by measured latency and
consistency requirements.
