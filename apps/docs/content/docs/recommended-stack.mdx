My preferred stack starts with TypeScript web applications and adds native mobile apps
when needed. It is not a requirement for using Woostack.

## Application boundaries and rendering

Keep the public site and SaaS application in separate workspace apps, with shared UI
packages where useful. They have different rendering needs but share one deployment.

[Standalone TanStack Router](https://tanstack.com/router/latest/docs/framework/react/installation/with-vite)
is the routing recommendation for React/Vite SaaS applications and single-page applications
(SPAs). It handles typed navigation and URL state; TanStack Query owns remote-data caching,
and oRPC provides typed API calls. TanStack Start is not part of this stack.

Astro owns public-facing content such as `/`, `/pricing`, and `/blog/*`.
[Static generation](https://docs.astro.build/en/guides/on-demand-rendering/) produces HTML
at build time, so ordinary marketing pages need no request-time rendering service.
[React components](https://docs.astro.build/en/guides/framework-components/) can provide
interactive islands, such as a pricing calculator, without turning the whole site into a SPA.
Request-time server-side rendering (SSR) is reserved for pages whose initial HTML needs
fresh or request-specific data. It requires an adapter and server-handler integration,
not just a different client router.

For public documentation, [Fumadocs + Astro](https://www.fumadocs.dev/docs/manual-installation/astro)
combines customizable React layouts and MDX components with Astro's page routing and static
generation. Fumadocs supplies the documentation UI; Astro owns the site build. The recommended
integration is Astro, not Next.js.

Documentation normally lives at `example.com/docs/` in the same public-site build as marketing
and blog pages. Articles are prerendered and the search index is generated at build time;
interactive Fumadocs UI still uses React islands. Documentation shares the public site's
assets and GitHub Actions release, without a separate Worker or deployment pipeline.

## Mobile apps

The default starting point is a React/Vite web app and progressive web app (PWA).
When app-store distribution is warranted and a native experience is the long-term goal,
use React Native with Expo as the first mobile platform. Skip Capacitor as an intermediate
step before a planned React Native migration. There is no need to build a mobile app
before the product warrants one.

The mobile app lives in a separate workspace app, with
[Expo Router](https://docs.expo.dev/router/introduction/) owning native stacks, tabs, and
modals from the first mobile release. TanStack Router remains the browser router.
[Expo DOM components](https://docs.expo.dev/guides/dom-components/) use `'use dom'` to reuse
existing web screens or self-contained sections inside that native shell. They run in
WebViews, not native controls; the benefit is incremental replacement without changing
mobile platforms, not an immediate native performance improvement.

Native UI replaces web screens where it improves the experience most, such as frequent
workflows, keyboard-heavy forms, lists, and gestures. Rich-text rendering or infrequently
used screens can remain DOM components when replacement adds little value. A complete
native rewrite is not a prerequisite for the first mobile release.

### Code sharing and integration boundaries

Share platform-independent business logic, types, validation, API contracts, and translation
catalogs where useful. Web UI, including shadcn/ui and browser CSS, does not become native UI.
DOM components use separate runtimes; React context, global state, and query caches are not
automatically shared with native screens. Small serializable props and asynchronous native
actions keep that boundary explicit. Native views cannot be nested inside DOM components.
Device integrations belong on the native side so they survive screen replacement.

Expo CLI and Metro bundle reused web source; an unchanged Vite build is not the input.
The existing Cloudflare-hosted backend stays in place, with the mobile app calling its
configured HTTPS API rather than assuming same-origin `/api` requests. Authentication,
redirects, and persistence need platform-specific integration. A representative flow on a
real iPhone should verify login, session restoration, logout, and authenticated requests
before substantial UI migration.

### Mobile delivery

Mobile binaries have a separate release lifecycle from the web deployment. Prefer
[EAS Build](https://docs.expo.dev/deploy/build-project/) and
[EAS Submit](https://docs.expo.dev/deploy/submit-to-app-stores/) for native builds and store
uploads; the public site, PWA, and API keep their existing Cloudflare deployment.
Apple's [minimum-functionality guideline](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality)
still applies: Expo or a native navigation bar does not guarantee approval for a repackaged
website.

## Internationalization

When multilingual support is required, use [i18next](https://www.i18next.com/) with
[react-i18next](https://react.i18next.com/) for React/Vite and React Native applications.
Share translation catalogs, supported locales, and fallback configuration where useful;
keep initialization, locale detection, and persistence in each application. Private SaaS
routes do not need locale prefixes just to translate their interface.

Mobile apps should [bundle the translations](https://www.i18next.com/how-to/add-or-load-translations)
needed at startup so they remain available offline. A hosted translation service is optional.

For public sites, [Astro's native i18n routing](https://docs.astro.build/en/guides/internationalization/)
owns localized URLs. Keep static generation as the default, using i18next core for interface
strings with an [explicit page locale](https://www.i18next.com/overview/api#getfixedt) rather
than changing a shared global language during rendering. Translated articles and documentation
stay in the content layer.

## Runtime architecture

Deploy the public site, web app, and Hono API as **one Cloudflare Worker per environment**, with
[two Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/):
`example.com` for the Astro public site and `app.example.com` for the SaaS application
and its `/api` endpoints. The app uses `/` as its route base, not `/app/`.

These are two browser origins, even though they share a Worker. The SPA calls `/api/*`
on its own origin. Public-site links open the app subdomain; browser API calls from the
public site would be cross-origin and need an explicit CORS policy.

<StackRuntimeDiagram id="stack-runtime" />

Cloudflare's [asset binding matches pathnames, not hostnames](https://developers.cloudflare.com/workers/static-assets/binding/#runtime-api-reference).
Separate asset directories and Worker-first dispatch prevent both hosts from resolving to
the same index file. This topology runs Worker code for asset requests too. It keeps one
release unit, but the two apps share deployment timing and Worker configuration.

## SEO

Public pages should return their main content and metadata in the initial HTML. Google can
render JavaScript, but [server rendering or prerendering](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)
also serves crawlers that do not run it. Static Astro output meets this requirement; SSR
is not an SEO requirement for every request. Private SaaS screens do not need SSR for search.

### Content and metadata

Each indexable page needs a descriptive title, meta description, canonical production URL,
semantic headings, and crawlable links. A shared Astro layout can keep these consistent.
[Open Graph metadata](https://ogp.me/) supplies shared-link previews.
Relevant [structured data](https://developers.google.com/search/docs/appearance/structured-data/intro-structured-data),
such as `Article` for a blog post, must match visible content; it does not guarantee rich results.

### Discovery and indexing

Astro's `site` setting is `https://example.com` for
[`@astrojs/sitemap`](https://docs.astro.build/en/guides/integrations-guide/sitemap/).
Public canonical URLs and sitemap entries use that root domain, never the internal asset
prefixes. Only indexable marketing, blog, and documentation URLs belong in the public sitemap, not
`app.example.com` screens, API routes, previews, or noncanonical duplicates.
Each hostname has its own [`robots.txt`](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt);
the root domain's file advertises the public sitemap and does not control the app subdomain.
Moved pages need HTTP redirects; missing public pages need HTTP 404 responses, not a
successful SPA shell.

Authentication protects private data. The app subdomain is non-indexable by default;
any deliberately public app page needs an explicit indexing decision. For reachable app
shells and preview pages,
[`noindex`](https://developers.google.com/search/docs/crawling-indexing/block-indexing) belongs
in the initial HTML or `X-Robots-Tag` response header. Crawlers must be able to fetch it;
blocking the same URL in `robots.txt` prevents them from seeing the directive. Neither
`robots.txt` nor `noindex` is access control. Production public pages must not inherit preview
indexing restrictions.

### Performance and verification

Limited client JavaScript, appropriately sized images, and stable layouts help the public
site load and respond well. [Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals)
measure loading, responsiveness, and visual stability; rendering choice alone does not
establish good performance or search ranking.

The [deployment checks](/docs/guides/deploy-cloudflare#2-verify-the-built-application) cover
raw HTML, metadata, sitemap URLs, and response status before release. Search Console URL
Inspection and PageSpeed Insights provide production indexing and performance evidence.

## Scaling the stack

Workers can scale the stateless API across Cloudflare's network, but that does not
give PostgreSQL unlimited throughput or make writes local to every user. Capacity
depends on query cost, transaction duration, contention, and cache hit rate, not
registered-user counts. Slow queries, database CPU and I/O, lock waits, connection
pool wait time, and API tail latency distinguish the bottlenecks.

### Database capacity comes first

Indexes, bounded result sets, fewer database round trips, and short transactions
usually offer more value than another service. External API calls inside a database
transaction hold connections while doing no database work. Larger pools can make
an overloaded database slower rather than increase throughput.

[Hyperdrive connection pooling](https://developers.cloudflare.com/hyperdrive/configuration/tune-connection-pool/)
reuses origin connections across Cloudflare's edge network. Its connection budget needs room for
other database clients and every Hyperdrive configuration targeting that database.
[Neon autoscaling](https://neon.com/docs/introduction/autoscaling) adds compute
within configured bounds when efficient queries still saturate the database.
Neither removes contention on frequently updated rows.

### Match the scaling option to the workload

Cloudflare-native services are the default additions for the Workers deployment,
not mandatory dependencies. Each solves a different problem.

| Workload | Preferred option | Boundary or tradeoff |
| --- | --- | --- |
| Repeated public HTTP responses | [Cloudflare cache](https://developers.cloudflare.com/workers/reference/how-the-cache-works/) | Avoids SQL on a hit. The Workers Cache API is data-center-local; a local delete is not global invalidation. Shared caches must not expose personalized responses. |
| Read-heavy configuration or derived values that change infrequently | [Workers KV](https://developers.cloudflare.com/kv/concepts/how-kv-works/) | Globally cached reads, with eventual consistency. Updates can take 60 seconds or more to become visible elsewhere. Unsuitable for strict counters or immediate permission revocation. |
| Repeated SQL reads that tolerate stale results | [Hyperdrive query caching](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/) | Avoids origin queries for eligible cache hits. Writes do not invalidate cached results; pooling alone does not add read replicas. |
| Strict per-user or per-credential quotas, collaborative rooms, or per-resource coordination | [Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) | Strongly consistent storage and coordination within each object. One object per coordination key distributes load; one global object becomes a bottleneck. |
| Best-effort API abuse protection | [Workers Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) | Fast, approximate limits maintained separately per Cloudflare location. Not a strict worldwide quota. |
| Write bursts or deferrable work such as notifications and imports | [Cloudflare Queues](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) | Buffers bursts, not sustained database overload. At-least-once delivery requires idempotent side effects; bounded consumer concurrency protects PostgreSQL. |
| Read traffic or reporting that exhausts primary compute despite query tuning | [Neon read replicas](https://neon.com/docs/introduction/read-replicas) | Additional read-only compute, with explicit application routing. Replicas are eventually consistent and do not increase write capacity. |
| Expensive recurring reports | Precomputed summaries or a separate analytical workload | Trades freshness and pipeline complexity for less transactional database work. A replica can isolate reporting compute before a separate analytics system is justified. |
| Hot-row writes or tenants that dominate traffic | Data-model changes, tenant isolation, then sharding when justified | Cache does not resolve authoritative write contention. Sharding adds routing, migration, and cross-shard query costs. |

### Freshness and state ownership

Hyperdrive query caching is enabled by default. A cache-disabled Hyperdrive
binding retains connection pooling and is the appropriate path for reads that
must be fresh, including authorization, billing state, and read-after-write flows.
Separate cached and uncached Drizzle clients make that distinction explicit.
Replica reads are also unsuitable when a flow requires the latest committed
state; those reads belong on the uncached primary path.

KV suits values whose stale window is acceptable. It is not a drop-in Redis
replacement for atomic updates. Durable Objects suit strongly coordinated state
owned by one user, credential, room, or resource, but their consistency does not
extend into a PostgreSQL transaction. Keeping the same authoritative state in
both systems introduces a synchronization problem.

For application-managed caches, tenant-scoped keys and authorization checks
protect private data. Expiry, invalidation, and bounded cache-miss concurrency
determine what happens after a write or when many entries expire together.
Redis remains an option when a workload needs its specific data structures,
atomic operations, or an existing integration. It is not the default shared cache
for this deployment; a remote Redis service adds another network dependency.

### Geographic limits

Edge execution does not remove the distance to the database writer. Fewer
sequential SQL round trips and cached reads help global users, while writes still
reach the primary. Neon read replicas are in the same region as their primary;
cross-region replicas require a separate project and logical replication.
Regional tenant placement or a different write architecture is a larger design
decision, justified by measured latency and consistency requirements.
