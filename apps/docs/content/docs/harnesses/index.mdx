---
title: Assistant capabilities
description: Required capabilities, skill invocation, and behavior when an operation is unavailable.
---

Woostack skills are instructions for a coding assistant. They do not depend on a named harness,
agent catalog, or tool API. The active session's tools, schemas, and permissions determine which
operations are available. Installing a skill does not grant access or enable missing tools.

## Native skill invocation

A `/woostack-*` example in this documentation names a skill request, not a terminal command or a
universal invocation syntax. Request the skill by its public name using your assistant's supported
skill-loading mechanism. For example, request `woostack-whiteboard` with a goal to plan, or
`woostack-execute` with a bounded change to implement. Confirm that the named skill is available
before relying on its workflow.

Invocation syntax does not change a skill's authorization rules. An explicit Execute request
includes draft-PR delivery unless narrowed, for example with `local only; do not commit or push`.
An ordinary implementation request authorizes local edits and checks, not automatic publication.

## Required capabilities

Each skill owns its requirements and stopping rules. Only capabilities needed for the requested
operation matter; planning does not require implementation tools or publication access.

| Operation | Required capability | When unavailable |
| --- | --- | --- |
| Load a skill | Access to its instructions and bundled assets | For an explicit missing skill, name it and ask whether to install it or proceed without it. |
| Inspect existing code | Authorized reads of the selected source | Report the evidence gap; do not invent current behavior. |
| Implement a change | Authorized file edits and applicable verification tools | Leave affected implementation or acceptance unmet. |
| Delegate work | A permitted worker launcher and a suitable task context | Keep optional work inline; required delegation remains blocked. |
| Run isolated visualization | A native subagent or isolated task context | Leave Visualize unrun rather than loading it in the parent. |
| Publish to GitHub | Authorized access to the exact target and required operations | Stop affected publication, not unrelated local work. |
| Apply a model or effort override | A supported field and permission to use it | Disclose an unsupported optional override; required exact identity blocks without matching evidence. |

## Workers and workspaces

A worker handles an assigned task and returns its results. A separate conversation context does
not by itself restrict which files it can edit. Concurrent writers need independently owned
workspaces and scoped tasks. Workers verify the selected checkout, branch, base, and affected paths
before writing, even when the launcher accepts a workspace argument.

Use only available, permitted agents suited to the assignment. Keep configured role and model
routing unless the user requests an override. Woostack does not provision replacement agent
definitions, change assistant settings, or manage session titles and provider recovery.
Existing assistant configuration, extensions, and retained records remain user-owned; portability
changes do not authorize their cleanup or migration.

## Evidence limits

Tool availability and successful dispatch do not prove which model ran or that a workflow completed.
Report actual outputs and verification separately from configuration, documentation claims, and
unrun checks. A successful run in one assistant is not proof of compatibility with another.
