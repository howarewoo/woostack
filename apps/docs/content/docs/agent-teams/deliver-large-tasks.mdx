---
title: Deliver a large task with the agent team
description: Take a multi-issue request through the five-bot pipeline with one accountable owner at each stage.
---

A large request, such as a new feature that spans several pull requests, moves through the same
[pipeline](/docs/agent-teams) as a small fix. The difference is that it needs your decisions before
implementation starts and a coordinated set of pull requests after. This page shows how each bot
handles it. Your scope, permissions, and required approvals still apply at every step.

## 1. Steward scopes the request

1. Steward takes the request and recovers what already exists: related issues, open pull requests,
   earlier decisions in its memory, and current behavior in the code. It does not restart or
   cancel work that is already in progress.
2. It explores requirements with [Whiteboard](/docs/guides/whiteboard) and sizes the work as larger.
3. It raises **Needs you** items for the decisions that block implementation, each with a
   recommended choice. It does not hand anything to Engineer while one is open.
4. After you answer, it files the issues with acceptance criteria, notes their dependencies, and
   hands the set to Engineer in one handoff.

A plan does not authorize implementation. Your answers to the decision gates and Engineer's
`SOUL.md` do.

## 2. Engineer owns delivery

Engineer is the root owner for implementation. It handles dependencies, workers, integration, and
the final report in its chat.

1. Engineer groups the issues into pull requests with [Orchestrate](/docs/guides/coordinate-work)
   and gives a brief dependency plan. Dependent pull requests form a stack.
2. Each worker gets a bounded spec in its own child worktree: the outcome, exact inputs and base,
   allowed actions, verification, and done condition. One worker writes per worktree.
3. Independent pull requests run in parallel. When a shared contract is uncertain, Engineer verifies
   a representative slice before starting the dependent work.
4. Dispatch is not completion. Engineer waits on worker reports, CI events, and Reviewer's findings,
   inspects the actual diffs and evidence, and sends concrete corrections.
5. It marks each pull request ready for review and hands it to Reviewer once it is green, bottom of
   the stack first.

## 3. Reviewer reviews each pull request

Reviewer reviews each pull request at its exact head commit. Findings go back to Engineer, and the
worker's fix gets an incremental re-review. A clean pull request goes to Gatekeeper with the head
commit Reviewer reviewed. Restacking gives the layers above new head commits, so each goes back to
Reviewer before Gatekeeper takes it.

## 4. Gatekeeper merges in order

Gatekeeper calls each pull request's risk on its own. A stack merges bottom-up: Gatekeeper merges a
layer, waits for its deploy, and only then takes the next layer. A high-risk layer waits for your
merge, and the layers above it wait too. See the [merge checklist](/docs/agent-teams/gatekeeper#merge-checklist).

## 5. Sentinel watches each deploy

Each merge can start a production deploy. Sentinel investigates any that fail and files one issue
per failure. A fix goes back to Engineer as a new bounded handoff, not as a change to a pull request
that already merged.

## Handle blockers

When a step stops producing new evidence, the owner of that step sets it aside and continues
independent work. It records the missing fact, the affected acceptance criteria, who must act next,
and what will resume the work. Then it waits on an event or a **Needs you** answer, not on a polling
loop. If no automation can resume the work, it says how to resume it by hand.

## Finish

Engineer reports in its chat with the pull request links, the acceptance evidence, what is merged,
what is deployed, and what still waits for you. Delivered, blocked, waiting for you, and live are
different states, and the report keeps them apart. A successful worker or a green check does not by
itself mean the request is done.
