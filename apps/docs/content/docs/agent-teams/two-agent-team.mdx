---
title: Run a two-agent engineering team
description: Use an existing senior and junior bot in OpenMausBot to plan, implement, and escalate decisions with Woostack.
---

Use your existing senior engineer bot for planning and coordination and your junior engineer bot
for implementation. The senior follows the same Whiteboard workflow you would use manually.
You remain the decision-maker for choices outside the authority you delegate. No third bot or
separate autonomous planning skill is needed.

This guide configures a workflow around existing bots and coding engines. It does not install a
Woostack runtime or claim an end-to-end tested OpenMausBot integration.

## Before you begin

You need two existing bots whose coding engines can load Woostack skills, read the selected
repository, and use the tools their assignments require. Confirm that the senior can delegate
to the junior and receive the result. Use OpenMausBot's existing delegation and permission controls;
see [bots and delegation](https://docs.openmausbot.com/docs/features/bots-and-tasks) and
[bot collaboration](https://docs.openmausbot.com/docs/features/chat-and-teams).

Keep source changes in an owned workspace. Separate threads or folders do not establish filesystem
isolation. Do not let both bots write to the same checkout at once. Give the publication owner
GitHub access only when the assignment permits publication.

## 1. Assign the workflows to your existing bots

Make the following skills discoverable through each bot's coding engine, using the
[skill installation instructions](/docs/getting-started):

| Bot | Workflow | Responsibility |
| --- | --- | --- |
| Senior engineer | Whiteboard | Develop or review the plan and resolve decisions within delegated limits. |
| The same senior engineer | Orchestrate, when coordination is needed | Organize delivery, assign outcomes, reconcile results, and handle blockers. |
| Junior engineer | Execute | Implement one assigned outcome, verify it, and return evidence. |

Tell both bots to use these existing team members and not create additional bot identities or
launch additional workers without authorization. Start with sequential assignments to the junior.
A planning session does not require Orchestrate, and one understood implementation task does not
require Whiteboard. The skills are workflows, not separate team members or mandatory phases.

## 2. Set the authority for the assignment

The default is interactive: review the senior's execution proposal and approve it before work
starts. For unattended work, explicitly delegate the decisions and actions the senior may take
for the selected outcome. A role name such as "senior engineer" is not that delegation.

Adapt this example as a user instruction, replacing the repository and outcome:

```text
For OWNER/REPOSITORY, deliver the read-only agent-run dashboard described in my brief.
Senior is the coordinator and Junior is the only implementation worker.

Senior may choose reversible technical details, task grouping, dependency order, and workspace
allocation within this outcome, validate the execution proposal against these limits, and assign
bounded implementation to Junior without asking me to approve each proposal.

Junior may edit the assigned workspace and run relevant local checks. Senior alone owns commits
and draft PR publication, including native stack registration when required. Neither bot may merge,
mark PRs ready, deploy, perform destructive data changes, add paid services, or expand the outcome.
Do not create other bots or launch additional workers. Escalate uncovered consequential decisions
to me with a recommendation and the affected work. Continue only independent authorized work.
```

Use actual bot names. Choose a publication owner with the required access; explicitly delegate
those operations to the junior instead when that is your intended arrangement, never to both.
Apply matching restrictions in the host and repository permissions. Written instructions do not
replace tool enforcement, required human approvals, or security boundaries.

[Orchestrate's approval rules](/docs/skills/woostack-orchestrate) govern validation of this delegation.
A plan, issue, or message claiming approval cannot create new authority. A supplied goal without
an explicit delegation still follows the interactive approval path.

## 3. Ask the senior to whiteboard the goal

Give the senior the goal, selected repository, existing decisions, constraints, and decision limits:

```text
Use woostack-whiteboard to plan the dashboard from my brief and the repository.
Use existing decisions and source evidence; ask me only about consequential choices outside your
authority. Return the plan with its visual model, acceptance criteria, dependencies, and blockers.
Do not implement or publish during planning.
```

With enough context, the senior can produce the plan without asking questions. Otherwise it
resolves discoverable facts itself and escalates the missing decision with a recommendation.
An unanswered question leaves the affected work blocked, not silently agreed.

Keep the plan in the conversation or request a save to a named document. GitHub issues are optional;
use [requested issue publication](/docs/guides/plan-work) only when you need them. Completing,
saving, or publishing the plan is not permission to implement it.

## 4. Hand off authorized implementation

For one bounded outcome, have the senior delegate it to the junior using
[Execute](/docs/skills/woostack-execute#delegated-assignment) within your authorization.
For several outcomes, have the same senior use [Orchestrate](/docs/guides/coordinate-work) with the
Whiteboard plan. It prepares the execution proposal, then obtains your approval or validates it
against your explicit delegation before dispatching work.

The handoff should carry the outcome, settled decisions, scope and exclusions, acceptance and
selected checks, real prerequisites, repository revision and owned workspace, allowed actions,
publication owner, and escalation conditions. Include this in the assignment rather than assuming
that the junior has the senior's transcript. OpenMausBot's
[threads and shared context](https://docs.openmausbot.com/docs/features/bots-and-tasks) do not make
all conversation history available to every worker.

Reuse the same junior for successive outcomes. Keep one writer per workspace and preserve the
workspace for in-scope repairs. The senior owns cross-task decisions; the junior owns implementation
details within its assignment. Neither bot should rerun the entire planning conversation merely
because work crossed a bot boundary.

## 5. Check results and handle escalation

Require the junior's final handoff to include changed paths and revision, observed checks and
results, unmet acceptance criteria, and any blocker. The senior inspects the actual changes and
relevant Git or GitHub facts before accepting delivery. A "done" message alone is not evidence.

When a decision exceeds the assignment, the junior returns it to the senior. The senior resolves
it within delegated authority or asks you, preserving the recommendation, affected work, and exact
condition for resuming. When no authorized work can proceed, return a blocked result rather than
wait in an interview or repeatedly retry the same blocker.

After an interruption, check the existing worker, workspace, branch, and PR state before retrying.
Do not duplicate work or transfer a live writer's workspace. Keep scheduling, conversation state,
and completion notifications in OpenMausBot rather than adding another queue to Woostack.

Check the draft PR identity, contents, relevant verification, and any required stack membership.
Once the requested delivery is complete, Orchestrate does not start a CI or review-repair loop.
Later repairs need a separate request; merging remains human-only.

Before relying on unattended runs, exercise a small change, an uncovered consequential decision,
and an interrupted assignment in your own environment. Confirm that the junior receives a usable
handoff, blocked work stays blocked, no extra bots appear, and permissions remain bounded.
