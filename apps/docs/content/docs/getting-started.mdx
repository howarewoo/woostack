title: Getting started
description: Install woostack, create useful project guidance, and return a read-only plan for your repository's README.
---

This tutorial installs woostack in a Git repository you already have, helps you create or improve
its project guidance, and finishes with a read-only plan for a Verification section in its README.
Init edits only the guidance you authorize. The planning step edits nothing, files no issue, and
opens no pull request.

Run the terminal command in step 1 yourself. Send the slash requests in the later steps to your
coding assistant, with the same repository open in both places.

## Before you start

You need:

- An existing Git repository, open in your terminal and in your coding assistant.
- A [coding assistant](/docs/harnesses), the application that runs your agent and loads its skills.
  Another host works when it exposes the capabilities a task needs.
- Node.js and pnpm. The installation command below uses `pnpx`, pnpm's tool for running a package.

Document authoring needs no `.woostack/`, Doctor check, or GitHub access. Installing the skills
requires network access, and Plan may read existing GitHub issues. This tutorial publishes no issue
or pull request. A `/woostack-*` example names the logical request; each assistant's explicit skill
invocation is listed in the [harness reference](/docs/harnesses#native-skill-invocation).

## 1. Install the skills

Run this in your terminal from the repository root:

```bash
pnpx skills add howarewoo/woostack
```

Then confirm your assistant can find the skills you plan to use, for example `woostack-init` and
`woostack-plan`. Each installed skill is self-contained and works on its own; the
[command index](/docs/skills/using-woostack#command-routing) is an optional directory, and no
skill needs another one installed. They are
instructions for the agent, not shell programs. If a skill cannot be found,
[fix the installation before continuing](/docs/guides/troubleshooting#your-assistant-cannot-find-a-woostack-skill).

## 2. Create your project guidance

Send this to your coding assistant:

```text
/woostack-init Help me adopt Woostack in this repository. Create or update
README.md, AGENTS.md, DESIGN.md, PRODUCT.md, and ARCHITECTURE.md where useful.
Inspect existing evidence, reuse decisions we have already made, and consult
with me on the project's intention, structure, direction, and architecture
before writing. Show the proposed changes and apply edits within this document
scope. Do not initialize local support, change application source, commit, or publish.
```

Init first reports its understanding: what the repository's observed implementation, documented
intent, and proposed direction suggest, and which documents need creating, updating, or preserving.
It then asks a manageable set of questions about the repository's intention, structure, direction,
and architecture, and waits for your answers before writing. Later questions and proposed edits
respond to your answers, including answers that contradict what the existing code implies; you can
defer a decision rather than inventing an answer. Review meaningful changes to direction,
constraints, and agent permissions.

The result should give each document a distinct job: `README.md` introduces the project and its
shortest verified first-use path, linking deeper docs and policies without duplicating them.
`PRODUCT.md` records the intended users and scope using the current product-record format; a visual
`DESIGN.md` follows the design-system format, while an architecture-focused one keeps its established
role. `ARCHITECTURE.md` maps technical responsibilities, relationships, and boundaries, linking to
existing detailed architecture rather than replacing it. `AGENTS.md` remains unversioned operational
guidance with actual commands, boundaries, and conditional links to the other documents. See
[document responsibilities](/docs/skills/woostack-init#document-responsibilities) for the applicable
formats. Existing canonical documents and scoped instructions stay authoritative. Init includes the
availability-aware
[adoption paragraph](/docs/skills/woostack-init#document-responsibilities) in new or updated agent
instructions, so no skill becomes a prerequisite of another.

When verification guidance is relevant, Init inspects existing check commands, CI, and available
timing evidence. It can recommend repository-specific improvements, such as removing redundant commands
or configuring native runner features, without mutating manifests, lockfiles, or CI workflows. An
adequate verification setup remains unchanged. Current commands, agreed direction, and advisory
recommendations stay distinct, so proposed tools or unconfigured caches are never documented as available.

Read the report and the resulting guidance. Check that referenced files exist and that commands
match the repository. A good existing document may need no edits. Deferred decisions should be
visible, not presented as settled facts. Init distinguishes checks it ran from commands it only
inspected. An unsafe or ambiguous file/symlink target remains blocked rather than overwritten.

## 3. Create your first plan

Send this request to your coding assistant:

```text
/woostack-plan Plan a Verification section for this repository's README.
Use the repository's existing instructions and actual check commands.
Reuse an existing section if it already serves this purpose.
Keep the scope to documentation. Return the plan here; do not file
GitHub issues or implement changes.
```

Read the returned plan before deciding anything else. A complete answer names the documentation it
inspected and the change it proposes, and says how someone would confirm the result is accurate.
The repository may already have a useful Verification section, in which case the plan leaves it
alone. A check command the repository does not have is reported as missing instead of invented.

This step writes nothing. Plan does not edit your README or create an issue, branch, commit, or
pull request. The guidance edits from step 2 are not permission to implement the plan.

## Choose what to do next

Your plan stays in the conversation until you act on it. Delivering it is a separate, explicit
request: [Deliver one change](/docs/guides/ship-change) covers implementing the plan and submitting
a draft pull request, along with the GitHub capability and isolated workspace that delivery needs.
You decide whether it happens, and only you merge it; marking a draft ready is a separate
explicit request.

If you need local configuration or diagnostic support, ask Init separately:

```text
/woostack-init Initialize local .woostack/ support only. Do not edit project guidance.
```

That support path needs Bash, Git, and `jq`. It preserves existing settings and retained records,
creates missing support paths, and runs the shipped bundle's static checks without contacting
GitHub or handling credentials. You can inspect support health later with `/woostack-doctor
--check`; a clean local check is not proof of GitHub access. Neither support setup nor a failed
support check blocks document drafting or the local plan above. See
[local configuration troubleshooting](/docs/guides/troubleshooting#doctor-reports-a-local-configuration-error)
and the [configuration reference](/docs/configuration) when you need those settings. Python 3 is
needed only for the optional retained-record reader, not document authoring or Doctor.

For any other task, the [task guides](/docs/guides) start from the result you want.
