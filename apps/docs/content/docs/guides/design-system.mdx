---
title: Create and maintain a design catalog
description: Create a project-owned component catalog, inspect drift, or request a specific repair.
---

Use Design System for a live catalog of component variants, states, and interactions. It reuses
your project's compatible components and tokens. Component and preview source remain the
implementation reference; the catalog does not generate code snippets or copy controls.

You need [the skill installed](/docs/getting-started), repository access, and permission for any
necessary catalog dependency changes. Send the examples below to your assistant using its
[skill-loading mechanism](/docs/harnesses#native-skill-invocation).

## Create a catalog

1. Request the coverage you need:

   ```text
   /woostack-design-system Create a catalog using our DESIGN.md, existing UI
   exports, and application tokens. Keep changes local.
   ```

2. Review the declared coverage and exclusions before installation or file creation. If coverage
   leaves a material choice open, the assistant asks about it. An explicit full-coverage request
   must not be silently narrowed.

   Existing catalogs stay in place. New catalogs prefer Storybook when its framework integration
   fits; otherwise the assistant explains the smaller repository-native choice. Catalog callers
   adapt to public component APIs without changing product components to fit the catalog.

3. Run the recorded development and verification commands. Check search, component links,
   keyboard and narrow-screen navigation, themes, and representative overlays.

The result should be a working catalog and a report of its location, commands, declared coverage,
gaps, and component provenance. Command results and browser observations should be reported separately.
Missing required checks leave verification incomplete.

## Inspect an existing catalog

```text
/woostack-design-system inspect the existing catalog
```

This returns a gap and drift report without changing files, dependencies, or generated output.
Use its findings to choose maintenance scope.

## Request maintenance

Name the change and what must remain intact:

```text
/woostack-design-system Repair the dialog specimen to use our existing public
Dialog API. Preserve our tokens, other specimens, and product components.
Keep changes local.
```

A tooling migration also needs an explicit request. If the change conflicts with an existing API
or design rule, the assistant reports it instead of overwriting the implementation. Unrelated
customizations and dependencies stay untouched.

Creation and maintenance end with local changes; they create no branches, commits, PRs, or issues.
Request [Deliver](/docs/skills/woostack-deliver) separately for Git delivery. For arranging existing
screen sequences rather than catalog components, use [Flow Layout](/docs/skills/woostack-flow-layout).
See the [Design System reference](/docs/skills/woostack-design-system) for detailed tooling and compatibility rules.
