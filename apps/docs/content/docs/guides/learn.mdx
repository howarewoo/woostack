---
title: Create or improve a reusable skill
description: Create a new skill or iterate on an existing one using prompts, session evidence, and feedback with WooStack Learn.
---

Use Learn to create a new skill or improve one you already use. Supply a goal, feedback,
the current conversation, or a combination. For an existing skill, the result is a targeted
change to its current source, not another skill with overlapping instructions. Learn reports
what changed, what stayed intact, unresolved decisions, and checks actually performed.

For instruction-improvement suggestions rather than skill authoring, use
[Reflect](/docs/skills/woostack-reflect). Neither skill requires the other.

## Before you begin

[Install the skills](/docs/getting-started) or add Learn alone from your project root:

```bash
pnpx skills add howarewoo/woostack --skill woostack-learn
```

Enter the requests below in your coding assistant using its supported skill-loading
mechanism. `/woostack-learn` is a skill request, not a terminal command.

Keep relevant session evidence visible or supply the examples and sources Learn should
use. To prevent file writes while you review the result, add `Return a draft without
writing files.` Otherwise, Learn can write within the requested or established project
skill destination; without one, it returns a draft.

## 1. Choose the target and evidence

### Improve an existing skill

Name the skill or its canonical source and describe the improvement. A source path makes
the target explicit. For a project that already has `skills/review-migrations/SKILL.md`:

```text
/woostack-learn Improve skills/review-migrations/SKILL.md. Clarify when
missing compatibility requirements should block a review. Preserve its
read-only boundary. Return a proposed diff without writing files.
```

A session is not required. To learn from how an existing skill performed, use:

```text
/woostack-learn Improve review-migrations using the corrections from
this session. Simplify the existing instructions instead of adding
another checklist. Return a proposed diff without writing files.
```

Learn reads the current source and relevant resources and tests before proposing changes.
It keeps unaffected behavior and permissions intact. If the canonical source is unavailable,
supply it before expecting an applicable diff; an installed copy may not be the owner.

### Capture the current session

After completing a useful workflow, enter:

```text
/woostack-learn
```

Learn looks for one coherent procedure in the visible conversation. When one existing
skill clearly owns it, Learn improves that skill; otherwise it can create one. It retains
important decisions, corrections, prerequisites, and verification rather than every tool
call. Choose among the candidates when the target is ambiguous.

### Develop a workflow from a prompt

Describe the outcome and important limits. For example:

```text
/woostack-learn Create a read-only skill for reviewing database migrations
before release. It should report findings without applying migrations.
Return a draft without writing files.
```

Learn develops the minimum procedure from the supplied goal and relevant evidence.
Proposed steps remain distinguishable from steps demonstrated in a session.

### Narrow a session with a prompt

Name the work to retain and exclude unrelated tasks:

```text
/woostack-learn Turn only the migration-review work from this session into
a reusable skill. Preserve the important corrections and verification.
Leave out the deployment work. Return a draft without writing files.
```

The prompt sets the scope; the session supplies evidence. Missing conversation context
stays missing unless you supply it.

## 2. Resolve consequential gaps

Answer questions that affect behavior, permissions, data handling, compatibility, or
acceptance. Learn resolves discoverable facts itself and continues independent drafting
while marking affected branches unresolved.

Check the proposed scope before accepting the result. Learn changes the existing owner
within your authorization instead of duplicating it. It may return no change when the
feedback is already covered or contains only one-off details. A clear rule being ignored
calls for testing that behavior, not automatically adding a stronger warning.

## 3. Review the procedure

Read the result as though you had not seen the original conversation. Check its trigger,
inputs, decisions, and completion evidence. For an existing skill, review the diff against
the current version: the requested behavior should change without unrelated rewrites,
renaming, or permission changes. Check affected references and examples too.

A useful correction belongs at the decision it changes. For example, an unnecessary
compatibility layer can motivate checking release commitments before choosing a migration
strategy. It does not justify a universal ban on compatibility work.

Remove session narration, incidental names and paths, and generic advice that does not
change an outcome. Preserve essential constraints and safeguards. Supporting files should
hold necessary conditional detail or justified deterministic tooling, not hide excess prose.
The result must not carry secrets, private payloads, or one-time approvals from the session.

## 4. Check the evidence

Review Learn's validation report. File structure and parser checks do not establish that an
agent can use the workflow successfully.

For iteration, reuse relevant cases and compare the previous and revised versions on the
same affected examples. Check the improvement and behavior that should remain unchanged.
For the migration-review example:

| Case | Expected behavior |
| --- | --- |
| A request to review a synthetic migration fixture | Inspect the supplied evidence and report findings without applying the migration. |
| A review with a consequential compatibility decision missing | Identify the missing decision rather than inventing a compatibility requirement. |
| A request to format an unrelated document | Do not activate the migration-review skill. |

When the host supports fresh-context execution and you authorize it, test with the skill,
its bundled resources, and realistic inputs without the source conversation. Use fixtures,
a disposable workspace, or dry runs. Authoring the skill does not authorize live database,
publication, or deployment effects.

If execution is unavailable, keep the cases marked unrun. Do not treat a manual walkthrough
as a behavioral test. Revise from observed failures without appending duplicate warnings.

## 5. Apply or save the result

For an existing skill, request application of the reviewed diff to its canonical source.
Keep its name and location unless you explicitly intend to change them. For a new draft,
choose a project-local destination that follows your repository's conventions. For example:

```text
Save the reviewed skill as skills/review-migrations/SKILL.md.
Do not install it globally, commit it, or publish it.
```

Otherwise, review the files or diff at the destination Learn reports. The directory and
frontmatter name should agree; the generated name need not use a `woostack-` prefix.

Load the saved skill through your assistant's supported mechanism for a separately
requested task. Saving it does not execute its workflow or authorize its future effects.
After using it, invoke Learn again with specific feedback and the current source. Each pass
starts from that version rather than recreating the skill or accumulating session notes.

See the [Learn reference](/docs/skills/woostack-learn) for the full authoring contract.
