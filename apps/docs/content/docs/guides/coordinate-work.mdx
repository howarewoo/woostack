Use Orchestrate when several tasks have settled outcomes and need coordinated delivery. Supply
task descriptions, a plan, or exact issue URLs. You need repository access, a host that can delegate
to isolated workers, and GitHub publication capability for requested PR delivery.

<CoordinateWorkFlow />

## 1. Select the work

Send this [request to your assistant](/docs/harnesses#native-skill-invocation), replacing the
angle-bracket placeholders with actual task details:

```text
/woostack-orchestrate Propose task groups and a delivery plan for the tasks below.
Include scope, exclusions, real prerequisites, and verification for each group.
After approval, implement them and deliver draft pull requests. Do not merge.

<task 1: outcome, acceptance, non-goals, and prerequisites>
<task 2: outcome, acceptance, non-goals, and prerequisites>
```

You can pass `--issue <canonical tracker URL>` for an existing tracker. Add `local only` or
`do not push` to narrow delivery. For a goal that still needs requirements work, use [Whiteboard](/docs/guides/whiteboard).

## 2. Review the plan, then authorize execution

Before edits, worktree allocation, or worker dispatch, Orchestrate proposes the grouping.
Check that each group has a bounded result, acceptance evidence, and real prerequisites.
Related inseparable issues can share a PR; one issue can require several PRs. Implementation
checkpoints do not automatically create more issues, workers, or PRs. A decision or investigation
issue is not automatically an implementation group. Check its answer, evidence, and decision authority
before allocating dependent work; a closed issue alone does not establish the decision. Unresolved
questions block only affected allocation, so independent ready work can still be proposed.

Review the proposed interfaces, safe parallel work, and landing order. Prefer independently
reviewable results while keeping necessary atomic changes together. A stack can help review even
when some combined behavior can be verified only at its tip.

By default, approval authorizes execution. Revision-only feedback updates the proposal and pauses
again; explicit approval with revisions proceeds with those changes. You can instead delegate
bounded execution-planning authority to a named coordinator. It must validate the proposal against
your delegation and return uncovered choices to you. See [approval rules](/docs/skills/woostack-orchestrate).

## 3. Follow the results and dependencies

Each group has an integrating task owner in its own worktree, normally using Execute. One worker
can take sequential assignments, but concurrent writers never share a physical workspace.
Missing worker or isolation capability blocks affected orchestration; it does not authorize
coordinator implementation in the primary checkout.

Independent ready work can continue while a dependent task waits for a verified prerequisite.
The prerequisite is its required content and contract evidence, not simply a published PR.
Material changes to the execution proposal use the same approval boundary as the original plan.

| Result | What to verify |
| --- | --- |
| Integrated increment | The combined diff is necessary, within scope, and supported by the relevant checks. |
| Dependent work released | Its prerequisite content and contract evidence are ready. This can happen before PR publication. |
| Draft PR published | Publication safeguards passed; GitHub shows the intended head, base, and PR state. A draft may disclose unfinished acceptance. |
| Group complete | All acceptance criteria, requested delivery, and required native stack membership are verified. |

## 4. Inspect delivery

Root PRs target the approved trunk branch. Dependent PRs target their predecessor's branch and
require verified native stack registration; a chained base alone is insufficient. New PRs stay
drafts, and updates preserve existing readiness unless a change was requested.

In-scope repairs before completion stay with the same task owner and worktree. Repairs after
completion need a new request. Only humans merge, enable auto-merge, or queue PRs for merge.
The [coordination reference](/docs/skills/woostack-orchestrate#coordinate) owns recovery and delivery rules.
