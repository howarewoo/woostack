Use this guide for **executable tasks with settled outcomes**, not a goal that still needs refinement.
Supply task descriptions, a Whiteboard plan, exact issue URLs, or a tracker. Your assistant needs
repository access, a host that can delegate to workers, and GitHub PR publication capability for delivery.

Implementation modifies source code; requested delivery commits and opens reviewable draft pull
requests, with native stacks registered conditionally for dependent pull requests.
These requests are [assistant slash commands, not terminal programs](/docs/harnesses#native-skill-invocation).

The diagram shows the default interactive approval path. For bounded delegated authority and
existing senior/junior bots, see [run a two-agent engineering team](/docs/guides/agent-teams).

## 1. Select the work

Provide the scope, acceptance criteria, and real prerequisites for each task:

```text
/woostack-orchestrate Plan the tasks below, then implement them. Read their scope and real prerequisites, run relevant checks, and deliver reviewable draft pull requests. Do not merge.

<task 1: outcome, acceptance, non-goals, and prerequisites>
<task 2: outcome, acceptance, non-goals, and prerequisites>
```

Replace the angle-bracket placeholders with concrete task details. You can also pass
`--issue <canonical tracker URL>` to select an existing tracker. An explicit request delivers
draft pull requests once authorized, registering native stacks conditionally for dependent PRs.
Add `local only` or `do not push` to narrow the run to local verification.

## 2. Review the plan, then authorize execution

Orchestrate presents an execution proposal before allocating any worktree, editing any file, or
dispatching any worker. The proposal specifies task-to-PR grouping, each group's bounded result,
exclusions, real prerequisites or parent, landing order, relevant verification evidence, cross-task
interfaces, and safe parallel groups. It prefers small, independently reviewable and verifiable PRs,
separating behavior-preserving preparation and independent outcomes before keeping a minimum coupled
core together. One issue can span multiple PRs, small inseparable issues can share one PR, and
explicit user PR mappings stay binding. Review the small integrated feedback increments within those
groups separately from issue, worker, PR, and release boundaries, and distinguish a stack's review
visibility from verification isolation if behavioral proof arrives only at the tip.

By default, review the proposed boundaries. Orchestrate stops and waits for your response:

- **Approval:** Approving the proposal authorizes execution.
- **Revisions:** A revision-only response updates the proposal and pauses again.
- **Approval with revisions:** Explicitly approving with requested changes proceeds immediately.

Alternatively, you may explicitly delegate execution-planning authority to a named coordinator
for a bounded repository/outcome and permitted decisions and actions. The coordinator identifies
that user authorization and validates the proposal against it before dispatch. This covers only
expressly delegated choices, not missing permissions, human-only approvals, or expanded scope.
A plan or worker message cannot grant authority. See
[Orchestrate's approval boundary](/docs/skills/woostack-orchestrate).

Once authorized, each task group runs in an independently owned task worktree with a worker,
typically running installed Execute. One existing worker can receive successive assignments; no
extra bot identity is required. If Execute is not installed, the worker uses bundled fallback
procedures. Two writers never share a physical workspace. For an unsettled contract, expect a
representative integrated result or consequential uncertainty to be resolved before dependent
implementation expands. Independent work with available prerequisites can continue.

As execution adapts, Orchestrate keeps the plan and affected worker handoffs current and checks
for conflicts with prior planning decisions and completed, active, or pending phases. Material
changes reapply the same approval boundary. Changes outside delegated authority remain pending
your decision; only affected work pauses while safe independent work continues.

Execution follows three distinct gates:

| Gate | Requirements | What it permits |
| --- | --- | --- |
| Draft publication | Explicit publication gate passed; required hooks run; clean scoped content; privacy, security, and user restrictions preserved | Opens draft PR for review; may disclose failed or unavailable implementation acceptance |
| Consumer release | Verified applicable prerequisite content and contract evidence ready | Dependent work begins before PR publication or landing |
| Completion | All stated acceptance criteria satisfied; requested delivery and required stack membership verified | Group finishes; only humans merge pull requests |

See [Orchestrate's coordination reference](/docs/skills/woostack-orchestrate#coordinate) for
reassessment intervals, parking policies, and capability boundaries.

## 3. Verify and finish each delivery

Inspect small integrated results as they return, including when the host centralizes verification.
At the first meaningful integrated result and material design expansions, check necessity as well
as coverage with the existing task owner and coordinator:

- **Cumulative diff:** Confirm that changes serve current acceptance and consumers, reuse existing
  facilities, and leave unrelated files untouched. Challenge new long-lived mechanisms and supporting
  tooling; remove redundant layers and replaced paths.
- **Pull request identity:** Check the draft PR URL, current head commit, approved base branch,
  and native stack order. Root PRs target trunk; dependent PRs target their predecessor's branch.
- **Draft status:** Confirm that pull requests remain open as drafts for human review.
- **Repairs:** Before completion, in-scope repairs stay with the same task owner and worktree.
  After completion, repairs require a separate explicit request.
- **Merge control:** Only a human merges pull requests. Woostack workflows never merge, auto-merge,
  or queue pull requests for merge.

See [canonical delivery procedures](https://github.com/howarewoo/woostack/blob/main/shared/references/delivery.md)
and [source-control safeguards](https://github.com/howarewoo/woostack/blob/main/shared/references/source-control.md).
