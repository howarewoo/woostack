---
title: Coordinate several tasks
description: Plan grouped multi-task work, delegate each group, and verify stacked draft PRs.
---

Use this guide for **approved executable tasks**, not a goal that still needs a plan. Supply task descriptions, exact issue URLs, a tracker, or an explicitly selected Project. Your assistant needs repository access, a host that can open workers, and GitHub PR publication capability for the example below. Implementation changes source; requested delivery commits and opens draft PRs. [Skill requests differ from terminal commands](/docs/harnesses#native-skill-invocation).

## 1. Select the work

Provide the scope, acceptance, and real prerequisites for each task, or select the exact source containing them. A tracker is context, not an extra task. For example:

```text
/woostack-orchestrate Plan the tasks below, then implement them. Read their scope and real prerequisites, run relevant checks, and deliver reviewable draft pull requests. Do not merge.

<task 1: outcome, acceptance, non-goals, and prerequisites>
<task 2: outcome, acceptance, non-goals, and prerequisites>
```

Replace the angle-bracket lines with real tasks. `--issue <canonical GitHub tracker URL>` can select an exact tracker instead; it does not require a native sub-issue graph or a fixed input schema. An explicit request delivers draft PRs and native stacks for the dependent PRs once approved; add `local only` or `do not push` to narrow it, and a bare issue link grants none of that delivery authority.

## 2. Review the plan, then authorize execution

The orchestration proposal comes before any workspace allocation, source edit, or worker dispatch: task-to-PR mapping, required changes, intended parents and landing order, safe parallel work, and delivery approach. Group small related tasks around an inseparable implementation/verification path, not adjacency or a shared controller, and preserve your requested mapping.

Orchestrate stops for your approval or revisions before creating task branches or dispatching workers. Approving the proposal begins execution; a revision-only response produces an updated proposal and another pause, while explicitly authorizing execution with revisions proceeds immediately. Once approved, each group has one integrating writer with exclusive access to its task workspace. Substantial groups can use bounded contributions with explicit interfaces and separate writer workspaces under the [coordination procedure](/docs/skills/woostack-orchestrate#coordinate).

A dependent starts from verified prerequisite content, which can be a sufficiently complete immutable checkpoint before its PR lands or publishes. Landing order alone must not serialize implementation; missing capabilities still block affected work. Reconcile checkpoint content with the planned parent before delivery. Missing worker or isolation capability is reported, not replaced by edits in your primary checkout.

## 3. Verify and finish each delivery

Continue pre-delivery corrections in the same allocation. Admit replacement writers and temporary contributions under the [coordination procedure](/docs/skills/woostack-orchestrate#coordinate); verify ownership, integration destination, and safe disposition.

Before broad consumer integration, complete high-risk new authority, mutation, persistence, or selected-context contracts, check their invariants and delegated callees' side effects, and obtain independent review. Resolve findings and refresh affected evidence before releasing consumers. Final review focuses on changed contracts and consumers; combined-result verification remains required.

Verify the integrated tree and cumulative diff under the canonical [testing guidance](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/tdd.md#when-evidence-still-applies). Independently reconcile child evidence, check new interactions on the canonical result, and refresh affected checks and required implementation review after changes. Limit only conflicting heavy runs while light tests proceed. Confirm PR identity, published head, base, content, and required native stack membership/order. A dependent targets its predecessor; a chained base is not membership. Reconcile interrupted workers or uncertain publication/registration through [current-state inspection](/docs/guides/troubleshooting) before retrying.

Finish verified groups and continue only undelivered work. Coordinator and workers do not fetch CI/reviews, wait for checks, or start repairs; incoming events do not reopen completed groups. Parent-ref/content reads remain valid for dependents. Later repairs need a separate explicit request and can reuse the verified workspace, branch, and PR.

Report coverage, PRs/stack order, applicable verification, limitations, blockers, and workspace disposition without fresh CI/review reads. Report unmet external acceptance without claiming uninspected CI passed. Preserve draft/readiness defaults and human-only merging.
