---
title: Coordinate several tasks
description: Plan grouped multi-task work, delegate each group, and verify stacked draft PRs.
---

Use this guide for **approved executable tasks**, not a goal that still needs a plan. Supply task descriptions, exact issue URLs, a tracker, or an explicitly selected Project. Your assistant needs repository access, a host that can open workers, and GitHub PR publication capability for the example below. Implementation changes source; requested delivery commits and opens draft PRs. [Skill requests differ from terminal commands](/docs/harnesses#native-skill-invocation).

## 1. Select the work

Provide the scope, acceptance, and real prerequisites for each task, or select the exact source containing them. A tracker is context, not an extra task. For example:

```text
/woostack-orchestrate Plan the tasks below, then implement them. Read their scope and real prerequisites, run relevant checks, and deliver reviewable draft pull requests. Do not merge.

<task 1: outcome, acceptance, non-goals, and prerequisites>
<task 2: outcome, acceptance, non-goals, and prerequisites>
```

Replace the angle-bracket lines with real tasks. `--issue <canonical GitHub tracker URL>` can select an exact tracker instead; it does not require a native sub-issue graph or a fixed input schema. An explicit request delivers draft PRs and native stacks for the dependent PRs once approved; add `local only` or `do not push` to narrow it, and a bare issue link grants none of that delivery authority.

## 2. Review the plan, then authorize execution

The orchestration proposal comes before any workspace allocation, source edit, or worker dispatch: task-to-PR mapping, required changes, intended parents and landing order, cross-task interfaces, safe parallel groups, and delivery approach. Review those task boundaries rather than specifying each task's specialist agents. Group small related tasks around an inseparable implementation/verification path, not adjacency or a shared controller, and preserve your requested mapping.

Review the distinct gates for draft publication, releasing prerequisites to consumers, group completion, and external merge/release acceptance. An authorized draft may disclose failed or unavailable implementation acceptance without separate approval. It does not establish completion or consumer readiness. Explicit publication gates, required hooks, privacy, security and data-loss protections, scoped content, and user restrictions still apply. Use the [reassessment interval proposed by Orchestrate](/docs/skills/woostack-orchestrate#coordinate), or specify a different interval.

Orchestrate stops for your approval or revisions before creating task branches or dispatching workers. Approving the proposal begins execution; a revision-only response produces an updated proposal and another pause, while explicitly authorizing execution with revisions proceeds immediately. Once approved, each group has one task owner with exclusive access to its workspace, normally running installed Execute. Without Execute, the owner uses Orchestrate's bundled procedures; no additional installation is required.

Leave implementation decomposition and specialist handoffs to the task owner. It chooses useful contributions, integrates them, and verifies the task under [Execute's task-ownership guidance](/docs/skills/woostack-execute#own-implementation-and-contributions). Substantial groups can use separate writer workspaces, but contributors do not create extra PRs. When only the coordinator can launch permitted contributors, it relays the owner's assignment and returns the result to that owner. Host permissions and capacity still apply.

Approval covers routine in-scope repairs, existing-check fixes, focused probes of selected behavior or acceptance blockers, and authorized draft updates. Pause before turning diagnosis into a separate verification-tooling outcome unless it is already approved; [Orchestrate's authority boundary](/docs/skills/woostack-orchestrate#coordinate) defines when renewed approval is required. Task owners refer cross-task contract, dependency, or deliverable changes to Orchestrate. Keep one publication owner: by default workers return changes, observed evidence, and unmet criteria, and Orchestrate handles commits, PRs, and stacks; any delegated Git/PR operation must be explicit within the approved limits.

A dependent starts from verified prerequisite content and consumer-release evidence, which can be a sufficiently complete immutable checkpoint before its PR lands or publishes. Landing order alone must not serialize implementation; missing capabilities still block affected work. Reconcile checkpoint content with the planned parent before delivery. Missing worker or isolation capability is reported, not replaced by edits in your primary checkout.

## 3. Verify and finish each delivery

Return pre-delivery task corrections to the same owner and allocation. Admit replacement writers and temporary contributions under the [coordination procedure](/docs/skills/woostack-orchestrate#coordinate); verify ownership, integration destination, and safe disposition.

For ordinary reversible work, use existing relevant checks and the smallest practical observation. Extra integration or runtime checks, baseline/candidate comparisons, and independent review need an explicit requirement or a concrete material risk. Follow [Orchestrate's verification policy](/docs/skills/woostack-orchestrate#coordinate) to name that risk and select stronger evidence before consequential use or release. Missing required evidence blocks affected use or release while safe independent work continues.

Distinguish interaction-driver failures from application failures before source repairs. Keep unresolved privacy evidence on HOLD; preserve historical findings without reconstructing lost private evidence or clearing them through replacement runs. Keep exploratory corrections in the canonical allocation and reconcile dependents when required contract evidence is ready.

At each agreed checkpoint, follow [Orchestrate's reassessment guidance](/docs/skills/woostack-orchestrate#coordinate) to compare time spent with progress toward product acceptance and required safety evidence. Tooling artifacts or a change in diagnostic method alone do not justify further expansion. Change approach within authority, continue safe independent work, or report the blocker and decision needed. Keep the agreed cadence live during worker waits and leave healthy pending work running. When no authorized productive work remains, report blocked rather than extending diagnostics.

Inspect the integrated tree and cumulative diff, reuse applicable child evidence, and refresh selected checks and any required review after relevant changes. Extra verification follows the requirements or named risks above. Account for descendants in aggregate resource use; limit only conflicting heavy runs while light checks proceed. Confirm PR identity, published head, base, content, and required native stack membership/order under the [delivery procedures](https://github.com/howarewoo/woostack/blob/main/shared/references/delivery.md). A dependent targets its predecessor; a chained base is not membership. Reconcile interrupted workers or uncertain publication/registration through [current-state inspection](/docs/guides/troubleshooting) before retrying.

Publish eligible groups incrementally as their explicit publication gates pass, disclosing failed or unavailable acceptance by name. Preserve intended parents and required native stacks. Completion still requires selected acceptance; draft visibility alone proves neither consumer readiness nor group completion.

Finish groups once selected completion requirements and delivery are verified. Incomplete groups continue only authorized productive work; report blocked when none remains. Coordinator and workers do not fetch CI/reviews, wait for checks, or start post-completion repairs; incoming events do not reopen completed groups. Parent-ref/content reads remain valid for dependents. Later repairs need a separate explicit request and can reuse the verified workspace, branch, and PR.

Report coverage, PRs/stack order, applicable verification, limitations, blockers, and workspace disposition without fresh CI/review reads. Report unmet external acceptance without claiming uninspected CI passed. Preserve draft/readiness defaults and human-only merging.
