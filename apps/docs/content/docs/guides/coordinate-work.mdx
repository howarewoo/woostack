---
title: Coordinate several tasks
description: Plan grouped multi-task work, delegate each group, and verify stacked draft PRs.
---

Use this guide for **approved executable tasks**, not a goal that still needs a plan. Supply task descriptions, exact issue URLs, a tracker, or an explicitly selected Project. Your assistant needs repository access, a host that can open workers, and GitHub PR publication capability for the example below. Implementation changes source; requested delivery commits and opens draft PRs. [Skill requests differ from terminal commands](/docs/harnesses#native-skill-invocation).

## 1. Select the work

Provide the scope, acceptance, and real prerequisites for each task, or select the exact source containing them. A tracker is context, not an extra task. For example:

```text
/woostack-orchestrate Plan the tasks below, then implement them. Read their scope and real prerequisites, run relevant checks, and deliver reviewable draft pull requests. Do not merge.

<task 1: outcome, acceptance, non-goals, and prerequisites>
<task 2: outcome, acceptance, non-goals, and prerequisites>
```

Replace the angle-bracket lines with real tasks. `--issue <canonical GitHub tracker URL>` can select an exact tracker instead; it does not require a native sub-issue graph or a fixed input schema. An explicit request delivers draft PRs and native stacks for the dependent PRs once approved; add `local only` or `do not push` to narrow it, and a bare issue link grants none of that delivery authority.

## 2. Review the plan, then authorize execution

The orchestration proposal comes before any workspace allocation, source edit, or worker dispatch: task-to-PR mapping, required changes, intended parents and landing order, cross-task interfaces, safe parallel groups, and delivery approach. Review those task boundaries rather than specifying each task's specialist agents. Group small related tasks around an inseparable implementation/verification path, not adjacency or a shared controller, and preserve your requested mapping.

Review the distinct gates for draft publication, releasing prerequisites to consumers, group completion, and external merge/release acceptance. Use the [reassessment interval proposed by Orchestrate](/docs/skills/woostack-orchestrate#coordinate), or specify a different interval. Failed or unrun required implementation acceptance blocks delivery by default; an unfinished draft needs explicit separate approval and still cannot release consumers of failing behavior. Keep publication checks, privacy protections, and required review binding.

Orchestrate stops for your approval or revisions before creating task branches or dispatching workers. Approving the proposal begins execution; a revision-only response produces an updated proposal and another pause, while explicitly authorizing execution with revisions proceeds immediately. Once approved, each group has one task owner with exclusive access to its workspace, normally running installed Execute. Without Execute, the owner uses Orchestrate's bundled procedures; no additional installation is required.

Leave implementation decomposition and specialist handoffs to the task owner. It chooses useful contributions, integrates them, and verifies the task under [Execute's task-ownership guidance](/docs/skills/woostack-execute#own-implementation-and-contributions). Substantial groups can use separate writer workspaces, but contributors do not create extra PRs. When only the coordinator can launch permitted contributors, it relays the owner's assignment and returns the result to that owner. Host permissions and capacity still apply.

Approval covers routine in-scope diagnosis, repairs, checks, and authorized draft updates. Renew approval only for material departures or new permissions. Task owners refer cross-task contract, dependency, or deliverable changes to Orchestrate. Keep one publication owner: by default workers return verified changes and evidence, and Orchestrate handles commits, PRs, and stacks; any delegated Git/PR operation must be explicit within the approved limits.

A dependent starts from verified prerequisite content and consumer-release evidence, which can be a sufficiently complete immutable checkpoint before its PR lands or publishes. Landing order alone must not serialize implementation; missing capabilities still block affected work. Reconcile checkpoint content with the planned parent before delivery. Missing worker or isolation capability is reported, not replaced by edits in your primary checkout.

## 3. Verify and finish each delivery

Return pre-delivery task corrections to the same owner and allocation. Admit replacement writers and temporary contributions under the [coordination procedure](/docs/skills/woostack-orchestrate#coordinate); verify ownership, integration destination, and safe disposition.

Before broad consumer integration of a high-risk new model, authority, mutation, persistence, or selected-context contract, exercise the smallest meaningful vertical slice in the actual required runtime. Verify that it runs the changed source and inspect real behavior and delegated effects, alongside focused invariant checks and required independent review. Reuse applicable authorized runtimes, caches, and safe harnesses. Missing runtime evidence blocks affected consumers while independent work continues.

Distinguish interaction-driver failures from application failures before source repairs. Keep unresolved privacy evidence on HOLD; preserve historical findings without reconstructing lost private evidence or clearing them through replacement runs. Keep exploratory corrections in the canonical allocation and reconcile dependents at verified checkpoints rather than after every experiment. Final review focuses on changed contracts and consumers; combined-result verification remains required.

At each agreed checkpoint, compare elapsed preparation, builds, replay, and coordination with new behavioral evidence, using available timings and counts. When repeated attempts add overhead without new evidence, change approach within authority, continue independent work, or report the blocker and material decision needed. Keep the cadence live during worker waits through available host notifications and bounded waits; neither progress messages nor notifications reset it. Handle delivered notifications without deliberately waiting for the checkpoint. After reassessment, leave healthy work running unchanged; do not fail, cancel, message, or recheck a pending worker merely because the checkpoint arrived, or count pending work as passed.

Verify the integrated tree and cumulative diff under the canonical [testing guidance](https://github.com/howarewoo/woostack/blob/main/shared/references/tdd.md#when-evidence-still-applies). Independently reconcile child evidence, check new interactions on the canonical result, and refresh affected checks and required implementation review after changes. Account for descendants in aggregate resource use; limit only conflicting heavy runs while light tests proceed. Confirm PR identity, published head, base, content, and required native stack membership/order; Orchestrate remains accountable for delivery under the [delivery procedures](https://github.com/howarewoo/woostack/blob/main/shared/references/delivery.md), including read-back of explicitly delegated publication. A dependent targets its predecessor; a chained base is not membership. Reconcile interrupted workers or uncertain publication/registration through [current-state inspection](/docs/guides/troubleshooting) before retrying.

Publish eligible groups incrementally as their approved publication gates pass. Preserve intended parents and required native stacks. Draft visibility alone proves neither consumer readiness nor group completion; an approved unfinished draft continues only its authorized in-scope work.

Finish groups once completion requirements and delivery are verified, and continue only unfinished work. Coordinator and workers do not fetch CI/reviews, wait for checks, or start repairs; incoming events do not reopen completed groups. Parent-ref/content reads remain valid for dependents. Later repairs need a separate explicit request and can reuse the verified workspace, branch, and PR.

Report coverage, PRs/stack order, applicable verification, limitations, blockers, and workspace disposition without fresh CI/review reads. Report unmet external acceptance without claiming uninspected CI passed. Preserve draft/readiness defaults and human-only merging.
