---
title: Whiteboard a goal into a plan
description: Explore requirements, review the design visually, and hand off a plan when implementation is authorized.
---

Use [Whiteboard](/docs/skills/woostack-whiteboard) when you want to explore and
refine a goal before building. For implementation planning, you leave with a written plan and a
visual model that explain what to build, why, and what remains undecided. Requirements-only
exploration can stop earlier. An already-understood task does not need a Whiteboard session.
The same skill works for you or a delegated planning agent.

## Start the conversation

With Whiteboard installed in your coding assistant, enter a goal or supply an existing plan:

```text
/woostack-whiteboard Design a local dashboard for inspecting agent runs.
The first version observes runs but cannot cancel or retry them.
```

These are assistant requests, not terminal commands. See your host's
[invocation syntax](/docs/harnesses#native-skill-invocation). For an existing project, identify the
repository; for greenfield work, state that no code exists yet. A checkout is not required.

To explore requirements without choosing an implementation, narrow the request:

```text
/woostack-whiteboard Explore whether we should add team workspaces.
Clarify the requirements and compare approaches.
Do not choose an architecture or create implementation tasks yet.
```

Expect a focused specification or answer with alternatives, trade-offs, evidence, and open decisions.
A solution, delivery plan, and diagram are not required to finish this exploration. Choose whether
to develop an implementation plan later; completing exploration does not make implementation ready.

## Refine the requirements and picture

Answer material questions and correct the assistant's model as it develops. When the context
already settles the necessary decisions, Whiteboard can return a plan without asking questions.
State both the behavior you need and the conditions it must work under. Keep hard requirements
separate from preferences, and ask for the consequences of a choice before accepting it.

For example, ask:

```text
Walk me through what happens when a run fails halfway through.
Show which component records the failure and what the user sees.
```

The assistant updates the text and diagram together when you correct a boundary or decision.
It uses a diagram your host can render, or a readable text diagram without installing a renderer.
Ask about a relationship that seems wrong rather than waiting for a finished specification.

## Review the plan

Check that you can explain the core behavior, constraints, decisions, trade-offs, and small
observable feedback increments. Look for candidate behavior-preserving preparation, the minimum
coupled outcome, and consequential uncertainties to resolve before expanding dependent work.
Check platform dependencies against the intended account, entitlement, repository visibility, and
runtime where relevant. General platform documentation does not prove your setup or access. Keep
missing setup, access, and owner decisions distinct, with an owner and return condition for each
unresolved prerequisite. Whiteboard can propose a small feasibility test without running it. Park
only dependent work while independent work can proceed, and distinguish planned setup from configured
resources and end-to-end acceptance. Checkpoints can stay inside one plan
or delivery boundary, including an atomic cutover, while branch and PR allocation stays with the
implementing workflow. A useful draft may still contain a blocker; it identifies the decision or
investigation needed.
See [Whiteboard's return contract](/docs/skills/woostack-whiteboard) for details.

For an existing specification, request a review without rewriting it:

```text
/woostack-whiteboard Review this plan against the selected repository.
Return discrepancies, evidence, and recommended corrections only. Do not rewrite or publish it.
```

## Keep it or request implementation

The plan stays in conversation by default. Choose the action you need:

### Save the plan to a file

To keep the plan for later without implementing it, name the destination file explicitly:

```text
Save the current plan, including its diagram and unresolved questions,
to docs/plans/run-dashboard.md. Do not commit it or implement anything.
```

Saving a plan writes the file locally and writes nothing else. It files no GitHub issues and
starts no implementation.

### Publish the plan as issues

Ask Whiteboard to file the plan in an exact repository. Follow
[plan work and file issues](/docs/guides/plan-work) for publication and read-back. Publication is
optional; another agent can consume the Markdown plan directly.

### Request implementation

For one bounded outcome, request [Execute](/docs/guides/ship-change). To coordinate several outcomes,
explicitly invoke Orchestrate with the plan:

```text
/woostack-orchestrate Implement the Whiteboard plan above.
```

Orchestrate reads the plan and repository evidence and proposes task grouping and delegation.
By default it pauses for your approval before dispatching workers. A named coordinator can instead
validate covered decisions against authority you explicitly delegated, under
[Orchestrate's approval rules](/docs/skills/woostack-orchestrate). See
[coordinate several tasks](/docs/guides/coordinate-work) or
[set up an R&D team](/docs/agent-teams/setup).
