---
title: Whiteboard a goal into a plan
description: Collaborate on requirements, review the design visually, and hand off a plan only when you request implementation.
---

Use experimental [Whiteboard](/docs/skills/woostack-whiteboard) when you want to explore and
refine a goal before building. You leave with a written plan and a visual model that explain
what to build, why, and what remains undecided. Ideate, Harden, and Plan remain available;
an already-understood task does not need a Whiteboard session.

## Start the conversation

With Whiteboard installed in your coding assistant, enter a goal or supply an existing plan:

```text
/woostack-whiteboard Design a local dashboard for inspecting agent runs.
The first version observes runs but cannot cancel or retry them.
```

These are assistant requests, not terminal commands. See your host's
[invocation syntax](/docs/harnesses#native-skill-invocation). For an existing project, identify the
repository; for greenfield work, state that no code exists yet. A checkout is not required.

## Refine the requirements and picture

Answer material questions and correct the assistant's model as it develops. State both the
behavior you need and the conditions it must work under. Keep hard requirements separate from
preferences, and ask for the consequences of a choice before accepting it.

For example, ask:

```text
Walk me through what happens when a run fails halfway through.
Show which component records the failure and what the user sees.
```

The assistant updates the text and diagram together when you correct a boundary or decision.
It uses a diagram your host can render, or a readable text diagram without installing a renderer.
Ask about a relationship that seems wrong rather than waiting for a finished specification.

## Review the plan

Check that you can explain the core behavior, constraints, decisions, trade-offs, and delivery
steps. Verify dependencies and keep unanswered questions visible rather than converting them into
assumptions. A useful draft may still contain a blocker; it identifies the decision or investigation
needed rather than claiming the design is ready. See
[Whiteboard's return contract](/docs/skills/woostack-whiteboard) for details.

## Keep it or request implementation

The plan stays in conversation by default. You have two distinct exit choices:

### Option A: Save the plan to a file

To keep the plan for later without implementing it, name the destination file explicitly:

```text
Save the current plan, including its diagram and unresolved questions,
to docs/plans/run-dashboard.md. Do not commit it or implement anything.
```

Saving a plan writes the file locally and writes nothing else. It files no GitHub issues and
starts no implementation.

### Option B: Request implementation

To coordinate implementation immediately, explicitly invoke Orchestrate with the plan:

```text
/woostack-orchestrate Implement the Whiteboard plan above.
```

Orchestrate reads the plan and repository evidence, proposes task grouping and delegation,
and pauses for your approval before dispatching workers. See
[coordinate several tasks](/docs/guides/coordinate-work) for the execution procedure.

Whiteboard does not publish issues during the trial. To export a plan as GitHub issues, use the
separate [plan work and file issues](/docs/guides/plan-work) guide.
