---
title: Plan a change
description: Turn a goal into requirements and a plan, or review an existing specification without implementing it.
---

Use Whiteboard when the goal or important choices still need work. Implementation plans default to
a temporary Markdown file, with a short summary and its absolute path in chat. Exploration and
review-only answers stay conversational. To settle an interactive experience before its implementation plan,
[prototype the UI change](/docs/guides/prototype) and bring the approved reference and handoff.
Requirements exploration can still come first. A task you already understand can go straight to
[Execute](/docs/guides/ship-change).

You need [Whiteboard installed](/docs/getting-started) in your assistant. For existing code, give
it access to the repository; a new product needs no checkout. Examples here are
[assistant requests](/docs/harnesses#native-skill-invocation), not terminal commands.

## 1. State the goal and limits

```text
/woostack-whiteboard Plan a Verification section for our README. The readers are
contributors who need to know which checks to run before submitting a change.
Use the repository's existing commands and reuse useful content. Return a plan
and a visual where it helps; do not edit repository files or publish issues.
```

Describe who has the problem, how they handle it now, what should improve, and the hard constraints
and non-goals. Whiteboard treats a proposed feature as a starting point and checks whether removal,
reuse, or a smaller change would serve the goal. For documentation, name the reader and what they
should be able to do. Whiteboard inspects available evidence and resolves consequential choices
during planning, not execution.
Consequential product choices affecting behavior, acceptance, permissions, data handling,
compatibility, cost, or recovery need an answer from you or an explicitly authorized delegate
before dependent implementation is ready. Reversibility does not authorize a default. Routine
implementation and design details within agreed behavior do not need an interview. This includes
minor wording or spacing changes that preserve meaning and constraints. No questions are required
when the context is complete.

For requirements exploration alone, say `Compare approaches without choosing an architecture or
creating implementation tasks`. For a review, supply the plan and ask for discrepancies and
recommended corrections only. Neither request requires a new implementation plan.

## 2. Refine the behavior

Open the returned path in your Markdown reader. The file contains the complete plan, including
its visual, decisions, acceptance, and unresolved questions. Whiteboard updates that same file
as decisions change and reads back each saved revision; chat gives you the status rather than
repeating the plan. Ask for the full plan in chat if you prefer.

Whiteboard starts with a working hypothesis and recommended direction based on available evidence.
It explains alternatives and trade-offs, asks focused questions, and updates the plan from your
answers until it is ready for handoff or you direct otherwise. A blocker prompts the next question
or a request for missing evidence. Ask it to walk through a concrete case if the recommendation
is unclear. For the README example:

```text
Walk through how a contributor chooses checks for a wording-only change.
What should the README say if a documented command is missing?
```

The assistant checks material transitions: the trigger, who may act, the result, and side effects.
It probes partial success, retry, cancellation, or interruption where those could change the outcome.
Correct the scope or assumptions as needed. This is a concrete walkthrough, not an exhaustive
checklist. During implementation planning, the assistant keeps its visual model and text consistent.
Your host can use a readable text diagram when it cannot render the preferred format.

A technically feasible feature may still fail to help its users. Whiteboard distinguishes these
product assumptions from feasibility and proposes learning or success evidence when it matters
to the direction. It does not invent agreed metrics or require analytics or experiments for every
change. Proposed learning remains a plan, not permission to run a test.

If your host supports delegation, you can authorize read-only scouts for independent questions:

```text
Use read-only scouts to inspect the existing check commands and contributor guidance.
Return source evidence, uncertainty, and recommendations. Do not edit, experiment, or publish.
```

Whiteboard chooses useful capacity, reconciles findings and conflicts, and brings material questions
to you. If optional scouting is unavailable, it inspects inline. Scouts cannot authorize behavior;
they are not workers running proposed feasibility tests.

## 3. Check the plan

Ask Whiteboard to challenge consequential assumptions with concrete counterexamples. For the README
example, a recommended check might exist but omit the files being changed. Expect material findings
with evidence or a labeled assumption, consequences, and the smallest correction or question.
A review may find no material issues. When another perspective could change a consequential
decision, you can authorize a separate read-only reviewer of the saved plan. Whiteboard gives it
the complete artifact and primary sources, without planning history, previous reviewer verdicts,
or leading approval framing. It leaves that revision unchanged until review finishes. If the
reviewer cannot access the file, it receives the exact full plan inline. Limited context separation
or a failed review must be reported, not treated as independent proof. Check each correction's effects on
requirements, dependencies, acceptance, and the visual. Reviewer agreement alone is not verification.

Before handing it off, check that:

- Functional and nonfunctional requirements, constraints, and non-goals are distinct from
  preferences and proposed defaults.
- Consequential choices have reasons. Material questions are answered or explicitly deferred by you,
  including any necessary later investigation. If you stop early, the result is a draft.
- Open questions name needed evidence, the decision owner, resolution condition, and affected
  dependents. Dependent implementation stays unready; independent ready portions remain usable.
- In-scope areas that cannot yet be framed as questions stay deferred, with the upstream answer
  needed to clarify them. They are separate from non-goals and speculative implementation tasks.
- Steps produce coherent observable results with acceptance checks and real prerequisites. Their
  material journeys, state transitions, failures, and recovery agree with the visual. Completion
  criteria are distinct from any draft-publication and consumer-release gates.
- Platform-dependent claims match the intended account, access, and runtime. Proposed setup is
  not described as already configured.

A feasibility test may be proposed as an implementation step; Whiteboard does not run it.
Implementation checkpoints need not become separate issues, workers, or PRs. For a plan spanning
sessions, check that its summary preserves the goal, decisions and reasons, next questions, and
blockers without requiring the original conversation. A fresh Orchestrate session should be able
to propose execution from the plan alone, without reopening settled choices, dropping acceptance,
or allocating blocked dependents. Whiteboard does not preassign workers, branches, or PRs;
Orchestrate owns execution grouping, allocation, and delivery.

## 4. Choose what happens next

When consequential questions are answered, material walkthroughs are complete, and the plan is
self-contained, Whiteboard says **“This plan is ready for handoff.”** It names the appropriate next
workflow without starting it. Routine implementation details can remain for execution. If decisions
or prerequisites still block part of the plan, it identifies the affected work and keeps asking
focused questions. You can stop, narrow the scope, defer a decision, or request the current draft
at any point; unresolved work remains marked as unready. Handoff readiness does not prove
feasibility, setup, or end-to-end acceptance.

| Next action | What to request |
| --- | --- |
| Keep the result in chat | Ask for the full plan inline instead of the file default. |
| Choose a durable document | Name the destination, for example: `Save this plan to docs/plans/readme-verification.md. Do not commit or implement it.` |
| File GitHub issues | Follow [Publish a plan as issues](/docs/guides/plan-work). |
| Implement one bounded outcome | Follow [Deliver one change](/docs/guides/ship-change). |
| Coordinate several executable outcomes | Follow [Coordinate several tasks](/docs/guides/coordinate-work). |

Temporary files can be cleared; they are not archival storage. Choose a durable destination when
you need one. Whiteboard reads existing content and preserves unrelated work before updating an
explicit destination. Keep the path in continuation context where your host supports it, and have
a resumed session read the file before relying on the plan. A lost path or file prevents guaranteed
recovery. If file creation, reading, or sharing fails, expect a disclosed limitation and a supported
alternative; if no usable path exists, expect the complete plan inline.

Saving or publishing a plan does not authorize implementation. See the
[Whiteboard reference](/docs/skills/woostack-whiteboard) for exact planning and publication rules.
