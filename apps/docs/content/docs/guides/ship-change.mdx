---
title: Deliver one change
description: Implement and verify a bounded task, then inspect its requested draft pull request.
---

Use this guide when the outcome and non-goals fit one reviewable change. Have the plan or exact issue URL, repository access, and a GitHub capability for a draft PR. Your assistant will edit source and, **because this guide requests PR delivery**, commit and publish the result. A natural-language request for local implementation alone does not authorize a push or PR. These are [logical skill requests, not terminal commands](/docs/harnesses#native-skill-invocation).

## 1. Request the task and delivery

Supply the bounded plan in the same session, or include it in a new session; chat history is not shared automatically. For example:

```text
/woostack-execute Implement the reviewed README documentation plan. Use the repository's actual verification commands, run relevant checks, and submit a draft pull request. Do not merge.
```

With a selected executable issue, `/woostack-execute <canonical GitHub issue URL>` is an alternative. An explicit Execute request delivers a draft PR unless you limit it to local work. Planning is optional; so is a separate Debug session. For a defect, establish the cause from evidence before correcting it. Resolve material scope or safety questions rather than guessing.

Before the first edit, Execute checks the physical repository, branch, HEAD/base where present,
index, and relevant staged/unstaged changes with read-only Git queries. A task-file read or passing
test does not replace that admission, even for a one-line change. Unknown workspace ownership or
an unsafe branch/base blocks editing; understood unrelated work stays preserved.

## 2. Inspect the implementation

Confirm the complete diff matches the outcome and leaves unrelated work alone. For ordinary reversible work, use existing relevant checks and the smallest practical observation. Follow [Execute's verification policy](/docs/skills/woostack-execute#implement-and-verify) to select extra verification for explicit requirements or a concrete material risk, including stronger evidence before consequential use or release.

Read the observed results and name any failed or unavailable acceptance criterion. Completion requires selected acceptance; draft publication alone does not satisfy it. Keep unresolved privacy findings on HOLD. If no authorized productive work remains, report blocked rather than extending diagnostics. Focused product questions and existing-check repairs remain routine; a separate verification-tooling outcome needs renewed approval before implementation unless already approved.

## 3. Verify delivery

An authorized draft may disclose failed or unavailable implementation acceptance without separate approval. Explicit publication gates, required hooks, privacy, security and data-loss protections, clean scoped content, and user restrictions remain binding. Draft visibility proves neither completion nor readiness for affected consumers. Follow [Execute's publication policy](/docs/skills/woostack-execute#requested-commit-and-publication) without silently reinterpreting task-specific gates.

Check the draft PR's URL, current head commit, base, body, and open state against Git and GitHub. If
you selected an issue, check its exact closing association only when the PR fully addresses it. A new
PR is a draft for human review; a request to mark it ready is executed, and merging stays with a
human. Before completion, in-scope repairs reuse the same task branch and PR under existing authority;
later repairs need a separate explicit request. For a missing check or uncertain write, [start with the matching
symptom](/docs/guides/troubleshooting). Execute performs this delivery itself under the
[delivery procedures](https://github.com/howarewoo/woostack/blob/main/shared/references/delivery.md);
an explicit commit-only, rebase, restack, or readiness request is
[Commit's](/docs/skills/woostack-commit) own operation.
