---
title: Deliver one change
description: Request a bounded implementation, check its results, and inspect the draft pull request.
---

Use Execute for one bounded outcome, such as a README update, feature, bug fix, or test task.
You need repository access and the relevant skill [installed in your assistant](/docs/getting-started).
Draft PR delivery also needs an authorized GitHub publication capability.
If the UI experience is still unsettled, [prototype the change first](/docs/guides/prototype).
For an approved prototype, supply the accessible snapshot and handoff as the visual and interaction
acceptance reference.

## 1. Request the change

Send this [request to your assistant](/docs/harnesses#native-skill-invocation), replacing the
README task with your own outcome if needed:

```text
/woostack-execute Add or update the README's Verification section using the
repository's actual check commands. Keep it focused on contributors choosing
checks for a change. Verify the claims and links, run relevant checks, and
submit a draft pull request. Do not merge.
```

An explicit `/woostack-execute` request includes draft PR delivery unless you narrow it.
Add `Keep changes local; do not commit or push` for local work only. An ordinary natural-language
implementation request authorizes local edits and checks, not automatic publication.

A plan or exact issue URL can supply context, but neither is required. For a bug fix, Execute
establishes the cause before editing; a separate Debug session is optional. Before any edit,
it checks the branch, base, index, and existing changes. Unknown ownership or an unsafe workspace
blocks editing.

For documentation, state the audience and intended result. Guided root-document authoring belongs
to [Init](/docs/skills/woostack-init); a bounded edit with settled decisions, like the README
example, can stay in Execute.

Execute resolves repository facts and makes routine implementation choices within its authority. If a
consequential requirement is missing, it pauses affected work without guessing a default or fallback.
It continues safe independent work, required review, healthy checks, and eligible requested delivery.
The final handoff includes nonblocking questions, affected acceptance, a recommendation, and a resume
condition. A host-blocking question is reserved for an answer that blocks all remaining useful
authorized work; an accurate blocked handoff is also valid.
Permissions, privacy, publication, and release gates still apply. Use
[Whiteboard](/docs/guides/whiteboard) to settle material behavior before implementation when needed.

## 2. Review the implementation evidence

[Select verification requirements](/docs/guides/verification) before implementation. Then inspect
the combined result:

- The diff serves the requested outcome and preserves unrelated work.
- Relevant checks actually ran, and the report explains failures or missing evidence.
- Documentation claims, examples, and links match their sources. Commands only inspected are
  distinguished from commands executed.
- Acceptance criteria are satisfied before the assistant claims completion. A draft PR can
  disclose unfinished acceptance when publication safeguards permit it.

For meaningful visible changes with PR delivery, provide a way to capture the running result and
upload it as GitHub-hosted media. The assistant uses available authorized tools; it does not
install an uploader or acquire credentials as a fallback. Missing capture or upload stays disclosed.
See [visual evidence requirements](https://github.com/howarewoo/woostack/blob/main/shared/references/delivery.md#pr-visual-evidence).

If a check fails or cannot run, use [troubleshooting](/docs/guides/troubleshooting#a-test-or-verification-step-fails).
Unresolved privacy findings remain on HOLD under the
[Execute verification policy](/docs/skills/woostack-execute#implement-and-verify).

### Compare an approved prototype

Preserve the approved presentation and interactions while retaining required production behavior.
Reuse existing components where they fit that experience; adapt or replace presentation that conflicts.

Compare an early representative rendered state at target sizes, including desktop and phone where
supported. Resolve material mismatches before extending the approach. At completion, reconcile every
in-scope surface and material state on the integrated candidate using matching viewport, theme, and
equivalent data/state. Record the production location,
observed comparison, and evidence in the existing acceptance checklist or verification summary.
Exercise transitions and use short recordings where motion matters. Refresh affected comparisons
after fixes, reusing evidence that still applies.

For example, a rest timer can preserve adjustment, expiry, cancellation, and persistence while adopting
the approved floating panel. Fidelity also covers its anchoring, countdown typography, controls, and
expanded, collapsed, and Ready states. Passing timing tests alone cannot establish those results;
implementation-only screenshots also need comparison with the reference.

Record each result as matched, an authorized deviation with its decision basis, or unmet. An explanation
for a different design is not approval to change it. Missing reference access, fixtures, or rendered
evidence leaves affected acceptance open. An eligible draft PR can disclose that limit; prototype
integration remains incomplete. Use existing checks for focused geometry or state regressions where useful.

## 3. Inspect the draft PR

Check the returned URL on GitHub. Confirm the intended head commit, approved base, description,
and open draft state. New PRs are drafts; an update preserves existing readiness unless requested
otherwise. If an issue was selected, closing keywords should appear only when the PR fully resolves it.
Screenshots or recordings should render and match the current visible result.

In-scope repairs before completion stay on the same task branch and PR. Later repairs need a new
request. Standalone rebases, restacks, and readiness changes belong to [Deliver](/docs/skills/woostack-deliver).
Only humans merge, enable auto-merge, or queue PRs for merge.
