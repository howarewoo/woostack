---
title: Set verification requirements
description: Choose checks for a task, reuse applicable evidence, and report what remains unverified.
---

Start with the task, repository rules, and active workflow. Record the checks in the ordinary task
scope or existing plan; no separate verification document or approval stage is needed.
[Verification](/docs/concepts/verification) explains why different claims need different evidence.

## 1. Identify what requires a check

For each check, name the requirement it satisfies and the outcome it protects: implementation
acceptance, publication, dependent work, or release.

| Status | What to do |
| --- | --- |
| Required | Obtain the evidence before claiming the affected outcome is verified. |
| Conditional | Name the trigger. The check becomes required when that condition applies. |
| Optional or out of scope | Disclose relevant coverage limits without treating them as failed acceptance. |

Use existing relevant checks for ordinary reversible work. Add a check when an applicable requirement
or concrete risk calls for it. Describe the possible failure, its consequence, and the smallest
observation that addresses it. A broad label such as "persistence" alone does not identify a risk.

For consequential authorization, privacy, destructive effects, migration, recovery, or financial
operations, follow [Execute's stronger evidence requirements](/docs/skills/woostack-execute#implement-and-verify).
Unresolved privacy evidence stays on HOLD.

## 2. Explain the selected checks before work

Say what each planned check covers, why it applies, and what missing proof would block. For a README
wording change, that might be:

```text
I will compare each documented command with the repository's scripts and inspect
changed links and anchors. I will not execute deployment commands to verify prose.
A missing command or broken link will leave that instruction unverified.
```

Use the target repository's policy. In Woostack itself, the
[root validation policy](https://github.com/howarewoo/woostack/blob/main/AGENTS.md#validation)
distinguishes prose inspection, parser and asset tests, and rendering or build checks. A wording
edit alone does not require a production build; a changed MDX component or route may.

Explain newly discovered risks in the same task scope. Accessibility checks follow applicable
project and task requirements. For example, 200% zoom is not a default Woostack blocker, but becomes
required when an explicit accessibility requirement calls for it. Unchecked coverage is never a pass,
and selected checks do not establish full WCAG conformance.

## 3. Reuse evidence where it still applies

Compare the earlier result with the relevant source, tests, fixtures, dependencies, configuration,
and environment. Reuse it when those inputs remain equivalent; a new commit identifier or handoff
alone is not a reason to rerun it.

Rerun affected checks when inputs change or equivalence is uncertain. New combinations need evidence
for their interactions even if each component passed separately. See
[evidence reuse](https://github.com/howarewoo/woostack/blob/main/shared/references/tdd.md#when-evidence-still-applies).

## 4. Report results at the affected boundary

State what ran, what it showed, and what remains unverified. Failed, timed-out, cancelled,
unavailable, or unrun required checks leave the affected outcome unverified. This includes
pre-existing failures. Name the unmet criterion and the actor or changed condition needed to resume.
For stalled checks, follow [bounded diagnosis](https://github.com/howarewoo/woostack/blob/main/shared/references/tdd.md#slow-checks-bounded-diagnosis-no-waiver)
instead of launching duplicate checks or retrying without new evidence.

Keep implementation acceptance, draft publication, dependent-work readiness, and merge or release
readiness separate in the report. An authorized draft may disclose missing implementation evidence
only when its publication conditions permit it. Required hooks, privacy, security, data-loss
protections, and user limits still apply. Draft visibility alone permits neither dependent work
nor a completion claim.

Use the [Execute publication rules](/docs/skills/woostack-execute#requested-commit-and-publication)
or [Orchestrate coordination rules](/docs/skills/woostack-orchestrate#coordinate) for the active task.
Only humans merge, enable auto-merge, or queue PRs for merge.
