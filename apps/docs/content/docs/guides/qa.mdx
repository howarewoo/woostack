---
title: QA a running app
description: Review user journeys, report reproducible defects and coverage limits, and retest fixes with WooStack QA.
---

Use [QA](/docs/skills/woostack-qa) to check a running app through its interface and receive a
report tied to the environment and behavior actually tested. This guide uses a draft editor;
replace it with the journey you want reviewed.

## Before you begin

Provide an authorized running URL, a disposable test account or isolated data, and an available
browser capability. QA uses the host's existing browser tools or installed browser CLI. It does
not install tooling, start or rebuild the app, edit product code or tests, or publish to GitHub.
Arrange any required setup through a separately authorized task before requesting QA.

Load [the QA skill](/docs/getting-started) through your assistant's supported mechanism. The examples
below are [assistant requests](/docs/harnesses#native-skill-invocation), not terminal commands.
Replace the example URL and revision placeholders with the intended candidate.

## 1. Specify the journey and expected behavior

```text
/woostack-qa https://staging.example.test
Review the draft editor on commit <commit-sha>, build <build-id>.
Use the authorized disposable editor account and synthetic drafts.
Check create, edit, save, cancel, reload, and recovery after an interrupted save.
Expected: saved changes survive reload; cancel preserves the last saved values;
an unsuccessful save keeps the user's edits available for retry.
```

Supply the relevant requirements or acceptance criteria. If you want a PR-specific review, include
its exact URL. Source inspection helps identify risks, but expected behavior needs a requirement
or an explicit rationale beyond what the implementation currently does.

Name any existing holds, account restrictions, or actions with consequences beyond the test data.
Deletes, payments, and external communications need explicit authorization. Ordinary save and edit
checks operate within the permitted test journey.

For a bounded investigation that ends at the first confirmed defect, use
`/woostack-qa <url> --stop-first` with the same context. A suspected defect must reproduce from
a clean starting state before it triggers that stop.

## 2. Check the preflight and coverage

Look for three separate answers: whether the app is reachable, whether it serves the intended
candidate, and whether the available browser can perform the requested checks. A page loading is
only reachability evidence. Missing candidate identity leaves revision-specific conclusions
unverified; missing browser capabilities limit the affected checks.

Expect a bounded journey list with the important risks and a basis for expected results. For the
draft editor, a successful save is the starting point. Reload, failed saves, retries, and later
edits expose different persistence and recovery risks.

If preflight fails, use the reported prerequisite to unblock the review. A blocked attempt with
zero executed journeys is not a clean result. QA does not repair the environment on its own.

Include relevant accessibility and layout requirements in the scope. When 200% zoom is required,
use genuine browser zoom on a desktop-sized viewport. CSS scaling or a device-pixel-ratio change
does not establish that result. Phone-sized emulation and physical-device testing remain distinct.

## 3. Read findings alongside coverage limits

Inspect the sanitized report at its reported output location. For each finding, check the user
impact, starting state, minimal reproduction, expected and observed behavior, evidence, and retest
criteria. Confirmed findings require a second clean reproduction. Intermittent behavior retains
its observed frequency; unconfirmed observations remain separate.

Read each journey's result separately from the overall run outcome. `PASS` and `FAIL` describe
observed behavior. `BLOCKED`, `NOT RUN`, `UNCONFIRMED`, and `SOURCE-ONLY` identify different limits
on the evidence. A completed run can contain defects, and a partial run can have no confirmed
findings while important journeys remain untested.

For example, no network inspection means network diagnostics remain unverified. Keyboard checks
do not establish full accessibility conformance. A local candidate does not prove that its hosted
deployment behaves identically. Use the report's limits when deciding what further evidence is
needed.

## 4. Retest a corrected candidate

Request implementation separately if you want a defect repaired. Once the corrected app is running,
supply the original report and the new candidate identity:

```text
/woostack-qa https://staging.example.test
Retest the interrupted-save finding in the report I supplied against
commit <corrected-commit-sha>, build <corrected-build-id>.
Repeat its original reproduction, verify edits remain recoverable after reload,
and check nearby save and cancel behavior using the disposable test account.
```

Check that the retest identifies the corrected revision and reports the original reproduction's
new outcome. Reuse earlier evidence only where the relevant behavior, requirements, and environment
still support it. Changed inputs and unresolved risks determine what needs fresh checks.

The report provides diagnostic evidence. Publishing it, changing code, or approving a release
remains a separate action. See the [QA reference](/docs/skills/woostack-qa) for the complete workflow
and [verification guidance](/docs/guides/verification) for deciding which evidence an outcome needs.
