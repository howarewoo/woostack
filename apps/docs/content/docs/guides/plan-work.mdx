---
title: Publish a plan as GitHub issues
description: File a settled plan as coherent issue outcomes and verify the publication.
---

Start with a settled plan and an unambiguous GitHub destination. Your assistant needs authorized
issue-write access and, for existing code, access to the selected repository. Greenfield publication
needs no checkout. If the goal or material choices still need refinement, use
[Whiteboard a goal into a plan](/docs/guides/whiteboard) first. These are **requests to your
assistant**, not terminal commands. Load the named skill using your assistant's supported
mechanism; see [skill invocation](/docs/harnesses#native-skill-invocation).

<span id="1-describe-the-outcome" />

## 1. Select the plan and destination

Supply the existing plan and name the destination repository or exact GitHub Project URL.
Check that the plan identifies the source inspected, bounded outcomes, acceptance and selected
evidence, and real prerequisites. Settle material choices before publication; a plan is not an
implementation or passing check. Whiteboard asks no questions when the available context suffices.

Group implementation checkpoints into coherent issue outcomes. A checkpoint need not become a
separate issue, worker, PR, or release. Keep necessary atomic changes together without temporary
bridges just to split delivery. See [Whiteboard's reference](/docs/skills/woostack-whiteboard)
for the planning and evidence rules.

<span id="2-review-and-optionally-publish" />

## 2. Publish the plan

Check that issue outcomes do not repeat existing issues and that dependencies reflect actual
prerequisites, not their order in a list. Ask explicitly:

```text
/woostack-whiteboard File the settled plan above as GitHub issues in OWNER/REPOSITORY.
Group implementation checkpoints into coherent issue outcomes and reuse existing
issues that already cover them. Include acceptance criteria and real prerequisites,
then read back the affected issues. Do not start implementation.
```

Replace `OWNER/REPOSITORY` with the actual destination. A request to plan and file issues in one
message already authorizes publication; a separate read-only planning pass or second approval is
not required. A Project or fixed issue hierarchy is not required. Ask for native relationships
only when you need them: they count only after their writes and read-back succeed. If relationship
operations are unavailable, keep the verified issue URLs and readable prerequisites. An explicitly
required native graph remains incomplete until verified.

## 3. Check the handoff

Compare the returned issues and their content with the plan; do not infer publication from a success
sentence. If a write has an unknown result,
[inspect it before trying again](/docs/guides/troubleshooting#an-issue-or-pull-request-write-has-an-unknown-result).
Choose implementation separately: [deliver one change](/docs/guides/ship-change) or
[coordinate several approved tasks](/docs/guides/coordinate-work).
[Whiteboard's publication rules](/docs/skills/woostack-whiteboard#saving-and-publishing) own the exact boundaries.
