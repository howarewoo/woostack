---
title: Coordinate several tasks
description: Plan grouped multi-task work, delegate each group, and verify stacked draft PRs.
---

Use this guide for **approved executable tasks**, not a goal that still needs a plan. Supply task descriptions, exact issue URLs, a tracker, or an explicitly selected Project. Your assistant needs repository access, a host that can open workers, and GitHub PR publication capability for the example below. Implementation changes source; requested delivery commits and opens draft PRs. [Skill requests differ from terminal commands](/docs/harnesses#native-skill-invocation).

## 1. Select the work

Provide the scope, acceptance, and real prerequisites for each task, or select the exact source containing them. A tracker is context, not an extra task. For example:

```text
/woostack-orchestrate Plan the tasks below, then implement them. Read their scope and real prerequisites, run relevant checks, and deliver reviewable draft pull requests. Do not merge.

<task 1: outcome, acceptance, non-goals, and prerequisites>
<task 2: outcome, acceptance, non-goals, and prerequisites>
```

Replace the angle-bracket lines with real tasks. `--issue <canonical GitHub tracker URL>` can select an exact tracker instead; it does not require a native sub-issue graph or a fixed input schema. An explicit request delivers draft PRs and native stacks for the dependent PRs; add `local only` or `do not push` to narrow it, and a bare issue link grants none of that delivery authority.

## 2. Plan the groups, then delegate them

The plan comes before any edit or worker: which tasks form which pull request, what each group must change, the intended parent and landing order, and which groups are safe in parallel. Small related tasks can share one coherent PR; task count does not set PR count, and your requested mapping is kept. Each group gets delegated implementation with exclusive access to its task workspace, even for a single-group run. A dependent group starts from a verified base containing its prerequisites. Missing worker or isolation capability is reported, not replaced by edits in your primary checkout.

## 3. Verify progress and resume safely

Continue in-scope repairs in the same delivery workspace, branch, and PR. A replacement writer inherits it only after verified release and inspection of current source. Extra workspaces need a concrete isolation reason and remain bounded contributions to that delivery target, with an integration destination and safe disposition. Follow the [canonical coordination procedure](/docs/skills/woostack-orchestrate#coordinate); another checkout does not isolate shared runtime resources.

Inspect the integrated diff, refreshed affected checks and review, and actual PR head, base, state, and issue association. Temporary-branch passes alone do not verify the combined PR. A dependent PR targets its predecessor and needs native stack registration; a chained base is not membership. Unknown ownership or a lost result requires [current-state inspection before retrying](/docs/guides/troubleshooting); safe independent work can continue. Report delivery coverage, temporary-workspace disposition, local checks, CI, review, and blocked work separately. Observation lasts only during the active session. New PRs stay drafts; readiness changes only on request, and humans decide whether to merge.
