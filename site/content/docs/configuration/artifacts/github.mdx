Select GitHub artifact mirroring with `artifacts.provider: "github"`. For Build and project-backed
Fix, the [local run](/docs/configuration/artifacts/local) remains the source of truth.
Standalone parent-issue Plan (`--parent-issue`) also requires `artifacts.provider: "github"`
but needs no Project settings, Project access, or mirror.

## Configuration

For Project workflows, replace the example owner and status options with verified values from
your GitHub account or organization. The five status options must exist on the selected
single-select field and have distinct names. Parent-issue Plan needs none of these:
the `github` object, `owner`, and `projectStatuses` may all be absent.

```json
{
  "artifacts": {
    "provider": "github",
    "github": {
      "owner": "acme",
      "ownerType": "organization",
      "statusField": "Status",
      "visibility": "private",
      "projectStatuses": {
        "planned": "Todo",
        "executing": "In Progress",
        "inReview": "In Review",
        "done": "Done",
        "blocked": "Blocked"
      }
    }
  }
}
```

| Field | Type | Constraint |
| --- | --- | --- |
| `artifacts.github.owner` | string | Required for Project workflows: nonempty GitHub organization or user login. Optional for parent-issue Plan; when present it must match the canonical repository owner. |
| `artifacts.github.ownerType` | string | Optional `"organization"` or `"user"`. Resolved via discovery when omitted. |
| `artifacts.github.statusField` | string | Optional exact case-sensitive single-select field name. Defaults to `"Status"`. |
| `artifacts.github.visibility` | string | Optional `"private"` or `"public"`. Defaults to `"private"`; applies only to newly created Projects. |
| `artifacts.github.projectStatuses` | object | Required for Project workflows: mapping of exactly five keys (`planned`, `executing`, `inReview`, `done`, `blocked`) to nonempty, distinct option names on the configured status field. Not required for parent-issue Plan. |

Credentials belong in the host's secret store, never in repository configuration. Use an available,
authorized GitHub capability exposed by the host (prefer native GitHub tools when suitable;
host-authenticated `gh` remains supported). Discover actual operation capabilities and supported
read/write shapes rather than assuming tool names or schemas. Custom HTTP/GraphQL clients, credential
reads, and token forwarding are forbidden.

### Transport capabilities and boundaries

Preflight only the capabilities needed by the selected operation through the authorized GitHub
interface. Parent-issue publication needs issue, native parent/sub-issue, and dependency reads/writes,
complete pagination, and independent read-back. Issue-write access does not prove native
relationship-write access. Project workflows additionally require their selected Project, membership,
and Status operations; unavailable Project access does not block parent-only publication. A read-only
task must not require unrelated write/delete access.

Unsupported or unknown required capabilities, unauthorized scopes, another run's markers, unexpected
changes, or partial responses stop the provider operation. No test mutation is used to prove
publication permissions.

## Identities, hierarchy, and graph

Accepted canonical URL forms are:
- Projects: `https://github.com/orgs/<owner>/projects/<N>` (organizations) or `https://github.com/users/<owner>/projects/<N>` (users).
- Issues: `https://github.com/<owner>/<repo>/issues/<N>`.

Use these URLs to select resources and associate them with a PR. GitHub's internal GraphQL node
IDs and Project item IDs are kept separately for API changes.

Build and project-backed Fix resolve an exact supplied Project URL or create one `[Build]/[Fix] <goal>`
Project under the configured owner. The complete specification is written inside `ProjectV2.readme`
between markers `<!-- woostack-spec-start -->` and `<!-- woostack-spec-end -->`, preserving unrelated
README bytes. `shortDescription` contains a concise goal summary.

Existing Project plans retain parentless repository issues (`parent = null`) with direct membership.
An explicitly admitted specification parent and its member children may also be represented in a
Project; verify native links separately and never count a container as an extra task or import
nonmember children automatically. No implicit conversion or reparenting occurs. Before creating
resources, allocate recovery markers (`<!-- woostack-project-mutation:<UUID> -->` and
`<!-- woostack-issue-mutation:<UUID> -->`) to recover uncertain creation without duplicates.

### Parent-issue planning (standalone Plan only)

Standalone Plan accepts an explicit parent-issue selector instead of `--project`:

```text
/woostack-plan <approved specification> --parent-issue new
/woostack-plan [<approved specification>] --parent-issue <exact canonical GitHub issue URL>
```

`--parent-issue` is exclusive with `--project` and standalone only; delegated Plan stays
provider-free. It requires `artifacts.provider: "github"` but needs no Project settings, Project
access, Project capabilities, or mirror. The canonical repository comes from trusted Git/GitHub
evidence; when `artifacts.github.owner` is configured, it must match that repository's owner.

Publication creates or reuses one selected specification parent and reconciles one native direct
PR-sized child issue per planned task, then wires the prerequisite `blocked-by` DAG separately. The native parent hierarchy
is distinct from `blocked-by` edges and from Git branch ancestry: it groups the plan, it never
orders delivery or selects a branch parent. The parent is never a task or dependency endpoint, has
no execution, and gets no PR. Child reads verify complete parent/child pagination and each child's
actual parent. New IDs reuse the existing marker recovery without replay on uncertainty. Unrelated
or human-owned fields are preserved and children are never reparented. Nested containers, cycles,
missing endpoints, foreign parents, and partial pagination or capabilities fail closed. Repeating an
unchanged sync performs zero mutations. Task, dependency, and mapping shapes match Project mode,
with the parent stored separately in the spec item when applicable; standalone parent-issue Plan
creates no Build/Fix run.

Parent-issue planning is planning only. Explicit Orchestrate execution consumes the admitted native
child scope; bounded Execute still admits one complete task.

GitHub plans use explicit prerequisite graphs. Independent roots, forks, chains, and joins are valid;
only genuine prerequisites become native `blocked-by` edges. Each edge is a `[prerequisite, dependent]`
tuple: the dependent carries the native edge pointing at the prerequisite (blocking) issue, and reads
normalize back into the same order with both endpoints verified. Stable ordinals control display and
tie-breaking, not dependencies or Git ancestry. Existing chain edges are preserved unless the approved plan explicitly changes them.

Each root records its approved integration parent. Dependents record their prerequisites and a
parent-selection policy. The concrete parent may be a declared predecessor or an explicitly approved
integration branch/SHA containing every prerequisite change. The latter need not itself be a
predecessor task or have its own PR: verify canonical branch/SHA ancestry and every prerequisite's
complete delivery evidence, plus the integration parent's PR evidence whenever that PR exists.
Before checkout, the caller selecting a bounded task must
supply that parent and complete prerequisite-readiness evidence under the
[workspace/ancestry guidance](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/worktrees.md#repository-and-ancestry-evidence).
A join without one parent containing all required changes remains valid but cannot run until an
explicit parent/integration decision is made. Planning never creates an automatic integration branch.

Synchronization validates the complete graph before mutations and independently reads back every
issue, native hierarchy, selected membership, and exact edge. Missing or foreign endpoints,
ambiguous identities, cycles, and incomplete pagination block; they do not expand selected scope.

Execute accepts one selected bounded task, not a complete DAG. A task from any valid DAG may use
[ordinary Execute admission](/docs/skills/woostack-execute#admit-one-task) when its concrete parent and
complete prerequisite-readiness evidence are supplied; an unresolved join parent blocks that task.
An explicit [Orchestrate](/docs/skills/woostack-orchestrate) invocation dispatches the admitted graph
through isolated Execute workers. Linear, Plane, and local-only planning keep their existing sequence.

Orchestrate's `--issue` form selects the complete native child scope without requiring Project access
or provider mirroring. Its `--project` form selects only admitted Project members. Independently
validated PR delivery releases dependents; no issue closure or merge is required. Child delivery
notes preserve evidence, and only explicitly selected Project execution uses configured `inReview`
status. Both forms leave the scope open for human review/merge.

## Lifecycle and closure (retired Execute reference)

> **Retired.** Execute no longer performs GitHub Project/issue lifecycle transitions, project/run
> controller reads, closure, or `--project`/`--run`/`--recheck` scope. It accepts one complete bounded
> task and an optional exact canonical GitHub issue URL; see
> [Execute retired inputs](/docs/skills/woostack-execute#retired-inputs).

Standalone provider-backed Plan remains the only workflow that closes an exact admitted Project.
Parent-issue Plan has no Project to close. Build/Fix handoff, abandonment, blockers, and completion
leave any mirrored Project unchanged.

## Workflow matrix

| Skill | GitHub provider behavior |
| --- | --- |
| [woostack-build](/docs/skills/woostack-build) | Resolves an exact supplied Project or creates one `[Build] <goal>` Project; writes specification to managed README; creates parentless issues with direct Project membership; and wires explicit prerequisite edges. |
| [woostack-fix](/docs/skills/woostack-fix) | Bounded Fix is provider-free. Project-backed Fix proves root cause before provider access, preserves an exact source `--issue` as context with a direct Project link, and creates/reconciles a separate increment DAG. |
| [woostack-plan](/docs/skills/woostack-plan) | Standalone Plan synchronizes one exact GitHub Project or one admitted specification parent and its native children through the selected operation capabilities; it reads every affected identity, hierarchy, dependency, and membership back independently. |
| [woostack-init](/docs/skills/woostack-init) | Discovers owner, ownerType, canonical repository, and status options through the selected authorized read-only GitHub capability only when `artifacts.provider: "github"`. Never selects persistence or probes writes. |
| [woostack-orchestrate](/docs/skills/woostack-orchestrate) | Executes the native direct children of one exact `--issue` without Project/mirror prerequisites, or the admitted members of one exact configured `--project`; verifies worker PRs and records delivery without closing issues or merging. |
| [woostack-execute](/docs/skills/woostack-execute) | Accepts one complete bounded task plus an optional exact GitHub issue URL; retired `--project`, `--run`, and `--recheck` are rejected. |
| [woostack-bootstrap](/docs/skills/woostack-bootstrap) | Optional persistence only after explicit design approval and approval to write to the verified filesystem target. |
| [woostack-doctor](/docs/skills/woostack-doctor) | Checks config types locally. Explicit live checks verify Project-mirroring identity and the fixed read-only Project/Status, pagination, and independent read-back capabilities without storing secrets; they are not a parent-mode capability receipt. |
| [woostack-change](/docs/skills/woostack-change) | Goal-only Change is provider-free. An explicit exact canonical GitHub issue input performs the required read of that issue through an authorized GitHub capability (native tools preferred; host-authenticated `gh` supported); it requires no artifact-provider configuration, Project, or mirror, and performs no issue lifecycle writes. |

See the [GitHub provider contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-providers/github.md)
for exact capability, resource identity, and recovery requirements.
