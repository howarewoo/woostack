The canonical implementation rules live in the
[artifact contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md#direct-publication-and-recovery)
and the [GitHub profile](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-providers/github.md#configuration-and-scope).
Plan owns direct publication and keeps native relationship capabilities and read-back strict.
Orchestrate is read-only when interpreting a tracker: a complete readable implementation index can
establish declared membership when native child links are absent, partial, or unavailable, provided
every selected issue and contract is independently readable. Missing native metadata is not a reason
to reject a complete declared scope, but it is never reported as a successful native read or Plan
publication.

For explicit Project workflows, replace the example owner and status options with verified values from
your GitHub account or organization. The five status options must exist on the selected single-select
field and have distinct names. Parent-issue Plan needs none of these: the `github` object, `owner`,
and `projectStatuses` may all be absent.

```json
{
  "github": {
    "owner": "acme",
    "ownerType": "organization",
    "statusField": "Status",
    "projectStatuses": {
      "planned": "Todo",
      "executing": "In Progress",
      "inReview": "In Review",
      "done": "Done",
      "blocked": "Blocked"
    }
  }
}
```

| Field | Type | Constraint |
| --- | --- | --- |
| `github.owner` | string | Required for explicit Project workflows: nonempty GitHub organization or user login. Optional for parent-issue Plan; when present it must match the canonical repository owner. |
| `github.ownerType` | string | Optional `"organization"` or `"user"`. Resolved via discovery when omitted. |
| `github.statusField` | string | Optional exact case-sensitive single-select field name. Defaults to `"Status"`. |
| `github.projectStatuses` | object | Required for explicit Project workflows: mapping of exactly five keys (`planned`, `executing`, `inReview`, `done`, `blocked`) to nonempty, distinct option names on the configured status field. Not required for parent-issue Plan. |

Credentials belong in the host's secret store, never in repository configuration. Use an available,
authorized GitHub capability exposed by the host (prefer native GitHub tools when suitable;
host-authenticated `gh` remains supported). Discover actual operation capabilities and supported
read/write shapes rather than assuming tool names or schemas. Custom HTTP/GraphQL clients, credential
reads, and token forwarding are forbidden.

### Transport capabilities and boundaries

Preflight only the capabilities needed by the selected operation through the authorized GitHub
interface. Plan parent-issue publication needs issue, native parent/sub-issue, and dependency
reads/writes, complete pagination, and independent read-back. Issue-write access does not prove
native relationship-write access. Project publication additionally requires the selected Project and
membership operations; Status operations are required only when status mutation is explicitly
selected. Unavailable Project access does not block parent-only Plan publication. Orchestrate's
read-only tracker interpretation can proceed from a complete readable implementation index and
independently read selected issues when native relationship reads are unavailable; it never mutates
relationships or issues. Unsupported or unknown required capabilities, unauthorized scopes, another
operation's markers, unexpected changes, or partial responses stop the relevant GitHub operation. No
test mutation is used to prove publication permissions.


## Identities, hierarchy, and graph

Accepted canonical URL forms are:
- Projects: `https://github.com/orgs/<owner>/projects/<N>` (organizations) or `https://github.com/users/<owner>/projects/<N>` (users).
- Issues: `https://github.com/<owner>/<repo>/issues/<N>`.

Use these URLs to select resources and associate them with a PR. GitHub's internal GraphQL node
IDs and Project item IDs are kept separately for API changes.

Explicit Project workflows resolve an exact supplied Project URL under the configured owner. The
complete specification may be represented in `ProjectV2.readme` between markers
`<!-- woostack-spec-start -->` and `<!-- woostack-spec-end -->`, preserving unrelated README bytes.
`shortDescription` contains a concise goal summary.

Existing Project plans retain parentless repository issues (`parent = null`) with direct membership.
An explicitly admitted specification parent and its member children may also be represented in a
Project; verify native links separately and never count a container as an extra task or import
nonmember children automatically. No implicit conversion or reparenting occurs. Before creating
resources, allocate recovery markers (`<!-- woostack-project-mutation:<UUID> -->` and
`<!-- woostack-issue-mutation:<UUID> -->`) to recover uncertain creation without duplicates.

### Parent-issue planning

Direct and composed Plan calls accept an explicit parent-issue selector instead of `--project`:

```text
/woostack-plan <approved specification> --parent-issue new
/woostack-plan [<approved specification>] --parent-issue <exact canonical GitHub issue URL>
```

`--parent-issue` is exclusive with `--project`. It requires only the exact canonical repository,
the explicit `new` intent or exact existing parent URL, and native relationship capabilities. It does
not require a Project, Status configuration, or local run. The canonical repository comes from
trusted Git/GitHub evidence; when `github.owner` is configured, it must match that repository's owner.

Publication creates or reuses one selected specification parent and reconciles one native direct
PR-sized child issue per planned task, then wires the prerequisite `blocked-by` DAG separately. The native parent hierarchy
is distinct from `blocked-by` edges and from Git branch ancestry: it groups the plan, it never
orders delivery or selects a branch parent. The parent is never a task or dependency endpoint, has
no execution, and gets no PR. Child reads verify complete parent/child pagination and each child's
actual parent. New IDs reuse the existing marker recovery without replay on uncertainty. Unrelated
or human-owned fields are preserved and children are never reparented. Nested containers, cycles,
missing endpoints, foreign parents, and partial pagination or capabilities fail closed. Repeating an
unchanged sync performs zero mutations. Task, dependency, and mapping shapes match Project mode,
with the parent stored separately in the spec item when applicable. Direct and composed Plan calls
retain publication identities and the last verified boundary in their handback without creating a local run.

Parent-issue planning is planning only. Orchestrate interprets the planning handback or other
understandable issue/task context; a complete readable tracker index can establish declared
membership without native child links, but every selected issue and contract still needs independent
reads. Missing native metadata is not successful native Plan publication. Bounded Execute still
admits one complete task.

GitHub plans use explicit prerequisite graphs. Independent roots, forks, chains, and joins are valid;
only genuine prerequisites become native `blocked-by` edges. Each edge is a `[prerequisite, dependent]`
tuple: the dependent carries the native edge pointing at the prerequisite (blocking) issue, and reads
normalize back into the same order with both endpoints verified. Stable ordinals control display and
tie-breaking, not dependencies or Git ancestry. Existing chain edges are preserved unless the approved plan explicitly changes them.

Each root records its approved integration parent. Dependents record their prerequisites and a
parent-selection policy. At execution, Orchestrate first considers the approved integration branch
and then an existing verified unmerged prerequisite branch when stacking is permitted. A candidate
must have the recorded branch/SHA and prove canonical ancestry for every current prerequisite; a
multi-dependency task may stack when one existing branch already contains all requirements. If no
candidate exists, the join remains valid and becomes a task-local `waiting-for-merge` checkpoint;
it does not request an integration strategy. Planning never creates an automatic integration
branch, combines branches, or rewrites the graph.

Publication validates the complete graph before mutations and independently reads back every issue,
native hierarchy, selected membership, and exact edge. Missing or foreign endpoints, ambiguous
identities, cycles, and incomplete pagination block; they do not expand selected scope.

Execute accepts one selected bounded task, not a complete DAG. A task from any valid DAG may use
[ordinary Execute admission](/docs/skills/woostack-execute#admit-one-task) when its concrete parent and
complete prerequisite-readiness evidence are supplied; an unresolved join remains waiting rather
than a request for a new parent. An explicit [Orchestrate](/docs/skills/woostack-orchestrate)
invocation interprets the complete planning handback or other understandable work context, resolves
executable tasks and a bounded DAG, and dispatches ready tasks through isolated Execute workers.

Plan's only supported publication scopes are the explicit GitHub Project and parent-issue selectors
above; both retain the same prerequisite DAG and read-back contract. For Orchestrate, `--issue`,
`--issues`, and `--project` are convenience hints rather than an exhaustive admission taxonomy. The
model uses conversation, repository, and GitHub evidence to resolve canonical identities, separate
tasks from context, preserve native/declared/inferred edge provenance, and ask about material
ambiguity. Tracker content without native links can still be interpreted. For Orchestrate, a Project
is included only when explicitly selected; its status lifecycle is used only when that selection
requests status mutation, and inferred relationships are never published back to GitHub. Independently
validated PR delivery releases dependents; no issue closure or merge is required. Child delivery notes
preserve evidence, and all work leaves the scope open for human review/merge.

## Lifecycle and closure (retired Execute reference)

> **Retired.** Execute no longer performs GitHub Project/issue lifecycle transitions, project/run
> controller reads, closure, or `--project`/`--run`/`--recheck` scope. It accepts inline bounded
> instructions or one canonical task-bearing issue URL as the complete input; see
> [Execute retired inputs](/docs/skills/woostack-execute#retired-inputs).

Explicit Project lifecycle operations use only the retained exact Project and its configured fields.
Parent-issue Plan has no Project lifecycle to close. Historical handoff, abandonment, blockers, and
completion leave any retained Project artifact unchanged.

## Workflow matrix

| Skill | GitHub behavior |
| --- | --- |
| [woostack-prepare](/docs/skills/woostack-prepare) | Produces or accepts a complete packet and delegates direct native graph publication to Plan; it does not create implementation work, branches, PRs, or execution. |
| [woostack-plan](/docs/skills/woostack-plan) | `--project` requires an exact existing canonical Project URL and direct issue-graph publication; `--parent-issue new` or an exact parent URL publishes the native parent/child graph without a Project. Direct and composed Plan use the same publisher; there is no draft-only mode. |
| [woostack-orchestrate](/docs/skills/woostack-orchestrate) | Interprets a complete planning handback or other understandable work context, resolves executable tasks and a bounded dependency DAG with provenance, dispatches ready tasks, verifies worker PRs, and records delivery without closing issues or merging. Issue, issue-list, and Project arguments are convenience hints; native links are evidence when present. |
| [woostack-execute](/docs/skills/woostack-execute) | Accepts inline bounded instructions or one canonical task-bearing issue URL as the complete input; retired `--project`, `--run`, and `--recheck` are rejected. Goal-only Execute makes no remote calls; an exact issue permits only its documented read through authorized GitHub capabilities (native tools preferred; host-authenticated `gh` supported), with no Project configuration or issue lifecycle writes. Commit owns repository/PR delivery. |
| [woostack-init](/docs/skills/woostack-init) | Validates optional `github` configuration once and may discover non-secret owner/status defaults through authorized native GitHub capabilities or host-authenticated `gh`; it never selects persistence or probes writes. |
| [woostack-bootstrap](/docs/skills/woostack-bootstrap) | May publish an approved design only to an exact explicitly selected Project after target approval and collision checks. |
| [woostack-doctor](/docs/skills/woostack-doctor) | Checks config types locally. An explicit live request validates a trusted fixed read-only GitHub contract and never grants parent-mode requirements. |

See the [GitHub profile contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-providers/github.md)
for exact capability, resource identity, and recovery requirements.
