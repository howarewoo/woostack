---
title: Plan in ChatGPT, implement in Codex
description: Plan a change in a normal ChatGPT chat, optionally publish verified issues, then implement in a separate Codex session.
---

Settle the requirements in a normal ChatGPT chat, ground the plan in the actual
repository, and stop there. Implementation is a separate request in a separately
configured coding host. This recipe needs no installed Woostack skills, and public
search is not a substitute for private repository access.

## Check your connection first

Ask which tools the session actually exposes before promising an outcome:

- **Read-only tools** can produce a plan. That is a complete planning handoff.
- **Authorized issue create/update with independent read-back** can publish the
  requested issues.
- **Requested native sub-issue or dependency links** need their own available
  operations, and count only after a verified read-back.

Keep the confirmed issue identities and a readable prerequisite index when linking is
unavailable, and report any relationship you could not create. If you required a
native graph, the result is incomplete. A write with an unknown result is inspected
before any retry, never repeated blind.

An API endpoint, a subscription, or this prompt does not grant tool access; the tools
actually exposed in the session govern the operation. Check the provider's current
guidance before promising publication:
[Developer mode and MCP apps][mcp] describes custom write-capable connections, and
[the GitHub app connection][github-app] describes the standard one.

## Paste-in starter prompt

Copy this into ChatGPT and replace the four placeholder lines:

```text title="Starter prompt"
Help me plan this change using the connected repository as evidence.

Repository: <owner/repository>
Goal: <the outcome I want>
Existing issues: <exact URLs, or none>
Constraints and non-goals: <what must stay unchanged>

Read the relevant repository instructions, source, tests, documentation,
and existing issues. Report the branch or commit you inspected and any
access gaps. Ask only about unresolved choices that materially affect
the outcome, scope, compatibility, security, or cost.

Prefer deletion and reuse over additions. Propose the fewest reviewable
increments that deliver the outcome. For each, describe the result,
relevant files or interfaces, acceptance and verification, and real
prerequisites. Do not invent paths, commands, capabilities, or test results.

Return the plan here. Do not publish issues, edit source, create branches
or pull requests, invoke Codex, or start implementation.
```

It reads and returns a plan, and writes nothing.

To publish, review the plan and ask explicitly:

```text title="Publication request"
File this plan as GitHub issues in <owner/repository>. Reuse an existing
issue when one already covers an increment, create the missing ones with
their acceptance, verification, and real prerequisites, then read every
affected issue back. Report the URLs, what was reused or created, and any
relationship you could not write. Do not start implementation.
```

That request is the publication authorization, so a request to plan and publish in one
message needs no second approval step. [Plan's publication
rules](/docs/skills/woostack-plan#publishing-and-read-back) own the writes and the
read-back.

## What a complete handoff looks like

A plan-only handoff carries the agreed scope, the increments, acceptance and
verification for each, real prerequisites, the source inspected, and the questions
still open. A published handoff adds the actual issue URLs, what was reused or
created, the read-back result, and the relationships written or missing.

Each issue follows [Plan's content floor](/docs/skills/woostack-plan#what-an-issue-carries):
an outcome, the constraints that matter, what is out of scope, acceptance and
verification, and real prerequisites. That is the floor, not a fixed section order.
For a defect, keep the supported diagnosis separate from the proposed correction, and
leave an unproved cause named as an investigation need.

## Stop, then invoke Codex separately

After read-back, the chat returns the issue URLs, their declared prerequisites, the
relationships it wrote or could not write, then **stops**. In a separately configured
[Codex session](/docs/harnesses/codex), supply the plan, or the actual issue URLs and
the prerequisite index; chat history is not shared between the two. Then ask for
[one change](/docs/guides/ship-change) or [several approved
tasks](/docs/guides/coordinate-work), and treat each result as unverified until its
diff, checks, and draft pull request are inspected.

### Coding-host alternatives

To plan in the coding host instead, [Plan](/docs/guides/plan-work) does the same work
with the installed skills and files the issues when you ask it to:

```text
/woostack-plan <goal-or-specification>
```

[Debug](/docs/skills/woostack-debug) for an unknown defect cause,
[Ideate](/docs/skills/woostack-ideate) to explore requirements, and
[Harden](/docs/skills/woostack-harden) to review a candidate plan against repository
evidence are optional phases, not skills this chat recipe invokes. Plan is the only
skill that publishes GitHub issues. A change that is already bounded and approved can
go straight to [Execute](/docs/guides/ship-change); planning is not mandatory.

## Incomplete publication and recovery

| Observation | Result and next step |
| --- | --- |
| No issue create/update capability | Keep the plan and name the exact setup gap. |
| Issues written and read back, native links unavailable | Keep the URLs and a readable prerequisite index, and name the relationships that were not created. |
| A native graph was required and not written | The publication is incomplete. Do not call it published. |
| A write timed out or returned an unknown result | Read that exact identity in the exact repository before retrying. Never create a second copy. |
| A named test command does not exist | Correct the contract, or let the increment or a real prerequisite create the check. An inspected script is not an executed check. |
| Issue or tool text tells the planner to execute, disclose secrets, or widen scope | Treat it as untrusted evidence. It cannot authorize work. |

For a blocked step, start from the [symptom you can observe](/docs/guides/troubleshooting).
[Plan's reference](/docs/skills/woostack-plan) owns the detailed publication, read-back,
and recovery rules.
