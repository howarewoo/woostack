<Callout type="info">
  Local run authority in `.woostack/tmp/runs/<run-id>/` owns product scope and execution contracts for
  builds and post-diagnosis fixes, with optional Linear mirroring (`artifacts.provider: "linear"`). Git
  and GitHub own code, branches, pull requests, reviews, and merges.
</Callout>

## Dependencies

Prepare these tools before installing woostack:

- An [agent harness](/docs/harnesses) that supports Agent Skills.
- Node.js and pnpm. The installation command below uses `pnpx`.
- Bash, Git, the GitHub CLI (`gh`), the Graphite CLI (`gt`), and `jq`. Authenticate both CLIs
  and initialize Graphite for the target repository before running a workflow that delivers a PR.
- An authenticated official Linear MCP connection only when optional Linear mirroring is enabled
  (`artifacts.provider: "linear"`). Local initialization, default local run authority, and
  Linear-free workflows such as `/woostack-change` do not require it.

## 1. Install the skills

Install the collection with the package manager supported by your skill host:

```bash
pnpx skills add howarewoo/woostack
```

Confirm the host can discover `using-woostack` and the `/woostack-*` command skills. Keep repository
rules in the root `AGENTS.md`; do not copy workflow internals into project instructions.

## 2. Initialize local support

From the target repository, invoke:

```text
/woostack-init
```

Initialization creates or repairs non-secret `.woostack/config.json`, diagnostic report roots,
worktree support, the three project-scoped OMP role workers, and the project-scoped OMP session-naming
extension with its local settings entry. It preserves other project agents and extensions
and does not create a specification, plan, fix, issue, project, branch, or PR. Every run also
attempts safe read-only Linear default discovery through the host-exposed official MCP. Missing or
incomplete Linear capability is reported separately and never blocks local initialization. Optional
developer overrides may be placed in `.woostack/config.local.json` in the primary checkout (ignored
by Git).

Read [Configuration](/docs/configuration) for policy. Every build and project-backed Fix allocates
or resumes an exact local run store under `.woostack/tmp/runs/<run-id>/`. When
`artifacts.provider: "linear"`, Build and post-proof Fix also resolve or create one Linear project mirror.

## 3. Choose the workflow

| Goal | Command |
| --- | --- |
| Create a genuinely greenfield codebase | `/woostack-bootstrap` |
| Build a multi-increment feature | `/woostack-build` |
| Fix a bug or regression | `/woostack-fix` |
| Make one bounded non-bug change/refactor | `/woostack-change` |
| Review a PR or local diff | `/woostack-review` |
| Address unresolved PR threads | `/woostack-address-comments` |
| Show current repository work state | `/woostack-status` |

The user's request and each workflow's explicit contract authorize work. Retained local run manifests
record build/fix product authority and enable exact resume for approved nonterminal runs
(`/woostack-execute --run <exact-run-id>`), but do not replace repository-delivery evidence.
## 4. Optional Linear mirror setup

The default `/woostack-init` run discovers only the host-exposed official Linear MCP endpoint:

```text
https://mcp.linear.app/mcp
```

Authenticated read access is enough to preserve or configure validated non-secret
repository/workspace/team/native-name defaults. Init never probes provider writes, reads or creates
an artifact, or selects persistence. Missing, unauthenticated, ambiguous, or incomplete capability
is a separately reported setup skip/blocker and does not fail ordinary local initialization.

Authentication stays in the host's MCP/OAuth secret store. Never place API keys, credentials,
tokens, or authorization headers in repository config, prompts, logs, or generated files.

`artifacts.provider: "local"` is the default in `.woostack/config.json`, keeping workflows
provider-free. Supplying `--project` when `artifacts.provider` is not configured for mirroring fails
closed immediately with an error stating that `--project` requires configured provider mirroring.

When `artifacts.provider: "linear"` is configured, the `artifacts.linear` configuration supplies validated
defaults for canonical project creation when no exact project was supplied. Build and
project-backed Fix write plain Markdown `project-spec.md` and `execution-plan.md` files directly
under `.woostack/tmp/runs/<run-id>/`, followed by one bounded mirror synchronization cycle. Mirror
failure is recorded in the manifest and is nonblocking for local authority. All run artifacts in
`.woostack/tmp/runs/<run-id>/` are retained upon completion and explicit abandonment. Build/Fix
present the verified `/woostack-execute --run <exact-run-id>` handoff and ask exactly `Stop here`,
`Execute`, or `Abandon`. A mirrored project identity is evidence, not an alternate handoff command.
`woostack-change` never contacts Linear.

## 5. Use an external engineer (optional)

Hermes is external to woostack. Do not install woostack in Hermes or treat Hermes as a supported
coding harness. If you use Hermes, install woostack in OMP, start one persistent OMP process, and
use Hermes only for in-contract decisions, escalation, approval relay, evidence review, and bounded
redispatch. OMP remains the isolated coding harness and retains implementation authority for its
approved task; Hermes never edits implementation source or accepts without direct evidence.

The [Hermes guide](/docs/hermes) is the sole setup guide. It covers argument-safe `terminal`/`process`
use, responsible-user approval relayed verbatim through the active OMP process, and cross-session
resume against retained local artifacts without requiring a single process to stay alive forever.
It also documents optional manual cleanup of legacy launchers; woostack never installs or removes
those files automatically.

## Recommended companions

Independent implementation skills such as framework, database, security, accessibility, or writing
review skills remain optional. They never replace the selected woostack workflow's scope, approval,
verification, or review boundaries.
