This tutorial installs woostack in an existing Git repository and sets up its local configuration.
Run the terminal command in step 1 yourself, then send the slash commands in steps 2 and 3 to
your coding agent.

If you want to discover requirements in ChatGPT before using your coding allowance, follow
[Plan in ChatGPT, implement in Codex](/docs/chatgpt-to-codex). Its copyable prompt distinguishes a
planning-only result from published issues, and names the relationships it could not create. The
standard GitHub app is read-only. Authorized issue create/update can publish a complete readable
issue set for later Orchestrate verification even when native relationship writes are unavailable.
Install woostack in the coding host for the separate execution step, not as a prerequisite for that
chat.

## Before you start

You need:

- A coding [agent harness](/docs/harnesses), the application that runs your coding agent and
  loads its skills. That page covers the harnesses with documented host notes. Any other host that
  loads the skills works when it exposes the capabilities a task needs.
- Node.js and pnpm. The installation command below uses `pnpx`, pnpm's tool for running a package.
- Bash, Git, `jq` (a command-line JSON tool), and Python 3 available as `python3` in the environment
  where your agent runs commands. Init's OMP support script requires Python 3.
- An existing Git repository open in both your terminal and your agent.

The optional historical run-store reader additionally requires Unix/POSIX locking, ownership,
directory, and no-follow filesystem primitives. Python 3 alone does not make that helper a native
Windows program; installing and reading the skills does not require it.

Installed runtime paths need only the skill collection and your consumer repository, not this
project's source checkout or docs application. Maintainers can check that boundary with the
[installed integration smoke](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/workflow-smoke.md#5-installed-integration-matrix);
its deterministic helper checks and manual traces are not actual-host benchmark results.

Before using a workflow that delivers a pull request (PR), ensure Git is available and the host
exposes an authorized GitHub capability for the required reads/writes. Prefer native host GitHub
tools when suitable; authenticated `gh` is a supported alternative. The selected interface must
provide exact repository/branch/PR reads and independent write read-back; see the
[source-control contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-commit/references/source-control.md).
These delivery tools are separate from the local setup in this tutorial.

You do not need GitHub Project configuration for local setup. By default, woostack keeps
configuration, diagnostics, and any retained historical run records in the repository's local
`.woostack/` workspace. Direct GitHub issue or Project operations are explicit and never create a
second remote record.

## 1. Install the skills

Run this in your terminal from the repository root:

```bash
pnpx skills add howarewoo/woostack
```

Confirm that your harness can find `using-woostack` and the `/woostack-*` command skills. These are
instructions for the agent, not shell programs. `/woostack-init` and the other examples on this page
name the logical command; each harness has its own documented way to invoke a skill explicitly, and
the [harness reference](/docs/harnesses#native-skill-invocation) lists them. If the skills do not
appear, stop here and fix the harness installation before continuing.

## 2. Initialize local support

Send this to your coding agent with the same repository open. Do not run it in your terminal:

```text
/woostack-init
```

Init creates missing `.woostack/` configuration, diagnostic report directories, and support for
Git worktrees (separate working directories used to isolate changes). It also installs the local
OMP session-naming extension under `.omp/`; delegation uses agents already exposed by the active
session, not project-managed agent definitions. It preserves unrelated OMP agents, extensions, and
valid user configuration.

Init does not create a development plan, issue, branch, or PR, and it does not commit or push.
It stops when a path or file collision makes a change unsafe. Existing policy and reports require
an explicitly approved repair before replacement; legacy records are never migrated or deleted
implicitly.

When it finishes, check the agent's report for local setup errors and confirm that
`.woostack/config.json` exists. Init may perform narrow read-only GitHub discovery through an
authorized native capability or host-authenticated `gh` when an explicit GitHub operation needs
defaults. Missing GitHub configuration or capability does not block local setup, and discovery does
not authorize later writes. Keep credentials in your harness's authentication store, never in
`.woostack/config.json`.

## 3. Check the installation

Send this command to your coding agent:

```text
/woostack-doctor --check
```

In `--check` mode, Doctor reports local configuration and support-file problems without repairing
them or contacting GitHub. Resolve any reported local configuration error before starting
repository work. To request proposed repairs, invoke `/woostack-doctor` without `--check`; it must
ask for approval before changing anything. Doctor has no live GitHub mode; the selected workflow
reads its own required GitHub evidence through an authorized host capability.

<Callout type="info">
  Keep project-specific rules in the root `AGENTS.md`. The
  [adoption skill](/docs/skills/using-woostack) provides a short routing paragraph you can add
  to that file. Init does not edit `AGENTS.md`; avoid copying workflow internals into it.
</Callout>

## Choose what to do next

Use the workflow map to choose a command for your next task. Plan returns a plan and files GitHub
issues only when the request asks for it; the configuration reference explains surviving repository
policy and optional direct GitHub Project configuration.

For planning in the coding host, use [Plan](/docs/skills/woostack-plan), and call the public
[Debug](/docs/skills/woostack-debug), [Ideate](/docs/skills/woostack-ideate), and
[Harden](/docs/skills/woostack-harden) phases directly when you want them. An already-complete
bounded task can go straight to [Execute](/docs/skills/woostack-execute) without any planning.
For approved multi-task work, hand Orchestrate the plan, the published issues, or understandable
issue/task context. It interprets the conversation, repository, and GitHub records, separates
executable issues from context, reads the real dependencies with provenance, and asks a focused
question only when material ambiguity affects outcome, scope, or authority. With `--issue`, a
complete readable tracker index can establish declared membership when native child links are
absent, partial, or unavailable; every selected issue still needs real identity and a complete
contract. `--issue`, `--issues`, and `--project` are convenience hints, not an exhaustive admission
taxonomy. A Project is included only when explicitly selected; its status lifecycle is used only
when that selection requests status mutation. See
[Orchestrate](/docs/skills/woostack-orchestrate#coordinate) for coordination, graph evidence, and
uncertainty boundaries.
