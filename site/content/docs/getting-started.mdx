<Callout type="info">
  Linear owns current product scope and execution contracts for builds and post-diagnosis fixes.
  Git and GitHub own code, branches, pull requests, reviews, and merges. The responsible user's
  exact native Linear approval event clears only the matching fix/build revision gate.
</Callout>

## 1. Install the skills

Install the collection with the package manager supported by your skill host:

```bash
pnpx skills add howarewoo/woostack
```

Confirm the host can discover `using-woostack` and the `/woostack-*` command skills. Keep repository
rules in the root `AGENTS.md`; do not copy workflow internals into project instructions.

## 2. Initialize local support

From the target repository, invoke:

```text
/woostack-init
```

Initialization creates or repairs non-secret `.woostack/config.json`, diagnostic report roots,
worktree support, and the three project-scoped OMP role workers. It preserves other project agents
and does not create a specification, plan, fix, issue, project, branch, or PR. Every run also
attempts safe read-only Linear default discovery through the host-exposed official MCP. Missing or
incomplete Linear capability is reported separately and never blocks local initialization.

Read [Configuration](/docs/configuration) for policy. Every build resolves or creates one Linear
project. A proved fix binds or creates one Linear issue after proof and needs no project.

## 3. Choose the workflow

| Goal | Command |
| --- | --- |
| Create a genuinely greenfield codebase | `/woostack-bootstrap` |
| Build a multi-increment feature | `/woostack-build` |
| Fix a bug or regression | `/woostack-fix` |
| Make one bounded non-bug change/refactor | `/woostack-change` |
| Review a PR or local diff | `/woostack-review` |
| Address unresolved PR threads | `/woostack-address-comments` |
| Show current repository work state | `/woostack-status` |

The selected workflow's contract and approval gates authorize work. Linear records are required for
fix/build product authority but do not replace repository-delivery evidence.

## 4. Automatic Linear default setup

The default `/woostack-init` run discovers only the host-exposed official Linear MCP endpoint:

```text
https://mcp.linear.app/mcp
```

Authenticated read access is enough to preserve or configure validated non-secret
repository/workspace/team/native-name defaults. Init never probes provider writes, reads or creates
an artifact, or selects persistence. Missing, unauthenticated, ambiguous, or incomplete capability
is a separately reported setup skip/blocker and does not fail ordinary local initialization.

Authentication stays in the host's MCP/OAuth secret store. Never place API keys, credentials,
tokens, or authorization headers in repository config, prompts, logs, or generated files.

The `linear` configuration supplies validated defaults after a workflow requires or selects Linear.
Build uses them to create its canonical project when no exact project was supplied. A proved new fix
uses its configured team to create one issue when no exact issue was supplied. Policy cannot
authorize a provider write. Before access, the workflow verifies canonical repository association
and workspace/team; after every mutation or approval event, it independently reads the exact record
back.

Build uses one project for the high-level specification, one direct issue per increment, and native
issue dependencies. Fix uses one issue. `woostack-change` never contacts Linear.

## 5. Optional: configure a Hermes + OMP engineer pair

The pair is one adapter for the [engineer-agent contract](/docs/concepts/engineer-agents):

- Hermes decides, performs independent review, comments, accepts, redispatches, and escalates.
- One isolated OMP profile implements one approved bounded task in one collision-safe worktree.
- Hermes never codes; OMP never reviews or accepts its own work.
- Git/GitHub evidence remains authoritative.

Create distinct Hermes and OMP profiles/sessions, role-owned credential/config roots, a stable
engineer name, and a canonical worktree contract. Confirm the installed OMP CLI invocation and use
an argument-safe PTY interface. Profile names alone are not isolation.

For fix/build units, connect the official MCP independently in each profile and keep their secret
stores and sessions distinct. Artifact-optional units need it only when explicitly selected.

Follow the exact setup and dispatch boundaries on the [Hermes](/docs/harnesses/hermes) and
[OMP](/docs/harnesses/omp) pages.

The canonical [Hermes bound-unit setup](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/hermes.md#bound-unit-manifest-and-binding)
owns the setup sequence and manifest contract. Follow it once rather than copying the schema here;
the [OMP page](/docs/harnesses/omp) owns coder dispatch details.

## 6. Optional: production-error response policy

`/woostack-init --respond` may validate non-secret observability defaults and available authenticated
provider capabilities. It never requests credentials or queries production during setup.

[woostack-respond](/docs/skills/woostack-respond) writes sanitized local diagnostic reports and
keeps raw provider evidence transient. Reports are advisory; a remediation route independently
hardens its contract, and a proved fix route binds or creates one issue after root-cause proof.

## Recommended companions

Independent implementation skills such as framework, database, security, accessibility, or writing
review skills remain optional. They never replace the selected woostack workflow's scope, approval,
verification, or review boundaries.
