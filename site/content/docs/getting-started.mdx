This tutorial installs woostack in a Git repository you already have, checks that the local setup
works, and finishes with a read-only plan for a Verification section in that repository's README.
The planning step edits no application source, files no issue, and opens no pull request; Init
does create local support files in step 2.

Run the terminal command in step 1 yourself. Send the slash requests in the later steps to your
coding assistant, with the same repository open in both places.

If you want to discover requirements in ChatGPT before using your coding allowance, follow
[Plan in ChatGPT, implement in Codex](/docs/chatgpt-to-codex). Its starter prompt returns a
read-only plan. To file issues, ask separately after reviewing the plan, or explicitly request
planning and publication together. The standard GitHub app is read-only; publication needs
authorized issue create/update tools and read-back. Install woostack in the coding host for the
separate execution step, not as a prerequisite for that chat.

## Before you start

You need:

- An existing Git repository, open in your terminal and in your coding assistant.
- A [coding assistant](/docs/harnesses), the application that runs your agent and loads its skills.
  Another host works when it exposes the capabilities a task needs.
- Node.js and pnpm. The installation command below uses `pnpx`, pnpm's tool for running a package.
- Bash, Git, and `jq`, a command-line JSON tool, available where your assistant runs commands.
  Init and Doctor validate `.woostack/config.json` with `jq`.
- Python 3, available as `python3`, only if you want the optional reader for retained local run
  records. Installing the skills, running Init, and running Doctor do not need it.

This tutorial needs no GitHub Project and publishes no issue or pull request. Installing the skills
requires network access, and Plan may read existing GitHub issues. A `/woostack-*` example names the
logical request, and each assistant has its own documented way to invoke a skill explicitly, listed
in the [harness reference](/docs/harnesses#native-skill-invocation).

## 1. Install the skills

Run this in your terminal from the repository root:

```bash
pnpx skills add howarewoo/woostack
```

Then confirm your assistant can find `using-woostack` and the `/woostack-*` workflow skills. They are
instructions for the agent, not shell programs. If your assistant cannot see them,
[fix the installation before continuing](/docs/guides/troubleshooting#your-assistant-cannot-find-a-woostack-skill).

## 2. Initialize local support

Send this to your coding assistant:

```text
/woostack-init
```

Init is local-only. It creates the missing `.woostack/config.json`, local diagnostic report roots,
and worktree support, and it stops at any path, permission, or file collision that would make a
change unsafe. It preserves what is already there, including legacy settings and retained run
records, then reports what it created, preserved, skipped, or blocked.

Init never contacts GitHub, discovers a Project, creates an issue, branch, or pull request, or edits
your `AGENTS.md`. It does not read or write credentials either, so keep GitHub authentication in
your host's secret store.

When it finishes, read the setup report and confirm that `.woostack/config.json` exists. A blocked
path is a result to report, not something to work around by overwriting the file.

## 3. Check the installation

Send this to your coding assistant:

```text
/woostack-doctor --check
```

In `--check` mode Doctor runs static local checks. It reads your configuration and support files,
makes no GitHub call, and changes nothing. It exits nonzero when it finds an error or cannot finish
a check, so a failed or incomplete inspection is not a healthy one, and a clean local check is not
proof of GitHub access. Resolve a reported local problem before continuing; the matching recovery
is in [Doctor reports a local configuration error](/docs/guides/troubleshooting#doctor-reports-a-local-configuration-error),
and remote access is a separate question in
[Doctor passes but GitHub fails](/docs/guides/troubleshooting#doctor-passes-but-github-fails).

## 4. Create your first plan

Send this request to your coding assistant:

```text
/woostack-plan Plan a Verification section for this repository's README.
Use the repository's existing instructions and actual check commands.
Reuse an existing section if it already serves this purpose.
Keep the scope to documentation. Return the plan here; do not file
GitHub issues or implement changes.
```

Read the returned plan before deciding anything else. A complete answer names the documentation it
inspected and the change it proposes, and says how someone would confirm the result is accurate. Two
honest outcomes count as success: the repository already has a Verification section that serves the
purpose, so the plan leaves it alone, and a check command the repository does not actually have is
reported as missing instead of invented.

This step writes nothing. Plan does not edit your README, create an issue, branch, commit, or pull
request. The files under `.woostack/` from step 2 are local setup you created on purpose, and they
are not the start of an implementation.

## Choose what to do next

Your plan stays in the conversation until you act on it. Delivering it is a separate, explicit
request: [Deliver one change](/docs/guides/ship-change) covers implementing the plan and submitting
a draft pull request, along with the GitHub capability and isolated workspace that delivery needs.
You decide whether it happens, and only you mark a draft ready or merge it.

For any other task, the [task guides](/docs/guides) start from the result you want.
