title: Getting started
description: Install woostack in a coding harness and initialize local repository support.

This tutorial installs woostack in an existing Git repository and sets up its local configuration.
Run the terminal command in step 1 yourself, then send the slash commands in steps 2 and 3 to
your coding agent.

## Before you start

You need:

- A supported [agent harness](/docs/harnesses), the application that runs your coding agent and
  loads its skills. Check that page for your harness's setup and capability limits.
- Node.js and pnpm. The installation command below uses `pnpx`, pnpm's tool for running a package.
- Bash, Git, `jq` (a command-line JSON tool), and Python 3 available as `python3` in the environment
  where your agent runs commands. Init's OMP support script requires Python 3.
- An existing Git repository open in both your terminal and your agent.

Before using a workflow that delivers a pull request (PR), also install Git and authenticate the
GitHub CLI (`gh`). Git + `gh` is the default source-control path. Graphite is optional for an
explicitly selected or verified already-managed task/stack; see the
[source-control contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-commit/references/graphite.md).
These delivery tools are separate from the local setup in this tutorial.

You do not need a Linear, Plane, or GitHub project for local setup. By default, woostack keeps
planning files and run records in the repository's local `.woostack/` workspace. Optional provider
mirroring copies those records to a configured service.

## 1. Install the skills

Run this in your terminal from the repository root:

```bash
pnpx skills add howarewoo/woostack
```

Confirm that your harness can find `using-woostack` and the `/woostack-*` command skills. These are
instructions for the agent, not shell programs. If the skills do not appear, stop here and fix the
harness installation before continuing.

## 2. Initialize local support

Send this to your coding agent with the same repository open. Do not run it in your terminal:

```text
/woostack-init
```

Init creates missing `.woostack/` configuration, diagnostic report directories, and support for
Git worktrees (separate working directories used to isolate changes). It also installs managed OMP
agent definitions and session-naming support under `.omp/`. It preserves unrelated project agents,
extensions, and valid user configuration.

Init does not create a development plan, issue, branch, or PR, and it does not commit or push.
It stops when a path or file collision makes a change unsafe. Existing policy and reports require
an explicitly approved repair before replacement; legacy records are never migrated or deleted
implicitly.

When it finishes, check the agent's report for local setup errors and confirm that
`.woostack/config.json` exists. Init attempts read-only Linear setup on every run and reports that
outcome separately. It also performs read-only GitHub discovery when
`artifacts.provider: "github"` is selected. Missing provider access does not block local setup,
and discovery does not enable mirroring or authorize later provider operations. Keep credentials
in your harness's authentication store, never in `.woostack/config.json`.

## 3. Check the installation

Send this command to your coding agent:

```text
/woostack-doctor --check
```

In `--check` mode, Doctor reports local configuration and support-file problems without repairing
them or contacting a provider. Resolve any reported local configuration error before starting
repository work. To request proposed repairs, invoke `/woostack-doctor` without `--check`; it must
ask for approval before changing anything. Provider connectivity checks require an explicit
`--live` request and a configured remote provider.

<Callout type="info">
  Keep project-specific rules in the root `AGENTS.md`. The
  [adoption skill](/docs/skills/using-woostack) provides a short routing paragraph you can add
  to that file. Init does not edit `AGENTS.md`; avoid copying workflow internals into it.
</Callout>

## Choose what to do next

Use the workflow map to choose a command for your next task. The configuration reference explains
how to change repository policy or enable optional provider mirroring.

For an approved GitHub plan, hand the coding agent one exact specification parent issue with native
PR-sized children using `/woostack-orchestrate --issue <canonical parent issue URL>`. If no common
parent or Project exists, supply the exact selected issues with
`/woostack-orchestrate --issues <canonical issue URL> ...`; list mode infers a bounded technical
DAG without creating a container or publishing native dependency edges. No GitHub Project is
required for either form. See [Orchestrate](/docs/skills/woostack-orchestrate) for admission,
worker capabilities, graph evidence, and recovery boundaries.
