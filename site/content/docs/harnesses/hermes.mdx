title: Hermes Agent
description: Optional decision-maker profile, native delegation, and isolated OMP implementation pairing.
---

Hermes can use woostack in two ways. Its native `delegate_task` route is the default. An explicit
Hermes + OMP pairing makes Hermes the decision-maker and independent reviewer while a separate OMP
profile implements one bounded task. Neither route requires Linear.

See the canonical
[Hermes host adapter](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/hermes.md)
for host routing and degradation rules.

## Native delegation

Use `delegate_task` with a complete bounded goal and exact repository/worktree context. Prefer a
leaf worker unless the task genuinely needs another independent decomposition layer. Batch
dependency-independent tasks within the configured concurrency limit.

A child gets fresh context, so the dispatch must contain every contract, path, invariant, and
handback field it needs. Hermes owns scope, synthesis, workflow gates, and acceptance.

## Optional Hermes + OMP engineer pair

The pairing follows the provider-neutral
[engineer-agent contract](/docs/concepts/engineer-agents):

- Hermes owns the contract, in-scope decisions, independent code/PR review, comments, acceptance,
  redispatch, and escalation.
- One isolated [OMP profile](/docs/harnesses/omp) owns implementation and self-check for one bounded
  task in one collision-safe worktree.
- Hermes never edits implementation source, runs implementation tests, commits, pushes, or opens the
  implementation PR.
- OMP never reviews or accepts its own work.
- Git/GitHub evidence owns source, ancestry, branches, PRs, review, and delivery truth.

### Required isolation

Pin one stable engineer name, distinct Hermes and OMP profiles/sessions, role-owned credential and
config roots, one canonical worktree/branch/base/head, one bounded task contract, and one expected
handback. Profiles isolate host state, not the filesystem or inherited Git/GitHub credentials;
worktrees and role-specific environments supply the actual boundary.

Do not dispatch on profile-name or config claims alone. Verify the active executables, profile,
repository, worktree, branch/ancestry, credential surfaces, and required capabilities.

### Dispatch and review

Use Hermes' argument-safe PTY process interface with the exact OMP CLI argv documented on the
[OMP page](/docs/harnesses/omp). Never interpolate task/artifact text into shell source.

1. OMP implements and verifies the bounded task, returning an uncommitted diff and evidence.
2. Hermes reads the complete diff and performs specification then quality review.
3. Only after a pass may Hermes redispatch the same OMP profile/worktree for one bounded
   `/woostack-commit` action.
4. Hermes independently reads the submitted PR/head/diff and performs the PR review.
5. An in-contract correction returns to the same coder/worktree. Contract changes go to the user or
   owning decision-maker.

No paired step merges.

## Linear artifacts

For exact caller-selected artifacts, explicit persistence, or fix/build plans with available
repository Linear capability, each profile may connect independently to the official Linear MCP at:

```text
https://mcp.linear.app/mcp
```

Credentials remain in each profile's own MCP/OAuth secret store. Do not share tokens/sessions or
place credentials in repository config, prompts, logs, staged files, or generated output. Follow the
[Linear artifact contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md).

Artifact access may synchronize specifications, plans, fixes, or review notes. It never supplies
assignment, dispatch, commit, review, or acceptance authority. `woostack-change` never contacts
Linear.

## Recovery

Stop at the last verified boundary on worktree, ancestry, credential, process-exit, verification,
review, submission, or read-back drift. Preserve recoverable work. Never silently switch profiles,
worktrees, or roles.
