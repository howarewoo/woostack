---
title: Harness reference
description: Supported coding harnesses, native capability differences, and host-specific behavior.
---

A harness is the application that runs your coding agent and gives it tools to read files, edit
code, and run commands. Woostack provides skills for that agent to follow. The six harnesses below
have documented adapters, which tell woostack how to use each host's tools.

Capabilities differ: a host may let woostack choose a model for each worker, set its working
directory, or run several workers at once. A worker (also called a subagent) handles an assigned
task and returns its results to the main agent. Giving it a separate conversation context does not
by itself restrict which files it can edit; the workflow must also set the allowed paths and
worktree, a separate checkout for the task.

When a required capability is missing, woostack reports the limitation or stops the workflow.
Unlisted hosts have no supported per-call routing.

Hermes may coordinate decisions and review results from one persistent OMP process, but woostack
does not install in Hermes. The coding harness runs the implementation and its workers. See the
[top-level Hermes guide](/docs/hermes) for the permission and process boundaries.

## Capability comparison

| Harness | Model and effort routing | Working directory | Host behavior |
| --- | --- | --- | --- |
| [omp (Oh My Pi)](/docs/harnesses/omp) | Selects an existing host agent; model and effort are host-owned, and Woostack leaves the conditional effort knob unset | Passed in the task prompt and verified by the worker | OMP manages models and recovery |
| [opencode](/docs/harnesses/opencode) | Model selection for each worker | Passed when supported; always included in the prompt | Provider usage-limit errors stop the worker |
| [Claude Code](/docs/harnesses/claude-code) | Model and supported effort selection for each worker | Worker uses and checks the directory named in the prompt | Provider usage-limit errors stop the worker |
| [Codex](/docs/harnesses/codex) | Model selection for local workers; one model per Codex Action job | Passed when supported; always included in the prompt | Local and CI routing differ |
| [Cursor / Composer](/docs/harnesses/cursor) | All workers use the session model | Worker uses the directory named in the prompt | Requested tiers use the same model |
| [Antigravity CLI](/docs/harnesses/antigravity) | One model per session | Worker uses the directory named in the prompt | Requires interactive login; cannot run in temporary headless CI |

For OMP,
[host-owned agent routing](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/omp.md)
selects a suitable agent already exposed in the active session. OMP controls the models behind
those agents, provider credentials, and fallback policy, including when Hermes coordinates the work.

The [model-tier reference](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/model-tiers.md)
defines the shared `fast`, `standard`, and `deep` policy. Each host page links to its adapter for
the exact tool calls and rules.
