---
title: Harness reference
description: Supported coding harnesses, native capability differences, and host-specific behavior.
---

A harness is the application that runs your coding agent and gives it tools to read files, edit
code, and run commands. Woostack provides skills for that agent to follow. The six harnesses below
have documented adapters, which tell woostack how to use each host's tools.

Capabilities differ, and only the active session's tool schema and discovered agents prove what a
harness accepts. A host may expose a model or effort field for each worker, set its working
directory, or run several workers at once — and a harness page is not proof that it does. A worker
(also called a subagent) handles an assigned task and returns its results to the main agent.
Giving it a separate conversation context does not by itself restrict which files it can edit; the
workflow must also set the allowed paths and worktree, a separate checkout for the task.

When a required capability is missing, woostack reports the limitation or stops the workflow. A
missing optional field falls back to the harness's own default with one notice. Unlisted hosts have
no documented per-call routing.

Hermes may coordinate decisions and review results from one persistent OMP process, but woostack
does not install in Hermes. The coding harness runs the implementation and its workers. See the
[top-level Hermes guide](/docs/hermes) for the permission and process boundaries.

## Capability comparison

| Harness | Model and effort routing | Working directory | Host behavior |
| --- | --- | --- | --- |
| [omp (Oh My Pi)](/docs/harnesses/omp) | Selects an agent the session exposes; model is host-owned and effort appears only when the active schema has it | Named in the prompt and verified by the worker | OMP manages models and recovery |
| [Claude Code](/docs/harnesses/claude-code) | A model parameter is documented for a single invocation; effort is a worker or session setting | Named in the prompt and verified by the worker | Provider usage-limit errors stop the worker |
| [Codex](/docs/harnesses/codex) | Requested in the prompt or agent configuration, with documented inheritance; one model per Codex Action job | Named in the prompt and verified by the worker | Local and CI routing differ |
| [opencode](/docs/harnesses/opencode) | Configured per agent; a per-call field is unproven until the active schema shows one | Named in the prompt and verified by the worker | Provider usage-limit errors stop the worker |
| [Cursor / Composer](/docs/harnesses/cursor) | Session model unless the active runtime exposes per-call routing | Named in the prompt and verified by the worker | Requested tiers may collapse onto one model |
| [Antigravity CLI](/docs/harnesses/antigravity) | One run model unless the active runtime exposes per-call routing | Named in the prompt and verified by the worker | Requires interactive login; cannot run in temporary headless CI |

For OMP,
[host-owned agent routing](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/omp.md)
selects a suitable agent already exposed in the active session. OMP controls the models behind
those agents, provider credentials, and fallback policy, including when Hermes coordinates the work.

The [model-tier reference](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/model-tiers.md)
defines the shared `fast`, `standard`, and `deep` policy. Each host page links to its adapter for
the exact tool calls and rules.

## Native skill invocation

Woostack skill names are the same in every harness. A `/woostack-*` example in this documentation
names the logical command or request; each harness has its own documented way to invoke a skill
explicitly. Use the form your harness documents — it is the same skill, with the same permissions
and the same result.

| Harness | Documented explicit invocation |
| --- | --- |
| [omp (Oh My Pi)](/docs/harnesses/omp) | `/skill:woostack-execute` |
| [Claude Code](/docs/harnesses/claude-code) | `/woostack-execute` |
| [Codex](/docs/harnesses/codex) | `$woostack-execute` |
| [opencode](/docs/harnesses/opencode) | Ask for the named skill; the native `skill` tool loads it |

Each harness page links the official documentation its example was verified against, and the
[host reference](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/README.md#native-skill-invocation)
lists them together. Cursor and Antigravity CLI have no source-verified invocation form recorded
here; use each harness's own documented form.
