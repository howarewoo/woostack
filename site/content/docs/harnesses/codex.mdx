Codex supports two ways to run woostack:

- Local Codex clients — the CLI, IDE extension, and desktop app — enable subagent workflows by
  default. A worker inherits its configured agent or parent model and effort
  ([subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)). An explicit one-run
  native request can be stated in the prompt; a wire field is passed only when the active schema
  exposes its exact name and the host permits it. A prompt alone does not prove the override ran.
- A Codex GitHub Action job runs one non-interactive `codex exec` step with host-configured
  `model` and `effort` inputs ([Codex GitHub Action](https://learn.chatgpt.com/docs/github-action)).
  Whether the job can fan out is a capability of the active run to verify.

No per-worker working directory is documented. The task prompt always names the exact worktree, the
separate checkout assigned to the task, and the worker verifies that path before it writes.

If the provider's usage limit is exhausted, the worker returns an error unless the host recovers.
Woostack does not manually enact repository fallback lists.

Invoke a woostack skill in Codex with its documented mention, for example `$woostack-execute` — type
`$` to mention a skill, or run `/skills`
([build skills](https://learn.chatgpt.com/docs/build-skills)). It is the same skill and the same
permissions as the `/woostack-*` form used elsewhere in this documentation.

## Receive a ChatGPT planning handoff

Follow [the ChatGPT-to-Codex guide](/docs/chatgpt-to-codex) to plan without installed chat skills.
ChatGPT's standard GitHub app is read-only. With no issue-write capability, the route is
planning-only. With authorized issue create/update and independent issue read-back but no native
relationship writes, ChatGPT can produce a complete readable tracker/index that Orchestrate later
verifies as declared scope; that is not successful native Plan publication. Full native Plan-style
publication still requires the strict issue, native containment/dependency, pagination, and read-back
operations. A subscription or API documentation does not prove any capability.

Install woostack in local Codex using [Getting started](/docs/getting-started). Confirm the current
runtime exposes delivery-capable subagents, isolated workspaces, Git, Python 3 for the Orchestrate
helper, and an authorized native GitHub interface or host-authenticated `gh`. Tracker interpretation
includes a Project only when explicitly selected; its status lifecycle is used only when that
selection requests status mutation. A missing delivery primitive blocks before dispatch; Codex Action's
single-session mode cannot run Orchestrate by implementing tasks inline.

After the planning chat has stopped with a verified native or declared handback, send the complete
planning context to Codex. A canonical tracker URL is a convenient hint:

```text
/woostack-orchestrate --issue <verified canonical tracker URL>
```

In Codex, write that same request as `$woostack-orchestrate --issue <verified canonical tracker
URL>`.

Orchestrate independently reads the tracker and every selected issue, resolves executable tasks and
a bounded technical dependency DAG, and then selects and summarizes a model-chosen single-parent
execution forest before branch/worktree allocation. It gives Execute workers their complete
contracts, persisted plan, and verified effective-prerequisite readiness. A complete tracker index
can establish declared membership with no native child links; each selected issue still needs real
identity and a complete contract, and the tracker stays context with no worker or PR. Independent
roots can run together; added execution parents are compatibility ordering, not native relationship
evidence. A join can stack on its selected verified branch when containment and readiness are
eligible. Only the approved `merge-checkpoint` fallback for existing divergence or repository
constraints enters `waiting-for-merge`; a suitable selected parent avoids that pause. No worker or
speculative checkout is reserved, unrelated work continues, and no integration strategy is
requested. Current PR lifecycle evidence is reconciled separately from retained delivery evidence,
including human-ready, merged, closed-unmerged, and legitimately deleted source-branch states.
Equivalent reordered input resumes the persisted plan. A newer execution-layout revision requires
genuinely unstarted changes except for verified recovery from legacy execution-parent drift;
incompatible started work is controlled `execution-plan-drift`. Changed technical graph is
`snapshot-drift`. While the session stays active,
Orchestrate keeps observing each admitted PR's remote checks and dispatches same-PR Execute repairs
for actionable failures using the effective graph. There is no automatic integration branch or merge,
and no monitoring after the session ends.

If chat tools cannot write issues, explicitly pass the complete approved packet to Plan in Codex.
This is coding-host planning, not a chat-only allowance-saving route. Plan remains the sole
skill-owned publisher and keeps its strict native publication gates. Prepare and the public phases
are also available here; a complete bounded task can go directly to Execute. Model and usage rules
are linked with their last-verified date in the guide.

For detection, local and Action behavior, per-skill instructions, and fallback rules,
read the [canonical Codex reference](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/codex.md).
