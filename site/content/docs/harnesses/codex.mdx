Codex supports two ways to run woostack:

- Local Codex clients — the CLI, IDE extension, and desktop app — enable subagent workflows by
  default. A worker inherits its configured agent or parent model and effort
  ([subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)). An explicit one-run
  native request can be stated in the prompt; a wire field is passed only when the active schema
  exposes its exact name and the host permits it. A prompt alone does not prove the override ran.
- A Codex GitHub Action job runs one non-interactive `codex exec` step with host-configured
  `model` and `effort` inputs ([Codex GitHub Action](https://learn.chatgpt.com/docs/github-action)).
  Whether the job can fan out is a capability of the active run to verify.

No per-worker working directory is documented. Pass the selected workspace in a delegated task
and have the worker verify it before writing. Provider recovery belongs to Codex.

Invoke a woostack skill in Codex with its documented mention, for example `$woostack-execute` — type
`$` to mention a skill, or run `/skills`
([build skills](https://learn.chatgpt.com/docs/build-skills)). It is the same skill and the same
permissions as the `/woostack-*` form used elsewhere in this documentation.

## Receive a ChatGPT planning handoff

Follow [the ChatGPT-to-Codex guide](/docs/chatgpt-to-codex) to plan without installed chat skills.
ChatGPT's standard GitHub app is read-only. With no issue-write capability, the route is
planning-only. With authorized issue create/update and independent issue read-back but no native
relationship writes, ChatGPT can produce a complete readable tracker/index that Orchestrate later
verifies as declared scope; that is not a verified native graph. When the request requires native
relationships, they stay outstanding until the host can actually write and read them. A
subscription or API documentation does not prove any capability.

Install woostack in local Codex using [Getting started](/docs/getting-started). Confirm the current
runtime exposes Git, isolated workspaces, and an authorized native GitHub interface or
host-authenticated `gh`; delivery-capable subagents let it run ready groups together. A session
without them reports that missing worker capability for the affected delivery instead of editing
the primary checkout.
Tracker interpretation includes a Project only when explicitly selected; its status lifecycle is
used only when that selection requests status mutation.

After the planning chat has stopped with a verified native or declared handback, send the complete
planning context to Codex. A canonical tracker URL is a convenient hint:

```text
/woostack-orchestrate --issue <verified canonical tracker URL>
```

In Codex, write that same request as `$woostack-orchestrate --issue <verified canonical tracker
URL>`.

Orchestrate independently reads the selected scope and dependencies, states the group plan, then
delegates each group to a worker in its own task worktree. When the host exposes no subagents, it
reports that boundary rather than running the same scope inline. See
[Orchestrate](/docs/skills/woostack-orchestrate) for scope, ordering, and delivery boundaries.

If chat tools cannot write issues, pass the plan and its evidence to Plan in Codex. Plan publishes
issues only when requested. Debug, Ideate, and Harden are optional phases; a bounded task can go
directly to Execute.

The optional [Codex host notes](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/codex.md)
record these mechanics against their sources.
