OMP is a supported coding harness, the application that runs your agent and its tools.
Woostack uses agents already exposed by the active OMP session. Install woostack in OMP, even
when an external engineer such as Hermes coordinates the work; woostack does not install a second
agent catalog.

## Native OMP agent routing

OMP's `task` tool accepts a worker selector but does not expose a per-call model, tier, or working
directory setting to Woostack: the task wire schema exposes no model field at all, and OMP resolves
the worker's model from the `task.agentModelOverrides` setting, the agent frontmatter `model` list,
then the parent session's model. Effort is conditional. When the host setting `task.enableEffort` is
enabled (default `false`), the active task schema exposes optional `effort` with exactly `"lo"`,
`"med"`, or `"hi"`.
When it is disabled, that field is absent. Woostack inspects the active schema or tool description
before dispatch and does not enable host settings or set the optional effort field. OMP owns effort
selection. Woostack records verified host effort evidence separately; it does not translate
repository model-tier values into this knob. A selector is not proof of the model or effort used.

The conditional schema and setting are documented in OMP's [task-agent discovery reference](https://github.com/can1357/oh-my-pi/blob/main/docs/task-agent-discovery.md)
and implemented by [`task/types.ts`](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/task/types.ts).
The dispatch-time setting and rejection path are in
[`task/index.ts`](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/src/task/index.ts).

- Run `woostack-init` before relying on session naming. It provisions only the session-name extension,
  settings entry, and ignore lines while preserving other project content. Init and Doctor never
  create or repair OMP agent definitions; delegated work selects agents already exposed by the host.

- Use only names actually exposed by the active session. OMP's bundled set includes `task` as a
  write-capable general-purpose agent, `scout` for read-only exploration, and `reviewer` /
  `security-reviewer` for read-only review; a session can expose more. Do not create aliases or
  project definitions to fill a missing name.
- Inspect the active task schema before choosing a wire shape. When `task.batch` is enabled, OMP
  exposes `{ context, tasks[] }`; send dependency-independent bounded tasks in that shape. When
  it is disabled, send one flat `{ agent?, task, ... }` call at a time where the workflow permits
  it. Do not send `tasks` or `context` in that mode because OMP rejects those fields before a
  worker starts.
- Pass the exact workspace, branch, parent/start SHA, allowed paths, authority limits, acceptance,
  required checks, smoke scenario, and result-evidence requirements in the task prompt. The `task`
  primitive does not accept `cwd`; the worker verifies the prompt-pinned workspace before editing.
- Execute remains one bounded task and does not schedule a project graph. Orchestrate requires a
  delivery-capable worker and blocks when the host cannot provide one. If batch is unavailable,
  Orchestrate may use supported single-call dispatch only where its own contract permits it; a
  sequence of calls does not prove same-wave or parallel execution.
- Missing capabilities and missing result evidence are reported as blockers. Woostack does not
  switch profiles, weaken isolation, or treat absent evidence as success.

## Native skill invocation

Invoke a woostack skill in OMP with its documented command, for example
`/skill:woostack-execute`. Interactive mode registers one slash command per discovered skill when
`skills.enableSkillCommands` is enabled, and `/skill:<name> [args]` injects that skill's content
([skills](https://github.com/can1357/oh-my-pi/blob/main/docs/skills.md)). It is the same skill and
the same permissions as the `/woostack-*` form used elsewhere in this documentation; every
documented form is listed in the
[host reference](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/README.md#native-skill-invocation).

## Previously generated agent definitions

Older installations may contain `.omp/agents/woostack-{fast,standard,deep}.md`. Init and Doctor
leave these user-owned files alone; their absence is normal and is never a failure. Cleanup is
optional, manual, and user-initiated — woostack never runs it, and there is no migration subsystem.

To remove only unchanged files generated by the retired provisioner:

1. Resolve the selected consumer repository to a canonical root and confirm each candidate was
   created by an older Woostack Init. An exact byte match is required but is not, by itself, proof
   of ownership. Obtain the historical provisioner from a separately verified `howarewoo/woostack`
   checkout at pre-retirement commit `cb3bbdc5789677bef2628390361ec9aa42e4827a`; do not assume that
   commit exists in the consumer repository. If the trusted source is unavailable, preserve the
   files for manual review.
2. Generate expected bytes in a separate temporary directory whose absolute path is canonicalized
   before invoking the historical provisioner. Never run it against the consumer repository.
3. Reject symlinked consumer `.omp` or `agents` directories. Compare each candidate with `cmp` and
   remove only a regular, non-symlink `.omp/agents/woostack-{fast,standard,deep}.md` file whose bytes
   match exactly and whose generated provenance is confirmed. Skip missing, modified, malformed,
   user-authored, or symlinked files, and keep every other agent and configuration entry.
4. Leave `.omp/agents/.gitignore` and unrelated ignore entries unchanged unless a user has
   separately confirmed, by provenance rather than filename, that a standalone `woostack-*.md` line
   was generated by Woostack. Any ambiguous, modified, symlinked, or user-owned entry stays in place
   for manual review.

Repeating the comparison and removal is idempotent and never follows or deletes a symlink target.

For the exact dispatch mechanics, the conditional batch shape, and the retained session-naming
extension, see the
[canonical OMP adapter](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/omp.md).

## Goal-derived session naming

When a woostack skill is invoked, OMP uses a concise session title based on the user's input. For
`/woostack-prepare` and `/woostack-execute`, it uses the input goal; an issue-backed Execute
invocation may use its explicit goal or exact issue input. A Prepare continuation uses the exact
verified packet goal, never a guessed run title.

A local extension handles session naming inside OMP:

- `woostack-init` installs `.omp/extensions/woostack-session-name.ts`, adds standalone ignore
  rules in `.omp/.gitignore`, and adds the extension's explicit path to local `.omp/settings.json`
  while preserving other settings.
- The extension registers `woostack_rename_session`, which calls OMP's automatic session-naming
  API. A title you set explicitly with `/rename` takes precedence.
- If the extension is not loaded, extensions are disabled, or the tool call fails, woostack gives
  a concise warning and continues without changing the title.
- OMP loads project extensions and settings at startup. Restart OMP after installation or repair
  to load the extension. If `.omp/settings.json` is tracked by Git or malformed, provisioning stops
  without changing it to protect shared configuration.

## Plain packets and retained records

Prepare, Ideate, Harden, and Plan exchange complete plain packets. Plan publishes the selected native
GitHub graph directly; parent mode needs no Project configuration, local run, or second remote record.
Explicit Project mode remains available when Plan receives an exact Project selector. Historical
records under `.woostack/tmp/runs/<run-id>/` remain readable and are not migrated or rewritten.

Credentials stay in the host's secret store and never enter repository config, prompts, logs, or
generated output. The [direct publication and recovery contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md#direct-publication-and-recovery)
defines retained-data handling and GitHub recovery.

Retained records contain plain Markdown `project-spec.md` and `execution-plan.md` files plus a recovery
manifest. They are planning evidence only; Execute does not resume them or accept `--recheck`. To
continue, supply exact retained identity and complete content to the responsible phase, or select one
complete bounded task and supply `/woostack-execute <bounded input>` with its parent evidence. See
[Execute retired inputs](/docs/skills/woostack-execute#retired-inputs).

Saved records do not grant permission to assign workers, edit code, commit, review, or accept a
product. They also do not prove delivery. Prepare does not publish directly; Plan owns its GitHub
issue-graph publication. Goal-only Execute makes no remote calls and needs no planning-provider call.
An explicitly selected exact GitHub issue permits only its required read through an authorized GitHub
capability (native host tools preferred; host-authenticated `gh` supported), with no Project
configuration or issue lifecycle writes. Commit owns repository/PR delivery.

Bootstrap and Commit use direct GitHub operations only when explicitly requested: Project publication
after design approval and target collision checks for Bootstrap, or an exact issue association for
Commit. Each write requires a separate read to confirm its result. A GitHub note failure is reported
separately from repository delivery, and Git/GitHub remain authoritative for repository results.

## Recovery

Stop if the profile, working directory, worktree, branch, ancestry, or credentials no longer match
the verified task, or if process exit, verification, review, or submission results are incomplete
or conflicting. Preserve recoverable work and report the last safe point to resume. Never switch
profiles or worktrees silently, or claim results that a worker did not provide.
