OMP is a supported coding harness, the application that runs your agent and its tools.
Woostack uses agents already exposed by the active OMP session. Install woostack in OMP, even
when an external engineer such as Hermes coordinates the work; woostack does not install a second
agent catalog.

## Native OMP agent routing

OMP's `task` tool accepts a worker selector but no model, tier, effort, or per-call working-directory
setting. The current inventory exposes `task` as a write-capable general-purpose agent, `scout` as
read-only exploration, and `reviewer` / `security-reviewer` as read-only review. Discovery remains
authoritative: invoke only names actually exposed in the active session, and never create aliases or
project definitions to fill a missing name.

- Use a write-capable discovered agent for implementation and delivery; a read-only agent must not
  receive a write task.
- Pass the exact workspace, branch, parent/start SHA, allowed paths, authority limits, acceptance,
  required checks, smoke scenario, and result-evidence requirements in the task prompt. The `task`
  primitive does not accept `cwd`; the worker verifies the prompt-pinned workspace before editing.
- Execute remains one bounded task and does not schedule a project graph. Orchestrate requires a
  delivery-capable worker and blocks when the host cannot provide one.
- Eval dispatches candidate and baseline siblings through the same discovered worker only when the
  host can prove matching completion identity, model/session identity, tier, effort, isolation, and
  complete receipts. A selector alone never proves comparable execution; missing proof blocks the
  comparative run, with only the explicitly accepted candidate-only qualitative smoke path available.
- Missing capabilities and missing result evidence are reported as blockers. Woostack does not
  switch profiles, weaken isolation, or treat absent evidence as success.

## Previously generated agent definitions

Older installations may contain `.omp/agents/woostack-{fast,standard,deep}.md`. Init and Doctor
leave these user-owned files alone; their absence is normal. Optional cleanup is manual and must
positively identify unchanged generated bytes before removal. Resolve a canonical repository, use
the pre-retirement commit recorded by the host adapter as the source of expected bytes, generate
those bytes in a temporary directory, and compare with `cmp`. Remove only matching regular files;
preserve modified, unknown, user-authored, or symlinked files and every unrelated OMP setting or
ignore entry. Do not run a historical provisioner against the selected repository. Leave the
standalone `woostack-*.md` ignore line for manual review unless its provenance is independently
confirmed. Repeating the comparison is idempotent and never follows a symlink.

For the exact cleanup boundary and the retained session-naming extension, see the
[canonical OMP adapter](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/omp.md).

## Goal-derived session naming

When a woostack skill is invoked, OMP uses a concise session title based on the user's input. For
`/woostack-change`, `/woostack-build`, and `/woostack-fix`, it uses the input goal; an issue-backed
Change invocation may use its explicit goal or exact issue input. A resume-only Build or Fix uses the
exact verified run goal.

A local extension handles session naming inside OMP:

- `woostack-init` installs `.omp/extensions/woostack-session-name.ts`, adds standalone ignore
  rules in `.omp/.gitignore`, and adds the extension's explicit path to local `.omp/settings.json`
  while preserving other settings.
- The extension registers `woostack_rename_session`, which calls OMP's automatic session-naming
  API. A title you set explicitly with `/rename` takes precedence.
- If the extension is not loaded, extensions are disabled, or the tool call fails, woostack gives
  a concise warning and continues without changing the title.
- OMP loads project extensions and settings at startup. Restart OMP after installation or repair
  to load the extension. If `.omp/settings.json` is tracked by Git or malformed, provisioning stops
  without changing it to protect shared configuration.

## Local run artifacts and optional remote mirroring

Build and project-backed Fix save their authoritative planning records under
`.woostack/tmp/runs/<run-id>/`. By default, `artifacts.provider` is `"local"` or omitted and these
workflows make no provider calls. Selecting `"github"`, `"linear"`, or `"plane"` enables copies in
the configured provider; the local records remain authoritative.

Credentials stay in the host's secret store and never enter repository config, prompts, logs, or
generated output. The
[Local run artifact and provider mirror contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md)
defines storage, synchronization, and recovery.

The run contains plain Markdown `project-spec.md` and `execution-plan.md` files and a recovery
manifest. These records are retained on completion and abandonment. They are planning artifacts only;
Execute does not resume them or accept `--recheck`. To continue, the caller selects one complete
bounded task and supplies `/woostack-execute <bounded input>` with its parent evidence and exact
retained state. See [Execute retired inputs](/docs/skills/woostack-execute#retired-inputs).

Saved records do not grant permission to assign workers, edit code, commit, review, or accept a
product. They also do not prove delivery. Fix makes no provider call before proving the cause, and
goal-only Change never contacts an artifact provider. Issue-backed Change performs the required read of
the explicitly selected exact GitHub issue through host-authenticated `gh`; no artifact-provider
configuration or Project is required.

Bootstrap and Commit write optional provider records only when explicitly requested: persistence
after design approval and target collision checks for Bootstrap, or `--issue` for Commit.
They use the official interface for `artifacts.provider`: host-authenticated `gh` for GitHub,
or official Linear/Plane MCP tools. Each write requires a separate read to confirm its result.
Optional synchronization failures do not block repository work unless synchronization was
explicitly required as part of the deliverable.
Git and GitHub remain authoritative for repository results.

## Recovery

Stop if the profile, working directory, worktree, branch, ancestry, or credentials no longer match
the verified task, or if process exit, verification, review, or submission results are incomplete
or conflicting. Preserve recoverable work and report the last safe point to resume. Never switch
profiles or worktrees silently, or claim results that a worker did not provide.
