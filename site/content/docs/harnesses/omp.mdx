OMP is a supported coding harness, the application that runs your agent and its tools.
`woostack-init` creates project workers that OMP can use for delegated tasks. Install woostack
in OMP, even when an external engineer such as Hermes coordinates the work.

## Native OMP worker routing

OMP's `task` tool accepts a worker name but no model, tier, or effort setting for that individual
call. Woostack creates three general-purpose project workers that refer to OMP's model roles.
OMP chooses the models behind those roles and manages provider credentials, thinking level,
retries, and fallbacks. It ignores repository model settings.

- Run `woostack-init` before optional delegated work. If managed worker definitions are missing or
  changed, `woostack-doctor` can repair them after approval while preserving other project agents.
- Execute accepts one bounded task per invocation and may run inline or use an optional worker. It
  does not process a local run or dispatch a project graph.
- An optional worker receives the exact worktree and full task contract, including its allowed scope.
  The bounded Execute task owns evidence, commit, and PR delivery; an optional worker may implement
  within that contract but is not a required handoff.
- If the tool cannot set a working directory, the prompt must name the exact worktree and require
  the worker to verify it before reading or writing.

See OMP's published [model roles](https://omp.sh/docs/roles), [custom
subagents](https://omp.sh/docs/subagents), and the canonical
[host adapter](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/omp.md)
for the exact role mapping and worker lifecycle.

## Goal-derived session naming

When a woostack skill is invoked, OMP uses a concise session title based on the user's input. For
`/woostack-change`, `/woostack-build`, and `/woostack-fix`, it uses the input goal; an issue-backed
Change invocation may use its explicit goal or exact issue input. A resume-only Build or Fix uses the
exact verified run goal.

A local extension handles session naming inside OMP:

- `woostack-init` installs `.omp/extensions/woostack-session-name.ts`, adds standalone ignore
  rules in `.omp/.gitignore`, and adds the extension's explicit path to local `.omp/settings.json`
  while preserving other settings.
- The extension registers `woostack_rename_session`, which calls OMP's automatic session-naming
  API. A title you set explicitly with `/rename` takes precedence.
- If the extension is not loaded, extensions are disabled, or the tool call fails, woostack gives
  a concise warning and continues without changing the title.
- OMP loads project extensions and settings at startup. Restart OMP after installation or repair
  to load the extension. If `.omp/settings.json` is tracked by Git or malformed, provisioning stops
  without changing it to protect shared configuration.

## Local run artifacts and optional remote mirroring

Build and project-backed Fix save their authoritative planning records under
`.woostack/tmp/runs/<run-id>/`. By default, `artifacts.provider` is `"local"` or omitted and these
workflows make no provider calls. Selecting `"github"`, `"linear"`, or `"plane"` enables copies in
the configured provider; the local records remain authoritative.

Credentials stay in the host's secret store and never enter repository config, prompts, logs, or
generated output. The
[Local run artifact and provider mirror contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md)
defines storage, synchronization, and recovery.

The run contains plain Markdown `project-spec.md` and `execution-plan.md` files and a recovery
manifest. These records are retained on completion and abandonment. They are planning artifacts only;
Execute does not resume them or accept `--recheck`. To continue, the caller selects one complete
bounded task and supplies `/woostack-execute <bounded input>` with its parent evidence and exact
retained state. See [Execute retired inputs](/docs/skills/woostack-execute#retired-inputs).

Saved records do not grant permission to assign workers, edit code, commit, review, or accept a
product. They also do not prove delivery. Fix makes no provider call before proving the cause, and
goal-only Change never contacts an artifact provider. Issue-backed Change performs the required read of
the explicitly selected exact GitHub issue through the selected authorized GitHub capability (native
host tools where suitable or host-authenticated `gh`); no artifact-provider configuration or Project is
required.

Bootstrap and Commit write optional provider records only when explicitly requested: persistence
after design approval and target collision checks for Bootstrap, or `--issue` for Commit. They use the
authorized host capability for `artifacts.provider` (native GitHub tools where suitable or
host-authenticated `gh` for GitHub, or official Linear/Plane MCP tools). Each write requires a
separate read to confirm its result. Optional synchronization failures do not block repository work
unless synchronization was explicitly required as part of the deliverable.
Git and GitHub remain authoritative for repository results.

## Recovery

Stop if the profile, working directory, worktree, branch, ancestry, or credentials no longer match
the verified task, or if process exit, verification, review, or submission results are incomplete
or conflicting. Preserve recoverable work and report the last safe point to resume. Never switch
profiles or worktrees silently, or claim results that a worker did not provide.
