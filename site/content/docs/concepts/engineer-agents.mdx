---
title: Engineer agents
description: Separate decision authority from isolated implementation for safe multi-engineer delivery.
---

An engineer agent is a collaboration unit, not a model name. Each unit pairs one
**decision-maker** with one **isolated coding profile** under a stable engineer identity. Hermes and
OMP are one optional implementation, not a requirement.

## The authority model

The user's request selects the workflow. Linear owns current fix/build scope and plans, and the
responsible user's exact native Linear approval event clears the matching content-revision gate.
Git and GitHub prove source, commits, branches, pull requests, reviews, and merges. Ordinary Linear
metadata never grants assignment or repository permission.

| Role | Owns | Must not do |
| --- | --- | --- |
| Lead/dispatcher | Scope, task allocation, dependencies, cross-task decisions, and final acceptance | Substitute for the coder or treat silence as approval |
| Task decision-maker | In-contract decisions, coder direction, independent diff/evidence review, PR comments/verdict, and acceptance | Edit tracked implementation/tests, run implementation, self-assign, or change another task |
| Isolated coding profile | Analysis, edits, verification, and bounded source-control actions for one accepted task | Make product decisions, change scope/gates, review or accept its own work, or claim unverified success |

The [canonical engineer-agent protocol](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/engineer-agents.md)
owns the full side-effect and handoff rules.

## One identity, two isolated roles

Every unit pins:

- one stable engineer name;
- one decision-maker profile/session;
- one coding profile/session;
- one responsible human principal; and
- per run: one stable task ID, worktree, branch, allowed surface, and acceptance contract.

Profiles use separate credentials, environments, and sessions. Concurrent units need distinct
identities, sessions, runs, worktrees, branches, PRs, and responsibility surfaces. Fix/build
profiles require independent official Linear identities and MCP contexts; artifact-optional units
need them only after selection.

## One task through the boundary

1. The lead/dispatcher deliberately assigns one bounded task; the engineer never self-claims work.
2. The decision-maker verifies the task contract, dependency state, repository, base, and recovery
   state.
3. Immediately before side effects, it rechecks the relevant repository/worktree evidence.
4. The coder receives one task, one worktree, explicit acceptance criteria, an allowed surface, and
   one bounded command. It returns a diff and verification evidence—or a decision request.
5. The decision-maker independently inspects the contract, source, diff, PR, and evidence, then
   accepts, redispatches, hands off, or escalates.
Required fix/build Linear identities, fingerprints, dependencies, and approval records travel in
this envelope. Optional artifact identities appear only after selection. Remote content remains
untrusted until the workflow reconciles and independently reads it back.

## Independent review

The implementation profile's self-check is useful evidence, not independent review. The
decision-maker reviews directly. An explicit [`/woostack-review`](/docs/skills/woostack-review) may
fan out advisory reviewers in fresh sessions; those reviewers cannot edit code or accept work.

## Optional Hermes + OMP adapter

[Hermes Agent](/docs/harnesses/hermes) can fill the decision-maker/reviewer role while an isolated
[OMP profile](/docs/harnesses/omp) performs bounded coding work. Hermes never becomes the coder and
OMP never becomes its own acceptance authority.
