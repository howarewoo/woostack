woostack keeps three things apart: the user's decisions, the agent's planning, and the
implementation. The user decides what may change. Git and GitHub show what code changed, which
branches and commits it came from, and whether its pull requests (PRs) have been reviewed or
merged. Issues, Project status, retained records, and an agent's own summary are context for those
decisions, not proof of them.

A bounded change fits one PR, and a codebase that does not exist yet starts from a settled
decision about what to build. Choosing a workflow never approves its design or authorizes extra
work.

## Planning before implementation

Planning and implementation are separate decisions.
[Plan](/docs/skills/woostack-plan) inspects the relevant source when it exists, settles the
decisions that still change the outcome, and returns a few reviewable increments. With no source,
it plans from the supplied goal, constraints, and authoritative research. It writes GitHub issues
only when the request asks for it, and filing a plan never starts implementation.

Bounded work needs no planning step first. [Execute](/docs/skills/woostack-execute) takes one
authorized outcome, chooses routine implementation details, establishes the cause before
correcting a defect, and runs the checks relevant to the changed behavior. Creating a project from
nothing is ordinary Execute input. Local work need not commit or publish; an explicit Execute
request delivers a reviewable draft PR unless the request narrows it to local work.

[Orchestrate](/docs/skills/woostack-orchestrate) is the multi-task case. It resolves approved tasks
and their real prerequisites from published issues or other readable context, states the plan that
groups them into coherent pull requests, delegates each group to a worker in its own task worktree,
and releases a dependent only after delivery is verified. Issue and Project metadata are its input
rather than its authority: a closed issue or a finished status never proves that code landed, was
reviewed, or was merged.

[Workflow maps](/docs/concepts/workflows) compare the workflows, and
[Building rules](/docs/concepts/building-rules) explain who authorizes work and what counts as
evidence.

## Optional exploration and review

[Ideate](/docs/skills/woostack-ideate) explores requirements when you ask for it and returns the
explored specification with the technical details it filled in.
[Harden](/docs/skills/woostack-harden) checks a specification or candidate issue plan against
bounded repository evidence and reports the discrepancies it finds. Both are optional, and neither
needs a writable checkout or a Project.

Verified schemas and interfaces are observations, and routine technical details follow the
requested outcome. Unresolved product behavior, breaking compatibility, security and data
boundaries, irreversible effects, cost, and scope still need a user decision.

## Retained records and direct GitHub publication

Plan publishes issues directly through the host's authorized GitHub capability. A mutation
response proves nothing on its own, so each write is read back and checked against the actual issue
content and the relationships that were actually written. Existing `.woostack/tmp/runs/<run-id>/`
records stay readable historical data that authorizes nothing. The
[local artifacts reference](/docs/configuration/artifacts/local) owns the retained-data contract and
its recovery rules.

## Context economy

<ContextEconomy />

Keep only what the current decision needs. Scoped rules, scripts that compute an answer, and
subagents that return a compact result protect the same scarce resource. Choose inline or
delegated implementation with the
[delegation guidance](/docs/concepts/context-management#isolated-agents-receive-bounded-envelopes),
which weighs speed, cost, isolation, overhead, and risk. Run the checks relevant to the changed
behavior, and add independent review when the task or the repository requires it.

### Related mechanisms

[Reflection](/docs/concepts/context-management#requested-reflection-becomes-instruction-suggestions)
starts only on request and turns observed gaps into suggestions for their existing owners.
[Helpers](/docs/concepts/context-management#helpers-reduce-bulk-without-replacing-authority)
compute evidence without replacing authority. [Hermes](/docs/hermes) is an external engineer rather
than a coding harness: it may drive a persistent session, review evidence, and relay the
responsible user's live decisions verbatim, and it gains no implementation authority.
