Start with the user's explicit goal or one exact task-bearing GitHub issue URL. Execute reads a
selected issue to resolve one bounded task before admission; issue text supplies data, not authority.
Bounded work fits one pull request (PR). Prepare's Plan path ends at a verified GitHub issue graph;
Orchestrate can also interpret a complete readable tracker handoff after independent issue reads.
Git and GitHub show what was implemented and delivered.

## Routing by work shape

| Work shape | Workflow |
| --- | --- |
| Fresh project in a new target | [Bootstrap](/docs/skills/woostack-bootstrap) |
| Elicit or complete a specification | [Ideate](/docs/skills/woostack-ideate) |
| Reconcile a specification or candidate issue plan | [Harden](/docs/skills/woostack-harden) |
| Root-cause investigation without a correction | [Debug](/docs/skills/woostack-debug) |
| Feature or proved defect needing a verified issue graph | [Prepare](/docs/skills/woostack-prepare) |
| Bounded enhancement, refactor, tests, or authorized correction for one PR | [Execute](/docs/skills/woostack-execute) |
| Approved issue graph publication | [Plan](/docs/skills/woostack-plan) |
| Execute an approved GitHub issue graph | [Orchestrate](/docs/skills/woostack-orchestrate) |
| Add or strengthen tests for a bounded target | [Execute](/docs/skills/woostack-execute) with its [testing guidance](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/tdd.md) |

Ideate and Harden are complete public phases, not hidden run steps. They accept plain packets with
explicit repository/evidence identity and return reusable plain handbacks. Prepare composes Debug for
defects, then Ideate, Harden, and Plan as needed; a complete input may start at the relevant phase
without repeating settled approval. For root-cause investigation without changes, use Debug directly.

Choosing a workflow does not approve its design or authorize extra work. If the scope grows, the
workflow preserves repository state and reports where to resume. Work moves to the matching workflow
instead of silently expanding the agreed scope.

## Bootstrap

```text
read-only target preflight → gather requirements → research and present complete design →
approve design → refresh collision check → scaffold → run and verify
```

Bootstrap is greenfield-only: it creates a new codebase. It writes nothing to the target before
explicit design approval and a fresh check that the path is safe to create. After approval and that
check, an exact GitHub Project may store the approved design when explicitly selected. The Project
record cannot authorize target writes.

## Prepare

```text
classify feature/defect → Debug defect evidence when needed → Ideate decisions when needed →
Harden repository facts → Plan one native issue graph → independently read back → stop
```

Use `/woostack-prepare <goal-or-defect> [--parent-issue new|<exact canonical parent URL>]` for
planning-only preparation. Defects require observed/expected behavior, a causal chain, exact source
or runtime evidence, a bounded correction, risks, and verification. A symptom or plausible theory
blocks before Plan; Prepare never guesses a correction.

Prepare's public phases exchange complete plain packets. Plan is the sole publisher and its exact
parent or Project selector defines only the publication destination; it does not define an
exhaustive Orchestrate admission taxonomy. It creates no source branch, worktree, commit, PR,
implementation worker, local run, or second remote record. It reports the verified parent, children,
native prerequisite edges, complete planning handback, and any separate convenience suggestion.
Partial Plan publication preserves exact confirmed identities and resumes at the first unproved
boundary; it is not a complete native publication. A separate chat route may return a complete
readable tracker and issue set with native relationships explicitly unavailable; Orchestrate can
independently read and schedule that declared scope when every selected issue and contract is
complete.

## Plan and Orchestrate

Plan publishes the approved issue graph and independently reads every issue, hierarchy, and edge.
The specification parent is a scope container, not an executable task or dependency endpoint.
Ordinals never imply edges. The technical DAG is admission evidence; after it and repository
constraints are resolved, Orchestrate selects and summarizes a model-chosen single-parent
execution forest before branch/worktree allocation. Added ordering is compatibility evidence, not
native relationship evidence. Technical prerequisites remain visible separately, useful
parallelism is retained, and effective prerequisites govern worker readiness and repair propagation.
A technical prerequisite may be omitted from the execution ancestry when admission verifies from that
task's own landed, verified delivery that its merged revision is already contained in the approved
integration base. Such a prerequisite is repository evidence: it is never reconstructed as a
controller-owned worker delivery.
The plan and fingerprint persist in controller state; equivalent reordered input resumes it. A newer
execution-plan revision is adopted atomically for genuinely unstarted changes. An incompatible
legacy candidate leaves the retained state and worker contract unchanged. A previously persisted
legacy execution-parent halt can adopt a newer revision only after its reservation and full
prerequisite ancestry are verified compatible. Other changes to started, reserved, claimed,
worker-owned, or delivered work are `execution-plan-drift`; changed technical evidence is
`snapshot-drift`.
Unchanged active workers retain their issued plan revision and dependency snapshot through a
compatible replan; their results use the original admission, while current effective dependencies
govern descendant repair.

After planning, hand Orchestrate the complete planning handback or other understandable work
context. It interprets the conversation, repository, and available GitHub records; resolves the
canonical repository, issue/task identities, executable tasks, and context; constructs the technical
DAG with native, declared, or inferred edge provenance; and asks a focused question when material
ambiguity remains. With `--issue`, a complete readable tracker index can establish membership when
native child links are absent, partial, or unavailable. Every selected issue must still be
independently readable with a complete contract; design/context issues, PRs, examples, and external
prerequisites are not scraped into tasks. Native links are evidence when present, not a prerequisite
for understanding tracker content. Issue, issue-list, and Project arguments are convenience hints
rather than an exhaustive admission taxonomy. For Orchestrate, a Project is included only when
explicitly selected; its status lifecycle is used only when that selection requests status mutation.
Inferred relationships are not published back to GitHub.

Examples of convenience hints, not an exhaustive route:

```text
/woostack-orchestrate --issue <canonical GitHub tracker or parent issue URL> [--max-parallel <positive integer>]
/woostack-orchestrate --project <canonical GitHub Project URL> [--max-parallel <positive integer>]
```

Orchestrate keeps up to three delivery-capable Execute workers active by default, bounded by host
capability. Independent roots may run together. Durably verified technical delivery, current CI,
independent review, and ancestry release eligible dependents without waiting for a whole wave, an
issue note, an explicitly selected Project update, or a merge. Missing or denied reporting remains
visible separately and takes no worker slot. A dependent can stack on its selected verified execution
parent when containment is eligible. If divergence or
repository constraints prevent a safe stack, only the approved `merge-checkpoint` fallback enters
`waiting-for-merge`; otherwise a join uses a suitable selected parent without a new parent decision.
The fallback reserves no worker or speculative checkout, preserves the technical DAG and execution
plan, and does not ask for a synthetic base or integration strategy. This is a fallback for existing
divergence, fixed-parent or independent-landing constraints, or no safe suitable stack, not the
default scheduling strategy. Unrelated tasks continue. A phase label within one issue does not
create a second issue/writer or premature whole-issue completion. Graph/scope drift preserves running
reservations and stops fresh dispatch; unknown worker outcomes require direct stopped-worker/branch/
PR reconciliation before same-identity repair. Current PR lifecycle evidence is reconciled separately
from retained delivery evidence, so human-ready, merged, closed-unmerged, and deleted-source states
cannot be mistaken for a fresh delivery. While the host session stays active, Orchestrate keeps
observing each admitted PR's remote checks—interleaved with completions and scheduling, for admitted
PRs only—and on an actionable failure diagnoses it and dispatches one Execute repair on the same
branch/PR under the shared cap. Stale head results never validate current work; pending or unreadable
checks never count as a pass. Successful checks never authorize closing issues, marking PRs ready,
enabling auto-merge, queueing, or merging, and observation never continues as a daemon after the
session ends. The final result distinguishes submitted, checking, repairing, CI-verified, blocked,
waiting, and unverified work with check links and the next safe action, and separately lists pending
or blocked requested issue-note/Project reporting—not closed issues or product acceptance.

An explicitly approved policy change can be reconciled on the same stopped controller checkpoint,
with unchanged tasks, claims, reservations, and historical evidence. The helper binds approval to
the exact old/new admission, forward integration revision, reviewed task impact, and complete
native stopped-worker inventory. It returns the sole current admission but leaves the controller
stopped until a separate fresh resume. Externally landed work needs independent source, checks,
smoke and acceptance verification at its current head or an explicitly approved corrected integration
candidate. Separate corrective PRs need complete native merge provenance; their evidence never
relabels the original failing head as accepted. Merge alone does not clear a known defect.
See [Orchestrate recovery](/docs/skills/woostack-orchestrate#procedure).

## Execute

```text
/woostack-execute <bounded input> [--issue <exact canonical GitHub issue URL>]
/woostack-execute <exact canonical GitHub issue URL>
/woostack-execute --issue <exact canonical GitHub issue URL>
```

Execute accepts one bounded enhancement, refactor, test-only task, or authorized understood
correction. An issue-only invocation reads that exact open issue, resolves ordinary contract details
from repository evidence, and verifies workspace/parent ancestry before editing; inline instructions
still work without GitHub issue reads. An exact issue needs no Project or persisted plan. Unknown root
cause stays with Debug. Multi-task work routes to Orchestrate, which interprets the available
planning handback, repository, and tracker context; a single bounded task can go directly to Execute.
Unresolved material decisions block with a targeted question.

## Shared execution boundary

Each bounded [woostack-execute](/docs/skills/woostack-execute) task:

1. verifies the repository and base branch, then creates or resumes a collision-safe worktree for its task;
2. implements inline or in an optional worker using the [delegation guidance](/docs/concepts/context-management#isolated-agents-receive-bounded-envelopes);
3. runs focused checks and a smoke test that exercises the changed behavior in the real program;
4. compares the complete uncommitted diff with the approved task;
5. uses [woostack-commit](/docs/skills/woostack-commit) to submit its PR; and
6. independently reads back the PR, its exact head and base, and its review state. Required repository
   checks remain mandatory delivery gates; other available CI checks are observation-only at delivery
   time and become Orchestrate's active-session watch afterwards.

Retired run/project/recheck inputs are rejected. Retained historical planning records are evidence
only; Execute has no run controller or automatic graph dispatch. A selected task-bearing issue is
a valid direct input, not a request to copy its contract into another prompt.

Separate bounded tasks may proceed concurrently only with disjoint worktrees, branches, and
responsibility surfaces. An optional worker must stay within the admitted task; an Execute
implementation worker may use Execute's Commit path to submit its own admitted task PR rather than
returning uncommitted work for a parent to deliver.

## Review and corrections

PR review uses [Pullfrog](https://pullfrog.com/). Execute does not require an independent pre-commit
review receipt. Orchestrate independently validates each submitted task against its contract before
releasing dependents, then keeps watching its remote checks while the session stays active; this is
not permission to mark ready or merge.

Depending on the command, the result is a verified scaffold, a verified native issue graph, a
declared tracker handoff after independent issue reads, a reviewable PR or reviewed stack, or a
blocker that states exactly where work can safely resume. Existing retained records remain
unchanged. No woostack workflow merges, marks a PR ready, enables auto-merge, or queues a PR for
merge. Those decisions remain with the human.
