title: Workflow maps
description: "Choose planning, bounded delivery, or a complete greenfield workflow."
---

Start with the user's explicit goal or one exact task-bearing GitHub issue URL. Execute reads a
selected issue as context, not authority. Prefer coherent, reviewable pull requests (PRs); related
authorized issues can share delivery, and reviewability may call for a split unless the user fixed
the mapping. Plan returns a plan and publishes issues only when the request asks for it;
Orchestrate can also interpret other complete readable tracker context after independent issue
reads. Git and GitHub show what was implemented and delivered.

## Routing by work shape

| Work shape | Workflow |
| --- | --- |
| Fresh project in a new target | [Bootstrap](/docs/skills/woostack-bootstrap) |
| Elicit or complete a specification | [Ideate](/docs/skills/woostack-ideate) |
| Reconcile a specification or candidate issue plan | [Harden](/docs/skills/woostack-harden) |
| Root-cause investigation without a correction | [Debug](/docs/skills/woostack-debug) |
| Feature, proved defect, or requested issue filing | [Plan](/docs/skills/woostack-plan) |
| Bounded enhancement, refactor, tests, or authorized correction | [Execute](/docs/skills/woostack-execute) |
| Execute approved multi-task work | [Orchestrate](/docs/skills/woostack-orchestrate) |
| Add or strengthen tests for a bounded target | [Execute](/docs/skills/woostack-execute) with its [testing guidance](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/tdd.md) |

Ideate and Harden are optional standalone phases, not required Plan steps. Invoke
[Ideate](/docs/skills/woostack-ideate) to explore requirements and
[Harden](/docs/skills/woostack-harden) for a read-only review of a specification or candidate issue
plan against repository evidence. For root-cause investigation without changes, use Debug directly.

Choosing a workflow does not approve its design or authorize extra work. If the scope grows, the
workflow preserves repository state and reports where to resume. Work moves to the matching workflow
instead of silently expanding the agreed scope.

## Bootstrap

```text
read-only target preflight → gather requirements → research and present complete design →
approve design → refresh collision check → scaffold → run and verify
```

Bootstrap is greenfield-only: it creates a new codebase. It writes nothing to the target before
explicit design approval and a fresh check that the path is safe to create. After approval and that
check, an exact GitHub Project may store the approved design when explicitly selected. The Project
record cannot authorize target writes.

## Plan

```text
inspect relevant source → identify unresolved decisions → draft a coherent plan →
publish issues when the request asks for it → read back actual content and relationships → stop
```

Invoke `/woostack-plan <goal-or-specification>` with ordinary complete-enough context. A planning-only
request returns the plan and makes no GitHub writes. A request to file issues already supplies
publication intent: Plan then inspects the relevant existing issues, creates or reuses the
requested issues, and reads their actual content back. It resolves an unambiguous destination from
the request and its context, and asks one focused question when that destination is ambiguous. An
unknown defect cause stays with [Debug](/docs/skills/woostack-debug); Plan does not guess a
correction.

Issues carry useful outcomes, important constraints, acceptance and verification, and the real
dependencies between them. Plan uses native sub-issue and dependency links when they are available
and requested. When they are unavailable, the written issues and an explicit readable index are
preserved, the missing relationships are reported, and an explicitly required native graph is never
called complete. Plan creates no source branch, worktree, commit, PR, implementation worker, local
run, or second remote record. A partial publication keeps exact confirmed identities and resumes at
the first unproved step.

## Orchestrate

Orchestrate works from the published issues or other complete work context. The technical DAG is
admission evidence; execution order, concurrency, and each task's base are the coordinating agent's
own decisions, made when it starts that task.
Added ordering is compatibility evidence, not native relationship evidence. Technical prerequisites
remain visible separately, useful parallelism is retained, and verified delivery with current
readiness releases eligible dependents without waiting for a whole wave, an issue note, an
explicitly selected Project update, or a merge. A technical prerequisite already landed in the
approved integration base is repository evidence, read from current Git and PR facts rather than
reconstructed from a delivery claim.

After planning, hand Orchestrate the plan, the published issues, or other understandable work
context. It interprets the conversation, repository, and available GitHub records; resolves the
canonical repository, issue/task identities, executable tasks, and context; reads the real
dependencies with their native, declared, or inferred provenance; and asks a focused question only
when material ambiguity affects outcome, scope, or authority. An omitted administrative field is not
a blocker. With `--issue`, a complete readable tracker index can establish membership when native
child links are absent, partial, or unavailable. Every selected issue must still be independently
readable with a complete contract; design/context issues, PRs, examples, and external prerequisites
are not scraped into tasks. Issue, issue-list, and Project arguments are convenience hints rather
than an exhaustive admission taxonomy. A Project is included only when explicitly selected; its
status lifecycle is used only when that selection requests status mutation. Inferred relationships
are never published back to GitHub.

Examples of convenience hints, not an exhaustive route:

```text
/woostack-orchestrate --issue <canonical GitHub tracker or parent issue URL>
/woostack-orchestrate --project <canonical GitHub Project URL>
```

Orchestrate runs each ready task in a host or repository workspace, using the host's native task and
agent operations when the host has them and working inline when it does not. Independent tasks may
run together and there is no fixed worker count; a host without subagents works the same scope
sequentially and says so. Each task's base is selected when the task starts, and the required change
must be available there. A squash merge needs current Git and PR evidence, not an assumed ancestor.
A dependent can stack on a verified parent branch when containment is
eligible; when divergence or repository constraints prevent a safe stack, Orchestrate reports that
the task needs a human merge decision and unrelated work continues. No automatic integration branch,
combined branch, or graph rewrite is ever created.
A phase label inside one issue never creates a second issue, a second writer, or premature
whole-issue completion.

No two writers share one workspace. Before reusing a workspace, the run inspects native worker state
and current Git/PR facts; if an older writer may still be active, it stops that affected work,
because serializing behind a possibly live writer does not prove it stopped. Instructions and prompts
do not enforce sandboxing or locks, and the run never claims they do. An unknown worker outcome is
rediscovered from direct Git, PR, and host evidence before anything is repeated, so no duplicate
writer or duplicate PR is launched and recoverable work survives. Current PR lifecycle evidence is
read separately from delivery evidence, so human-ready, merged, closed-unmerged, and deleted-source
states are never mistaken for a fresh delivery. While the host session stays active, Orchestrate
uses the host's own completion and check events or bounded observation of the delivered PRs, fixes
actionable failures within scope and budget, and reuses finished work. Stale head results never
validate current work, pending or unreadable checks never count as a pass, and observation never
continues as a daemon after the session ends. The final result reports delivered work, evidence,
limitations, remaining tasks, and blockers. Pending or blocked issue-note and Project reporting
is listed separately. Missing reporting never invalidates valid code or counts as done.

There is no persisted execution forest, lock service, or cross-harness replay guarantee; a run that
needs old replay stays pinned to its pre-cutover version. See
[Orchestrate coordination](/docs/skills/woostack-orchestrate#coordinate).

## Execute

```text
/woostack-execute <bounded input> [--issue <exact canonical GitHub issue URL>]
/woostack-execute <exact canonical GitHub issue URL>
/woostack-execute --issue <exact canonical GitHub issue URL>
```

Execute accepts one authorized bounded enhancement, refactor, test task, or correction. An
issue-only invocation reads that exact issue and resolves ordinary implementation details from
repository evidence; inline instructions still work without issue reads. No Project or execution
record is required. A bug's cause is established from reproduction or adequate source/runtime
evidence before repair; a request solely for diagnosis stays read-only in Debug. Multi-task work
routes to Orchestrate, which interprets the published issues, repository, and other available
tracker context; a single bounded task can go directly to Execute. Unresolved material decisions
block with a targeted question.

## Shared execution boundary

Execute checks the selected workspace, base, and relevant Git/PR facts, implements inline or delegates,
inspects the task diff, and runs the repository checks relevant to changed behavior. An existing
targeted test can serve as its smoke; required checks and reviews cannot be silently waived.
[Commit](/docs/skills/woostack-commit) owns staging, native Git publication, and PR submission.
The exact matching PR is read back for its head, base, state, and preserved human text. New PRs are
drafts; an explicitly requested incomplete draft must say what remains unverified. Native stack
registration is conditional on an explicit request or repository workflow requirement, not on every
dependent branch; inability to register an explicitly required stack is reported separately from
verified code. Unknown writes require discovery before retrying.

Separate concurrent writers need independently owned workspaces. A possibly active prior writer
blocks reuse until its exit is established; an existing approved workspace need not be replaced.
Retired run/project/recheck inputs do not select executable scope, and historical planning records
remain unchanged. A task-bearing issue is valid direct context, not a request to copy its contract
into a separate template.

## Review and corrections

PR review uses [Pullfrog](https://pullfrog.com/). Execute does not require an independent pre-commit
review receipt. Orchestrate independently validates each submitted task against its contract before
releasing dependents, then keeps watching its remote checks while the session stays active; this is
not permission to mark ready or merge.

Depending on the command, the result is a verified scaffold, a plan with the issues it published,
a reviewable PR or reviewed stack, or a blocker that states exactly where work can safely resume.
Existing retained records remain unchanged. No woostack workflow merges, marks a PR ready, enables
auto-merge, or queues a PR for merge. Those decisions remain with the human.
