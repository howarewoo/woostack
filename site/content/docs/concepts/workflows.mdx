title: Workflow maps
description: "Choose preparation, bounded delivery, or a complete greenfield workflow."
---

Start with the user's explicit goal. Change may also take an exact canonical GitHub issue URL as
explicit issue-backed input. Bounded work fits one pull request (PR) and uses the agreed scope in the
current conversation. Prepared work ends at a verified GitHub issue graph. Git and GitHub show what
was implemented and delivered.

## Routing by work shape

| Work shape | Workflow |
| --- | --- |
| Fresh project in a new target | [Bootstrap](/docs/skills/woostack-bootstrap) |
| Elicit or complete a specification | [Ideate](/docs/skills/woostack-ideate) |
| Reconcile a specification or candidate issue plan | [Harden](/docs/skills/woostack-harden) |
| Root-cause investigation without a correction | [Debug](/docs/skills/woostack-debug) |
| Feature or proved defect needing a verified issue graph | [Prepare](/docs/skills/woostack-prepare) |
| Bounded non-bug work for one coherent PR | [Change](/docs/skills/woostack-change) |
| Approved issue graph publication | [Plan](/docs/skills/woostack-plan) |

Ideate and Harden are complete public phases, not hidden run steps. They accept plain packets with
explicit repository/evidence identity and return reusable plain handbacks. Prepare composes Debug for
defects, then Ideate, Harden, and Plan as needed; a complete input may start at the relevant phase
without repeating settled approval. For root-cause investigation without changes, use Debug directly.

Choosing a workflow does not approve its design or authorize extra work. If the scope grows, the
workflow preserves repository state and reports where to resume. Work moves to the matching workflow
instead of silently expanding the agreed scope.

## Bootstrap

```text
read-only target preflight → gather requirements → research and present complete design →
approve design → refresh collision check → scaffold → run and verify
```

Bootstrap is greenfield-only: it creates a new codebase. It writes nothing to the target before
explicit design approval and a fresh check that the path is safe to create. After approval and that
check, an exact Linear, Plane, or GitHub project may store the approved design when selected. The
project record cannot authorize target writes.

## Prepare

```text
classify feature/defect → Debug defect evidence when needed → Ideate decisions when needed →
Harden repository facts → Plan one native issue graph → independently read back → stop
```

Use `/woostack-prepare <goal-or-defect> [--parent-issue new|<exact canonical parent URL>]` for
planning-only preparation. Defects require observed/expected behavior, a causal chain, exact source
or runtime evidence, a bounded correction, risks, and verification. A symptom or plausible theory
blocks before Plan; Prepare never guesses a correction.

Prepare's public phases exchange complete plain packets. Plan is the sole publisher and supports one
exact GitHub parent selector or one exact Project selector. It creates no source branch, worktree,
commit, PR, implementation worker, local run, or provider mirror. It reports the verified parent,
children, native prerequisite edges, and the separate next suggestion:
`/woostack-orchestrate --issue <verified-parent-url>` (or the applicable Project command).
Partial publication preserves exact confirmed identities and resumes Plan at the first unproved
boundary; it is not Orchestrate-ready.

## Plan and Orchestrate

Plan publishes the approved issue graph and independently reads every issue, hierarchy, and edge.
The specification parent is a scope container, not an executable task or dependency endpoint.
Ordinals never imply edges. A join without one verified parent containing every prerequisite remains a
valid plan with an explicit execution-time integration decision.

```text
/woostack-orchestrate --issue <canonical GitHub parent issue URL> [--max-parallel <positive integer>]
/woostack-orchestrate --project <canonical GitHub Project URL> [--max-parallel <positive integer>]
```

Orchestrate is a separate explicit command. Select exactly one scope. The specification parent with
native PR-sized children needs no Project or provider-mirror configuration; explicit Project execution
retains its configured membership and lifecycle checks. Orchestrate keeps up to three
 delivery-capable Execute workers active by default, bounded by host capability. Verified submission
and independent specification validation release dependents without waiting for a whole wave or a
merge. A dependent PR targets its verified prerequisite branch; a join pauses if no permitted single
parent contains all prerequisite changes. The final result is submitted PRs awaiting review/merge,
not closed issues or product acceptance.

## Change

```text
classify → scope → repository preflight → execute → verify → review → hand back
```

Change handles one bounded non-bug enhancement/refactor and has no hard approval gate. It accepts a
goal-only request or an exact canonical GitHub issue input; either path still requires one coherent
PR boundary, verification, smoke testing, and review. The goal-only path makes no artifact-provider
calls. The issue-backed path performs the required read of the selected issue through host-authenticated
`gh`; it requires no artifact-provider configuration, Project, mirror, or persisted plan.

```text
/woostack-change <goal>
/woostack-change [<goal>] --issue <exact canonical GitHub issue URL>
```

## Shared execution boundary

Each bounded [woostack-execute](/docs/skills/woostack-execute) task:

1. verifies the repository and base branch, then creates or resumes a collision-safe worktree for its task;
2. implements inline or in an optional worker using the [delegation guidance](/docs/concepts/context-management#isolated-agents-receive-bounded-envelopes);
3. runs focused checks and a smoke test that exercises the changed behavior in the real program;
4. compares the complete uncommitted diff with the approved task;
5. uses [woostack-commit](/docs/skills/woostack-commit) to submit its PR; and
6. independently reads back the PR, its exact head and base, and its review state. Required repository
   checks remain mandatory delivery gates; other available CI checks are observation-only.

Retired run/project/recheck inputs are rejected. A retained historical planning record is evidence
only and must be converted by supplying one complete bounded task contract; Execute has no run
controller or automatic graph dispatch.

Separate bounded tasks may proceed concurrently only with disjoint worktrees, branches, and
responsibility surfaces. An optional worker must stay within the admitted task; an Execute
implementation worker may use Execute's Commit path to submit its own admitted task PR rather than
returning uncommitted work for a parent to deliver.

## Review and corrections

Local Review uses one reviewer across all relevant concerns for bounded low-risk changes and
specialists for broader or riskier changes. An independent adjudicator checks each proposed finding
against the evidence. CI and audit keep specialist coverage. Review receipts record what was checked
and bind the result to the exact source.

Address-comments investigates every thread, batches coherent corrections and verification, then
replies and resolves each thread independently. Unsafe decisions stay open without discarding
independent safe work.

## Terminal outcomes

Depending on the command, the result is a verified scaffold, a verified issue graph, a reviewable PR
or reviewed stack, or a blocker that states exactly where work can safely resume. Existing retained
records remain unchanged. No woostack workflow merges, marks a PR ready, enables auto-merge, or queues
a PR for merge. Those decisions remain with the human.
