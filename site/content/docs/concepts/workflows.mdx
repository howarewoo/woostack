Start with the user's explicit goal. Bounded Execute also accepts one exact canonical GitHub issue URL
as explicit issue-backed input. Bounded work fits one pull request (PR) and uses the agreed scope in
the current conversation. Project-backed work keeps a local specification and ordered plan, with
optional copies in a provider. Git and GitHub show what was implemented and delivered.

## Routing by work shape

| Work shape | Workflow |
| --- | --- |
| Fresh project in a new target | [Bootstrap](/docs/skills/woostack-bootstrap) |
| Elicit or complete a specification | [Ideate](/docs/skills/woostack-ideate) |
| Reconcile a specification or candidate issue plan | [Harden](/docs/skills/woostack-harden) |
| Bug or regression to fix | [Fix](/docs/skills/woostack-fix) |
| Bounded enhancement, refactor, test-only task, or authorized understood correction | [Execute](/docs/skills/woostack-execute) |
| Coordinated feature requiring a complete specification and plan | [Build](/docs/skills/woostack-build) |
| Add or strengthen tests for a bounded target | [Execute](/docs/skills/woostack-execute) with its [testing guidance](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/tdd.md) |

Ideate and Harden are complete public phases, not hidden run steps. They accept plain packets with
explicit repository/evidence identity and return reusable plain handbacks. Build and project-backed
Fix may compose those phases through their own retained records, but no run, provider mirror, or
wrapper admission is required for direct use. For root-cause investigation without changes, use
[Debug](/docs/skills/woostack-debug).

Choosing a workflow does not approve its design or authorize extra work. If the scope grows, the
workflow preserves repository state and reports where to resume. Work then moves to the matching
workflow instead of silently expanding the agreed scope.

## Bootstrap

```text
read-only target preflight → gather requirements → research and present complete design →
approve design → refresh collision check → scaffold → run and verify
```

Bootstrap is greenfield-only: it creates a new codebase. It writes nothing to the target before
explicit design approval and a fresh check that the path is safe to create. After approval and
that check, an exact Linear, Plane, or GitHub project may store the approved design when selected.
The project record cannot authorize target writes.

Validate a user-specified stack directly. Compare alternatives when an unresolved material tradeoff
requires a choice; a stack preference is not approval of the complete design.

## Build

```text
allocate/resume local run and admit baseline (if a remaining provider path needs it) → adapt plain
input to public Ideate → adapt its complete handback to public Harden → write `project-spec.md`
(and any remaining bounded Linear/Plane mirror sync) → for GitHub scope, invoke Plan's public
Harden-backed direct publisher and read back the issue graph; for remaining provider paths, use their
transitional procedure → write `execution-plan.md` → retain run artifacts → verified
`Stop here`/`Execute`/`Abandon` handoff
```

The user verifies the complete specification, including technical details, through Ideate and Harden.
Those public phases can also run independently without Build or Fix. An increment is a piece of the
plan that fits one independently reviewable PR. Each increment records its outcome, scope,
acceptance criteria, verification, risks, prerequisites, and Git parent-selection policy.

The [artifact contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md)
owns local run storage and optional provider profiles. Run IDs remain exact, artifacts are retained,
and mirror failures do not replace or invalidate local authority. Build stops before automatic Execute
dispatch; the caller supplies one selected complete bounded task to Execute.

## Fix

```text
reproduce → prove cause → admit writable target → choose bounded or project-backed delivery
```

For an understood one-PR fix, present the complete diagnosis, correction, technical consequences,
and verification for explicit approval. Then implement, verify, independently review, and submit the
PR through the shared [bounded-delivery contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-fix/references/bounded-delivery.md).
No project manifest or artifact-provider call is needed.

Multi-increment or materially uncertain fixes, explicit project/run context, explicitly required
provider context, and requested coordinated persistence use the project-backed Build sequence. A
configured provider alone does not force that route. Source issues provide context; they do not become
execution plans or grant permission.

### Project-backed handoff

Build and project-backed Fix display the complete verified artifacts, run and task identities,
dependencies, parent branch/tip, optional mirror status, and retained artifact paths, then stop.
The user may stop, execute, or abandon in natural language. On `Execute`, the caller must select one
complete bounded task and supply it to [woostack-execute](/docs/skills/woostack-execute#retired-inputs);
there is no automatic dispatch. Ambiguous responses ask again; material scope changes return to
explicit verification. The [Build handoff](/docs/skills/woostack-build#verified-handoff) owns the
detailed transition and recovery rules.

GitHub planning supports [prerequisite DAGs and parent-issue hierarchy](/docs/configuration/artifacts/github#identities-hierarchy-and-graph).
Plan selects exactly one `--project` (explicit Project membership) or `--parent-issue new` or an
exact parent issue URL (native parent/child issues). Parent mode needs only the exact canonical
repository and native relationship capabilities; it needs no provider selector, Project, mirror, or
Build/Fix run. Direct and composed Plan use one Harden reconciliation and one publisher. A caller may
select one task for [bounded Execute admission](/docs/skills/woostack-execute#admit-one-task), or
explicitly invoke [Orchestrate](/docs/skills/woostack-orchestrate) for a GitHub scope. Execute does
not dispatch graphs.

## Orchestrate

```text
/woostack-orchestrate --issue <canonical GitHub parent issue URL> [--max-parallel <positive integer>]
/woostack-orchestrate --project <canonical GitHub Project URL> [--max-parallel <positive integer>]
/woostack-orchestrate --issues <canonical issue URL> <canonical issue URL> ... [--max-parallel <positive integer>]
```

Select exactly one scope family. The recommended ChatGPT-to-Codex handoff remains a specification
parent with native PR-sized children; this mode needs no Project or provider-mirror configuration.
Explicit Project execution retains its configured membership and lifecycle checks. Explicit list
execution reads exactly the supplied open issues, normalizes repeated/reordered URLs, and validates
complete contracts plus a supplied dependency DAG. Native, declared, and model-inferred edges keep
separate provenance/evidence; inference belongs to the skill, not the deterministic helper, and
inferred relationships are never published back to GitHub. External prerequisites block only their
affected tasks and never expand the list.

Orchestrate keeps up to three delivery-capable Execute workers active by default, bounded by host
capability. Verified submission and independent specification validation release dependents without
waiting for a whole wave or a merge. A dependent PR targets its verified prerequisite branch; a join
pauses if no permitted single parent contains all prerequisite changes. Unrelated tasks continue.
Graph/scope drift preserves running reservations and stops fresh dispatch; unknown worker outcomes
require direct stopped-worker/branch/PR reconciliation before same-identity repair. The final result
is submitted PRs awaiting review/merge, not closed issues or product acceptance.


## Execute

```text
/woostack-execute <bounded input> [--issue <exact canonical GitHub issue URL>]
```

Execute accepts one complete bounded enhancement, refactor, test-only task, or authorized
understood correction. It needs no parent issue, Project, planning provider, or persisted plan; an
exact issue is optional and read-only. Unknown root cause, unresolved scope, or work that needs
multiple increments stays at Debug/Fix or the applicable planning workflow.

## Shared execution boundary

> **Retired automatic handoff.** Build and project-backed Fix stop at retained artifacts; the caller
> selects one complete bounded task and supplies it to
> [woostack-execute](/docs/skills/woostack-execute#retired-inputs). Automatic Build/Fix-to-Orchestrate
> handoff remains separate from an explicit Orchestrate invocation.

Each bounded [woostack-execute](/docs/skills/woostack-execute) task then:

1. verifies the repository and base branch, then creates or resumes a collision-safe worktree for its task;
2. implements inline or in an optional worker using the [delegation guidance](/docs/concepts/context-management#isolated-agents-receive-bounded-envelopes);
3. runs focused checks and a smoke test that exercises the changed behavior in the real program;
4. compares the complete uncommitted diff with the approved task;
5. uses [woostack-commit](/docs/skills/woostack-commit) to submit its PR; and
6. independently reads back the PR, its exact head and base, and its review state. Required repository
   checks remain mandatory delivery gates; other available CI checks are reported for observation, and
   their result or availability alone does not block delivery.

Separate bounded tasks may proceed concurrently only with disjoint
worktrees, branches, and responsibility surfaces. An optional worker must stay within the admitted
task; a workflow that owns delivery retains its normal boundaries, while an Execute implementation
worker may use Execute's Commit path to submit its own admitted task PR rather than returning
uncommitted work for a parent to deliver.

## Review and corrections

Local Review uses one reviewer across all relevant concerns for bounded low-risk changes and
specialists for broader or riskier changes. An independent adjudicator checks each proposed finding
against the evidence. CI and audit keep specialist coverage. Review receipts record what was checked
and bind the result to the exact source.

Address-comments investigates every thread, batches coherent corrections and verification, then
replies and resolves each thread independently. Unsafe decisions stay open without discarding
independent safe work.

## Terminal outcomes

Depending on the command, the result is a verified scaffold, a reviewable PR or reviewed stack,
an approved handoff before implementation, or a blocker that states exactly where work can safely
resume. Explicit abandonment preserves recoverable work and any retained run artifacts.

No woostack workflow merges, marks a PR ready, enables auto-merge, or queues a PR for merge.
Those decisions remain with the human.
