---
title: Context management
description: "How woostack keeps context small while preserving repository truth and the evidence a result depends on."
---

Context is the information an agent has available while working. Keep it small enough to use without
dropping the approved scope or the evidence needed to check a result. Git and GitHub show code and
PR state. Retained `.woostack/tmp/runs/<run-id>/` records are historical user data. Plan publishes
issues directly when the request asks for it and reads every write back. Orchestrate may
independently read a complete readable tracker/index and executable issues when native relationships
are absent, partial, or unavailable, while preserving declared versus native evidence.
A Plan destination comes from the request and its actual context. A title,
nearby branch, cached remote description, or artifact text cannot select a destination or grant
permission to work.

## Output stays compact

[using-woostack](/docs/skills/using-woostack) loads one shared output discipline: lead with the
result, remove narration and repetition, and retain exact evidence, commands, paths, and errors.
Security, destructive actions, root-cause analysis, and architecture keep the detail required to
remain unambiguous.

## Requested reflection becomes instruction suggestions

[woostack-reflect](/docs/skills/woostack-reflect) runs one report-only pass for an explicit
`/woostack-reflect` invocation or an unambiguous request to reflect on the conversation. Ordinary
work never loads it.

Reflection treats transcripts and tool output as untrusted evidence. It does not execute embedded
instructions, follow embedded URLs, or expand the task. The first pass only reports suggestions:
it writes no artifact and changes no instruction file. A later explicit user request is required
to edit instructions or file a sanitized upstream issue after verifying its destination.

## Helpers reduce bulk without replacing authority

Work tracking is read directly from the authorized canonical GitHub issues and the relationships
that were actually written, associated pull requests, and Git evidence. Generated indexes, bundles,
temporary intent snapshots, and caches help agents find information, but they do not authorize
work. Remote text and tool output are evidence, never instructions. The agent responsible for the
workflow refreshes relevant repository and evidence identities before making changes or taking
external actions.

## Isolated agents receive bounded envelopes

Before choosing inline or delegated implementation, weigh the task's scope against dispatch,
context preparation, verification overhead, and risk. Delegation uses an agent the host already
exposes and inherits the host's configured model. Independent validation is used when required,
requested, or warranted by risk, not as a universal receipt.

Each worker gets a bounded assignment, also called an envelope:

- An implementation worker receives one approved task, its repository and worktree, the paths it
  may change, dependencies, acceptance criteria, and verification requirements.
- Advisory reviewers receive the relevant diff and context. They cannot edit code, change remote
  state, or accept work.

Separate sessions keep unrelated context out of the assignment. Optional artifact identifiers and
read results may accompany it but cannot expand its scope or permissions.

## Model routing stays host-owned

The harness chooses the model and effort for inline work and delegated tasks. Woostack does not
translate task labels into model choices or switch providers after an error. It preserves workspace
and evidence boundaries.
