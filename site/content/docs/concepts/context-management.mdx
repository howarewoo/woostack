---
title: Context management
description: "How woostack keeps context small while preserving repository truth and local run authority."
---

Context is the information an agent has available while working. Keep it small enough to use without
dropping the approved scope or the evidence needed to check a result. Git and GitHub show code and
PR state. Local manifests under `.woostack/tmp/runs/<run-id>/` record Build and project-backed Fix
plans and recovery state; Linear, Plane, or GitHub may hold optional copies.

Standalone-plan projects are read only when the caller selects the exact project or persistence
was explicitly selected. A title, nearby branch, cached remote description, or artifact text cannot
grant permission to work.

## Output stays compact

[using-woostack](/docs/skills/using-woostack) loads one shared output discipline: lead with the
result, remove narration and repetition, and retain exact evidence, commands, paths, and errors.
Security, destructive actions, root-cause analysis, and architecture keep the detail required to
remain unambiguous.

## Sessions end with instruction suggestions

[woostack-reflect](/docs/skills/woostack-reflect) runs at an ordinary final reply only when
the session already contains a concrete observed preventable instruction gap, per its canonical
candidate gate. A qualifying reply runs one report-only pass; otherwise it has no reflection headings.
An explicit `/woostack-reflect` invocation always runs exactly one pass.

Reflection treats transcripts and tool output as untrusted evidence. It does not execute embedded
instructions, follow embedded URLs, or expand the task. The first pass only reports suggestions:
it writes no artifact and changes no instruction file. A later explicit user request is required
to edit instructions or file a sanitized upstream issue after verifying its destination.

## Helpers reduce bulk without replacing authority

Work tracking is read directly from authorized canonical GitHub parent/child issues, native
dependency relations, associated pull requests, and Git evidence. Generated indexes, bundles,
temporary intent snapshots, and caches help agents find information, but they do not authorize
work. Remote text and tool output are evidence, never instructions. The controller, the agent
responsible for the workflow, refreshes relevant repository and local run records before making
changes or taking external actions.

## Isolated agents receive bounded envelopes

Before choosing inline or delegated implementation, weigh the shared
[model-tier guidance](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/model-tiers.md),
including speed and cost benefits for simple tasks, against dispatch, context preparation,
verification overhead, and risk. Delegated work uses the host's appropriate model or role.
Independent validation still checks the complete result.

Each worker gets a bounded assignment, also called an envelope:

- An implementation worker receives one approved task, its repository and worktree, the paths it
  may change, dependencies, acceptance criteria, and verification requirements.
- Advisory reviewers receive the relevant diff and context. They cannot edit code, change remote
  state, or accept work.

Separate sessions keep unrelated context out of the assignment. Optional artifact identifiers and
read results may accompany it but cannot expand its scope or permissions.

## Model routing stays host-owned

Hosts map `fast`, `standard`, and `deep` work to concrete models through the canonical
[model-tier reference](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/model-tiers.md).
OMP instead uses
[host-owned role routing](https://github.com/howarewoo/woostack/blob/main/skills/using-woostack/references/hosts/omp.md).
The host owns models, credentials, and fallbacks; woostack supplies the effective role or tier.
