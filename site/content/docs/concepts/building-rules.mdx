title: Building rules
description: Planning, optional issue publication, and bounded one-PR execution routes.

The user decides the product and authorizes work. Git and GitHub show what was delivered.
Plan plans a change and publishes GitHub issues only when the request asks for it; Orchestrate may
also consume a complete readable tracker and independently read its executable issues when native
relationship metadata is absent, partial, or unavailable. Implementation remains a separate
explicit workflow.

## Workflow scope

| Shape | Commands | Active contract | Provider/input behavior |
| --- | --- | --- | --- |
| Feature, proved defect, or requested issue filing | [woostack-plan](/docs/skills/woostack-plan) | outcomes, important constraints, acceptance and verification, and real dependencies; GitHub issues written only when the request asks for them | direct host-authenticated GitHub reads/writes only for a requested publication; no mirror required |
| Requested requirements exploration | [woostack-ideate](/docs/skills/woostack-ideate) | the user's decisions and open questions | no provider or run required |
| Requested read-only specification or issue-plan review | [woostack-harden](/docs/skills/woostack-harden) | reconciled content after bounded evidence checks | no provider or run required |
| Bounded enhancement, refactor, tests, or authorized correction | [woostack-execute](/docs/skills/woostack-execute) | one complete bounded contract from inline input or one canonical task-bearing issue, and one PR | goal-only is provider-free; an exact issue is read-only task input and Commit association |
| Greenfield codebase | [woostack-bootstrap](/docs/skills/woostack-bootstrap) | complete approved design | exact target only; direct GitHub Project publication is explicit |

The shape of the work determines the workflow. Historical development records cannot turn ambiguous
scope into a complete contract or replace direct repository evidence.

## Planning and informed approval

[Plan](/docs/skills/woostack-plan) is the complete planning workflow. It inspects the relevant
source, identifies the decisions that still matter, and returns a coherent plan. A planning-only
request makes no GitHub writes. A request to file issues already supplies publication intent, so
Plan resolves an unambiguous destination from the request and its context, inspects the relevant
existing issues, creates or reuses the requested issues, and reads their actual content and
relationships back. It asks one focused question when the destination is ambiguous. An unknown
defect cause stays with [Debug](/docs/skills/woostack-debug); Plan does not guess a correction.

Native sub-issue and dependency links are used when they are available and requested. When that
capability is unavailable, the written issues and an explicit readable index are preserved, the
missing relationships are reported, and an explicitly required native graph is never called
complete. A partial publication keeps exact confirmed identities and resumes at the first unproved
step. It creates no branch, worktree, commit, PR, worker, local run, or second remote record.

[Ideate](/docs/skills/woostack-ideate) and [Harden](/docs/skills/woostack-harden) are optional
standalone phases. Ideate explores requirements when the user asks for it; Harden performs a
read-only review of a specification or candidate issue plan against bounded repository evidence and
raises each material discrepancy. Verified schemas and interfaces are observations, and routine
technical details follow the requested outcome. Unresolved product behavior, breaking
compatibility, security and data boundaries, irreversible effects, cost, and scope still need a
user decision.

Execute accepts one selected bounded task under its [admission contract](/docs/skills/woostack-execute#admit-one-task), not a whole plan.
An explicit [Orchestrate](/docs/skills/woostack-orchestrate) invocation interprets the plan, the
published issues, or other understandable work context. It resolves the canonical repository,
issue/task identities, executable tasks, and real dependencies with provenance, then chooses the
execution order, concurrency, and each task's base when it starts that task. Added ordering is
compatibility evidence, not native relationship evidence; technical prerequisites remain visible
separately and useful parallelism is retained. A task whose own landed, verified delivery is already
contained in the approved integration base is satisfied evidence, not an imported worker delivery,
and the same holds for verified landed prerequisites outside the selected issue set: they remain
recorded external dependencies, not imported tasks, and their issue, merge, diff, checks, and exact
base containment stay in the handoff without creating an external claim, worker, or PR.
Issue, issue-list, and Project arguments are convenience hints, not an exhaustive admission taxonomy;
a complete tracker index can establish declared membership without native links,
while every selected issue and contract still needs independent reads. A Project is included only
when explicitly selected; its status lifecycle is used only when that selection requests status
mutation, and inferred edges are not published.

Plan independently reads back the identity and content of every issue it publishes, plus any
relationship it actually wrote. A readable index with independently readable issues can still be
read and coordinated by Orchestrate when its selected issues and contracts are complete. Plan may
suggest `/woostack-orchestrate --issue <exact canonical GitHub issue URL>`, but it never invokes it.

## Execution invariants

- Each increment fits at most one PR.
- Execute takes one complete bounded task per invocation: pass inline bounded input, one canonical
  task-bearing issue URL, or inline instructions with an optional exact canonical GitHub issue URL.
  Retired `--run`, `--project`, and `--recheck` inputs are rejected (see
  [Execute](/docs/skills/woostack-execute#retired-inputs)).
- Each bounded task runs its own worktree, branch, allowed paths, and PR. Separate tasks may proceed
  concurrently only when their paths, branches, worktrees, PRs, and responsibilities do not overlap.
- Focused checks, a smoke test of changed behavior, and comparison against the approved task precede
  delivery. Orchestrate verifies each delivered task and its current PR head before releasing
  dependents, and works sequentially when the host has no delivery-capable subagent.
- Git and GitHub prove parent-child branch relationships, PRs, commits, reviews, and merge state.
  Required repository checks remain mandatory delivery gates; non-required available CI checks are
  observation-only.
- Unresolved scope, ancestry, collision, required-evidence, or review conflicts stop the workflow.
  Agents never merge, mark a PR ready, enable auto-merge, or queue a PR for merge.

## Retained records and authority boundaries

Existing `.woostack/tmp/runs/<run-id>/` artifacts from retired planning wrappers remain readable
historical user data and are never migrated or mutated. A supplied record is evidence only after exact
identity, complete content, and freshness validation. It does not authorize publication, assignment,
implementation, or ownership. Legacy managed-provider records remain opaque; direct GitHub publication
uses only its exact selected scope.

| Surface | Authority |
| --- | --- |
| Planning content from Plan, Ideate, or Harden | plans, user decisions, and evidence; no source or issue authority |
| Plan's published issues | verified issue identities and content, plus only the relationships actually read back |
| Git and GitHub | source, ancestry, commits, PRs, checks, reviews, merge evidence |
| Audit, QA, response reports | sanitized non-authoritative diagnostic evidence |

The [Hermes guide](/docs/hermes) documents how an external engineer can review harness evidence
without receiving implementation authority.
