title: Building rules
description: The three-gate build loop, bounded one-PR routes, and explicitly selected Linear plan persistence.
---

Woostack separates workflow authority from durable artifacts. The user's request and explicit gates
authorize work. Git and GitHub own source, branches, commits, pull requests, reviews, and merge
evidence. Linear plan projects record approved fix/build/standalone plans only after caller
selection and never grant repository permission.

## Choose the smallest workflow

| Shape | Commands | Active contract | Linear behavior |
| --- | --- | --- | --- |
| Bounded bug or regression | [woostack-fix](/docs/skills/woostack-fix) | proven root cause plus one approved fix contract | selected persistence → project, parent plan issue, one increment child |
| Bounded non-bug change | [woostack-change](/docs/skills/woostack-change) | one explicit goal/contract | none |
| Multi-increment feature | [woostack-build](/docs/skills/woostack-build) | approved specification plus dependency-aware plan | selected persistence → project, parent plan issue, one child per increment |
| Greenfield codebase | [woostack-bootstrap](/docs/skills/woostack-bootstrap) | complete approved design | exact artifact or explicit persistence request only |

Route by work shape, not artifact availability. A project or issue never turns ambiguous work into an
approved contract.

## The three-gate build loop

Multi-increment work follows one fixed chain:

```text
ideate → approve design → harden specification → approve specification →
delegate candidate planning without provider mutation → harden increment graph →
persist one selected Linear hierarchy once → approve execution → execute → review → hand back
```

The only hard gates are:

1. **Design approval** — freezes the complete product/technical design.
2. **Specification approval** — approves the hardened written contract before planning.
3. **Execution handoff** — approves the dependency-aware plan and exact repository base before any
   implementation branch, worktree, commit, or PR exists.

Planning, hardening, provider synchronization, and read-back are work steps, not extra gates.
Silence, implication, issue state, or provider success never clears a gate.

## Execution invariants

- One independently shippable increment maps to at most one PR.
- Each active task has one controller identity, branch, collision-safe worktree, allowed surface,
  and current head.
- Dependency-independent disjoint tasks may run concurrently; prerequisites advance first.
- The implementation worker returns an uncommitted diff and evidence. The controller performs
  specification and quality review before authorizing commit/PR delivery.
- Graphite preserves stack ancestry. GitHub proves PR/head/base/check/review/merge state.
- Every workflow stops on scope, ancestry, collision, evidence, or review drift. No workflow merges.

## Explicitly selected Linear persistence

Artifact mode starts only when the caller supplies an exact Linear resource or explicitly requests
persistence. Tracked `.woostack/config.json` policy supplies validated defaults only after selection;
it cannot trigger a provider read/write or authorize a mutation. Before a selected write, the
workflow verifies the canonical repository association and resolved caller-selected workspace/team,
then preflights the host's official Linear MCP without reading the API key/OAuth credential.

Selected fix/build/standalone-plan persistence stores:

- one project containing the approved specification or diagnosis/fix context;
- one parent plan issue containing the complete plan;
- one native child issue per increment containing its full contract;
- native dependency relations between increment children; and
- notes derived from already-observed repository results.

Every mutation uses a stable identity and independent read-back. Exact resources take precedence
over creation. `woostack-change` never contacts Linear. Without selection, fix/build/plan make no
Linear call. Linear still does not assign the worker, own a branch, prove tests or review, approve
execution, accept work, or override Git/GitHub evidence.

Explicit abandonment is the one workflow-owned project-status transition. At execution handoff or
any other phase, a fix/build workflow stops repository work, sets an existing plan project to the
configured canceled status, and independently reads the transition back. It never creates a project
only to cancel it. Handoff, replanning, and blockers leave the project open.

## Authority boundaries

| Surface | Authority |
| --- | --- |
| User request and workflow gates | scope, decisions, approvals, acceptance criteria |
| Git and GitHub | source, ancestry, commits, PRs, checks, reviews, merge evidence |
| Graphite | stack and branch operations |
| Linear plan project | durable specification/fix context, parent plan, increment children, and notes |
| Audit, QA, response reports | sanitized non-authoritative diagnostic evidence |

The [engineer-agent contract](/docs/concepts/engineer-agents) keeps decision-making, isolated
implementation, and independent review separate without depending on a provider identity.
