title: Building rules
description: The plain-artifact local-authority build loop, optional Linear, Plane, or GitHub mirroring, and bounded one-PR routes.

The user decides the product and authorizes work. Git and GitHub show what was delivered.
Project-backed work keeps a specification, ordered plan, and recovery state locally. Bounded
work fits one pull request (PR) and uses the agreed scope in the current conversation.

## Workflow scope

| Shape | Commands | Active contract | Provider/input behavior |
| --- | --- | --- | --- |
| Bounded bug or regression | [woostack-fix](/docs/skills/woostack-fix) | proved diagnosis and complete user-approved correction/verification | none |
| Bounded enhancement, refactor, test-only task, or authorized understood correction | [woostack-execute](/docs/skills/woostack-execute) | one complete bounded input, with an optional exact GitHub issue | none for goal-only; issue-backed input reads only the selected GitHub issue |
| Larger or explicitly project-backed fix | [woostack-fix](/docs/skills/woostack-fix) | complete user-verified specification and increment plan | optional mirror |
| Multi-increment feature | [woostack-build](/docs/skills/woostack-build) | user-verified specification and ordered local increment plan | optional Linear, Plane, or GitHub mirror |
| Greenfield codebase | [woostack-bootstrap](/docs/skills/woostack-bootstrap) | complete approved design | exact artifact or explicit persistence request only |

The shape of the work determines the workflow. Development records cannot turn ambiguous scope
into a complete contract or replace direct repository evidence.

## Planning and informed approval

The [workflow map](/docs/concepts/workflows) shows the Build/Fix sequence. Ideate collects decisions
that the user verifies. Harden checks those decisions against the repository and raises one
discrepancy at a time. Technical details do not become approved just because they match existing code.
Plan divides the work into increments, each small enough for one PR. It records outcomes, scope,
acceptance criteria, verification, risks, explicit prerequisites, and parent-selection policy. It does
not prescribe every coding step or estimate changed lines. [GitHub plans](/docs/configuration/artifacts/github#identities-hierarchy-and-graph)
support dependency DAGs in both Project mode and standalone parent-issue mode
(`--parent-issue new` or an exact parent issue URL, exclusive with `--project`); Linear, Plane, and
local-only plans retain their sequential contract. Parent-issue mode requires
`artifacts.provider: "github"` but no Project settings, access, or mirror, and Build/Fix optional
mirrors never select it automatically. Its native parent hierarchy only groups the plan and is
distinct from `blocked-by` edges and Git branch ancestry; the parent is never a task, dependency
endpoint, execution, or PR, and unsupported nested or partial hierarchy fails closed.
Execute accepts one selected bounded task under its [admission contract](/docs/skills/woostack-execute#admit-one-task), not a whole plan.
An explicit [Orchestrate](/docs/skills/woostack-orchestrate) invocation selects a GitHub parent issue,
Project, or exact canonical issue list and dispatches ready tasks to Execute. List mode keeps the
selected set closed, validates native/declared/inferred edge provenance, and does not publish
inferred dependencies. Unlike parent-issue planning, parent-issue and list execution require no
provider-mirror configuration.

Build and project-backed Fix use the
[verified handoff](/docs/skills/woostack-build#verified-handoff). The user sees the complete artifacts
before choosing whether to execute, stop, or abandon. Clear natural-language choices are accepted;
ambiguity or a material change to the approved contract cannot start execution.

The [artifact contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md)
defines storage, optional mirrors, recovery, and how to handle a changed base branch. If the
integration branch's tip has changed since planning, the user must choose what to do before mutation.

## Execution invariants

- Each increment fits at most one PR.
- Execute takes one complete bounded task per invocation: `/woostack-execute <bounded input>`
  with an optional exact canonical GitHub issue URL. Retired `--run`, `--project`, and `--recheck`
  inputs are rejected (see [Execute](/docs/skills/woostack-execute#retired-inputs)). Build/Fix stop at
  retained artifacts; the caller selects one task and supplies its complete bounded contract.
- Each bounded task runs its own worktree, branch, allowed paths, and PR. Separate tasks may proceed
  concurrently only when their paths, branches, worktrees, PRs, and responsibilities do not overlap.
- Each active task has one branch, one collision-safe worktree, one allowed set of paths, and
  one current head commit.
- Focused checks, a smoke test of the changed behavior, and comparison against the approved task
  precede delivery. Orchestrate requires delivery-capable Execute subagents and independent
  post-submission specification validation before releasing dependents.
- Git and GitHub prove parent-child branch relationships, PRs, commits, reviews, and merge
  state. Graphite supplies additional stack evidence only when selected. Required repository checks remain
  mandatory delivery gates; non-required available CI checks are observation-only.
- Unresolved scope, ancestry, collision, required-evidence, or review conflicts stop the workflow.
  Agents never merge, mark a PR ready, enable auto-merge, or queue a PR for merge.

## Canonical local records and optional remote mirroring

Build and project-backed Fix use local records as the source of truth for the plan. Goal-only
Execute and bounded Fix make no artifact-provider calls unless an exact issue association or
requested provider operation is selected. Execute's exact GitHub issue input performs the required
read of that issue through an authorized GitHub capability (native tools preferred; host-authenticated
`gh` supported); it does not require provider configuration, a Project, a mirror, or a persisted plan.

Run artifacts are retained after completion or abandonment. Abandoning a local run leaves its mirror
unchanged. Standalone provider lifecycle operations follow the selected profile and never confer
source-control authority.

## Authority boundaries

| Surface | Authority |
| --- | --- |
| User request and decisions | initiates the selected workflow and authorizes decisions |
| Local run manifest (`.woostack/tmp/runs/<run-id>/`) | records project-backed scope, plans, task contracts, and recovery state; does not grant permission |
| Git and GitHub | source, ancestry, commits, PRs, checks, reviews, merge evidence |
| Graphite (optional) | stack and branch operations when explicitly selected or already managed |
| Audit, QA, response reports | sanitized non-authoritative diagnostic evidence |

The [Hermes guide](/docs/hermes) documents how an external engineer can review harness evidence
without receiving implementation authority.
