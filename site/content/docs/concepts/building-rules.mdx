The user decides the product and authorizes work. Git and GitHub show what was delivered.
Project-backed work keeps a specification, ordered plan, and recovery state locally. Bounded
work fits one pull request (PR) and uses the agreed scope in the current conversation.

## Workflow scope

| Shape | Commands | Active contract | Provider mirror behavior |
| --- | --- | --- | --- |
| Bounded bug or regression | [woostack-fix](/docs/skills/woostack-fix) | proved diagnosis and complete user-approved correction/verification | none |
| Bounded non-bug change | [woostack-change](/docs/skills/woostack-change) | one explicit goal/contract | none |
| Larger or explicitly project-backed fix | [woostack-fix](/docs/skills/woostack-fix) | complete user-verified specification and increment plan | optional mirror |
| Multi-increment feature | [woostack-build](/docs/skills/woostack-build) | user-verified specification and ordered local increment plan | optional Linear, Plane, or GitHub mirror |
| Greenfield codebase | [woostack-bootstrap](/docs/skills/woostack-bootstrap) | complete approved design | exact artifact or explicit persistence request only |

The shape of the work determines the workflow. Development records cannot turn ambiguous scope
into a complete contract or replace direct repository evidence.

## Planning and informed approval

The [workflow map](/docs/concepts/workflows) shows the Build/Fix sequence. Ideate collects decisions
that the user verifies. Harden checks those decisions against the repository and raises one
discrepancy at a time. Technical details do not become approved just because they match existing code.
Plan divides the work into increments, each small enough for one PR. It records outcomes, scope,
acceptance criteria, verification, risks, and the dependency order and parent branches. It does not
prescribe every coding step or estimate changed lines.

Build and project-backed Fix use the
[verified handoff](/docs/skills/woostack-build#verified-handoff). The user sees the complete artifacts
before choosing whether to execute, stop, or abandon. Clear natural-language choices are accepted;
ambiguity or a material change to the approved contract cannot start execution.

The [artifact contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md)
defines storage, optional mirrors, recovery, and how to handle a changed base branch. If the
integration branch's tip has changed since planning, the user must choose what to do before mutation.

## Execution invariants

- Each increment fits at most one PR.
- Execute requires exactly one of `--run <exact-run-id> [--recheck]`, `--project <...>`, or
  `--issue <...>`. Provider forms require configured provider access. Plane uses `--issue`;
  its project is not an executable scope. See [Execute](/docs/skills/woostack-execute) for exact inputs.
- Tasks run sequentially within each run. Separate runs may run concurrently only when their paths,
  branches, worktrees, PRs, and responsibilities do not overlap.
- Each active task has one controller, branch, collision-safe worktree, allowed set of paths, and
  current head commit.
- Implementation may run in the current session or in a separate worker. Focused checks, a smoke
  test of the changed behavior, and independent comparison against the approved task precede delivery.
- Git and GitHub prove parent-child branch relationships, PRs, commits, reviews, and merge
  state. Graphite supplies additional stack evidence only when selected. Available CI checks are
  observation-only; their result or availability alone does not block.
- Unresolved scope, ancestry, collision, required-evidence, or review conflicts stop the workflow.
  Agents never merge, mark a PR ready, enable auto-merge, or queue a PR for merge.

## Canonical local records and optional remote mirroring

Build and project-backed Fix use local records as the source of truth for the plan. The
[configuration reference](/docs/configuration) and its provider profiles explain provider selection
and each provider's resource types. Bounded Fix and Change make no provider calls.

Run artifacts are retained after completion or abandonment. Abandoning a local run leaves its mirror
unchanged. Standalone provider lifecycle operations follow the selected profile and never confer
source-control authority.

## Authority boundaries

| Surface | Authority |
| --- | --- |
| User request and decisions | initiates the selected workflow and authorizes decisions |
| Local run manifest (`.woostack/tmp/runs/<run-id>/`) | records project-backed scope, plans, task contracts, and recovery state; does not grant permission |
| Git and GitHub | source, ancestry, commits, PRs, checks, reviews, merge evidence |
| Graphite (optional) | stack and branch operations when explicitly selected or already managed |
| Audit, QA, response reports | sanitized non-authoritative diagnostic evidence |

The [Hermes guide](/docs/hermes) documents how an external engineer can review harness evidence
without receiving implementation authority.
