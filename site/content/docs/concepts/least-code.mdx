---
title: Least code, still safe
description: "woostack's core engineering tenet: write as little code as necessary without cutting edge cases or risks."
---

Write as little code as the problem needs. Less code leaves less to read, test, and maintain, but
correctness and safety determine how small a solution can be.

## Understand first, then take the first rung that holds

Read the affected code and trace the actual flow from start to finish before choosing a solution.
Then stop at the first option that solves the problem:

1. Decide whether the code is needed at all. This is YAGNI: "you aren't going to need it."
2. Reuse a helper, utility, or pattern already in the repository.
3. Use what the language's standard library provides.
4. Use a native platform feature before adding another layer.
5. Reuse a dependency the project already has.
6. Use a direct expression when it is clear and safe.
7. Write the minimum new implementation.

## Never shrink code by cutting safety

Prefer deletion and straightforward code. Never remove validation, error handling, security,
accessibility, or data-loss protection just to shrink a diff. Keep deliberate layers of protection,
even when they repeat a check. The DRY principle ("don't repeat yourself") does not justify removing
that protection.

When two solutions are the same size, choose the one that handles edge cases correctly. Keep the
regression test for a simplification that changes behavior. A deliberate limitation needs a `why`
comment that explains its limit and when to replace it.

## Comments explain why, not what

Use comments for reasons the code cannot explain: a hidden constraint, a workaround, or a condition
that must always hold. Avoid repeating what the code already says.
