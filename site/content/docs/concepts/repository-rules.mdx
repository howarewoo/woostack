---
title: Repository structure and rules
description: Why placement, boundary, dependency, testing, and delivery rules follow the repository's own conventions, and where each rule is owned.
---

A repository's own instructions, architecture, native conventions, selected dependencies, and
lockfiles are authoritative. Woostack's implementation rules describe the outcomes worth preserving
on top of that foundation; they never impose a layout, an abstraction, or a version the work did
not require. That is true for a codebase that already exists and for one you are creating now, so
there is one set of rules rather than separate contracts for greenfield and existing work.

[Execute](/docs/skills/woostack-execute) owns the executable form of this guidance. Its
[implementation patterns](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/patterns.md)
cover placement, shared extraction, boundaries, API compatibility, type safety, dependencies, and
the least-code standard, and its
[infrastructure reference](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/infrastructure.md)
covers deployment, migrations, environment and secrets, client lifecycle, and observability. This
page explains why those rules read the way they do and when each one applies.

## Repository-owned structure

The application that owns a capability keeps its code. Business logic, data access,
authentication, observability, UI, utilities, and vendor integrations belong to the unit that
needs them, organized by the unit's own module and export conventions. Role names such as
services, layouts, or validation do not require matching directories.

Shared code is a consequence of real reuse, not a starting layout. When several applications need
the same implementation or contract, the smallest coherent surface is extracted to the repository's
shared-code location, named for the capability it owns, and the application-local duplicates are
removed. Placeholder packages, speculative abstractions, and pass-through wrappers add a second
convention beside the repository's own, so they stay out. In a mixed-technology repository each
unit keeps its native structure and manifest, and root orchestration appears only when it
simplifies real cross-application commands.

## APIs and application boundaries

A boundary adapter translates data and errors between an external API or client and the models used
inside the application. Keeping transport, client, and vendor formats out of business logic is what
lets the domain logic stay testable and portable, so the guidance covers both directions across
HTTP/RPC, webhooks, queues, events, and third-party APIs. Database persistence mapping and
ordinary in-process calls sit outside that rule.

The pattern reaches new flows and existing flows the task materially changes. Migrating untouched
legacy boundaries is separate work, and a deliberately shared contract that already matches the
application's model needs no identity-only wrapper, although validation and error translation still
apply.

Published compatibility follows the same restraint. Existing identifiers stay stable, inputs gain
optional fields rather than losing any, outputs gain fields rather than changing meaning, and a
breaking change uses the repository's documented versioning mechanism. See
[patterns.md §3](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/patterns.md#3-application-boundary-adapters)
and
[§4](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/patterns.md#4-api-compatibility).

## Type safety

Types are how an application states its own contracts, so the strongest practical compile-time and
runtime checks in the selected stack are worth their cost. Untrusted values are narrowed at the
entry point before application code consumes them, related contract types derive from one
definition where the technology allows it, and bypassing a check needs a narrow documented reason.
Type helpers stay with the unit that owns them.

## Dependencies

Versions come from authoritative current sources, never from model memory, but only when a
dependency is actually being selected or changed. A task that needs no dependency change preserves
the existing versions and lockfile; treating a version lookup as a mandate to upgrade turns a
bounded task into an unrelated one. Each application declares the dependencies its runtime needs
in its own manifest, shared code declares its own categories where the ecosystem distinguishes
them, and only genuine repository-wide tooling belongs at the root. Compatibility warnings are
resolved in the consuming unit, lifecycle scripts are enabled only where the required installation
behavior was verified, and the selected package manager's lockfile and integrity metadata are
preserved.

## Least code, still safe

Less code means less to read, test, and maintain, but correctness and safety decide how small a
solution may be. Before adding code, trace the affected flow and stop at the first rung that
holds: confirm the code is needed, reuse an in-tree helper or pattern, use standard facilities,
use a native platform feature, use an already-installed dependency, write a direct one-line
implementation, and only then add the minimum new code.

When two approaches are the same size, choose the edge-case-correct one, and prefer deletion over
addition. Validation, error handling, security, accessibility, and data-loss protection are never
cut to shrink a diff, and deliberate layers of protection survive even when they repeat a check.
A simplification that changes behavior keeps its regression test, and a knowingly cut corner gets
a `why` comment naming the limit and the upgrade path. Comments explain reasons the code cannot
state; they do not repeat it. See [Least code, still safe](/docs/concepts/least-code) for the
rationale and
[patterns.md §7](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/patterns.md#7-least-code--comments)
for the full standard.

## Testing

For implementation work, follow the canonical
[Execute testing guidance](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/tdd.md).
It defines when a test-first sequence applies, meaningful coverage, characterization tests for
existing code, repository conventions, and concrete verification when no test runner exists. A
change is incomplete until its required verification passes.

## Production concerns

Deployment shape, migration safety, environment and secret handling, external client lifecycle, and
observability all depend on the selected stack and delivery model, so the
[infrastructure reference](https://github.com/howarewoo/woostack/blob/main/skills/woostack-execute/references/infrastructure.md)
states the outcomes rather than a vendor default. The reasoning behind them is short. Migrations
run through controlled automation with observable failure and recovery rather than from a
developer's machine. Production secrets come from the host's secret store or managed runtime
configuration, while the repository keeps a non-secret inventory of required configuration names
and validates them at startup. Vendor clients get an interface only when it improves portability,
testing, isolation, or reuse. Telemetry is structured and queryable, with credentials, personal
data, and other secrets redacted before transmission.

## Creating a project that does not exist yet

New-project work uses the same workflows as everything else. Nothing about it requires a separate
command, a checkout, a GitHub destination, or an extra approval event.

Planning a product before any code exists belongs to
[Plan](/docs/skills/woostack-plan). It works from the supplied goal, constraints, and
authoritative research, resolves only the material decisions that change the outcome, and writes
nothing unless the request asks for issues. Settled technology choices are reused rather than
re-asked.

Creating the first slice belongs to [Execute](/docs/skills/woostack-execute) as an authorized
bounded outcome. Repository, HEAD, index, base, and worktree checks apply where those objects
exist, so their absence is not a blocker. What replaces them is target admission before the first
write: one unambiguous intended path and physical parent, no symlinks in the target or its
ancestors, nothing unreadable, ambiguous, or unsafe, no competing writer, and a target that is
absent or empty. A collision blocks writing there; it is never permission to delete, overwrite,
reset, or scaffold around existing content.

The scaffold itself is the smallest requested working slice in the selected ecosystem's native
structure, with unrequested demo content removed, the project's own applicable checks actually
run, each requested surface booted or smoked through a meaningful path, and setup prerequisites,
selected technologies and lookup sources, non-secret environment names, and real commands
recorded in the README. A command that does not exist is never reported as passing, and requested
`AGENTS.md`, `DESIGN.md`, `PRODUCT.md`, or local support remain
[Init's](/docs/skills/woostack-init) work rather than automatic scaffold output.

A local-only scaffold needs no GitHub account, Project, remote, commit, push, or PR. Git
initialization happens only when requested or needed for requested delivery. A missing delivery
destination is an unmet delivery boundary, not permission to create remote resources or a reason
to block otherwise authorized local work.

## Delivery and workspaces

Branching, commits, pull requests, and remote writes belong to
[Commit](/docs/skills/woostack-commit) and its
[source-control contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-commit/references/source-control.md),
which owns staging, publication, PR content, read-back of head, base, and state, and the shared
authorized-tool and stack rules. New PRs are drafts, readiness changes only when the request asks,
and merging, auto-merge, and merge queues stay human decisions.

Once Git exists, the
[workspace guidance](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/worktrees.md)
owns isolation, ownership, and base selection for every later bounded feature or fix. A target with
no Git repository yet cannot use it, which is why scaffold admission is described separately above.
Retained runs, drafts, and provider records stay as their owner left them.

## Existing repositories

The same guidance preserves an existing repository's conventions and limits changes to the requested
scope. A read-only root-cause investigation belongs to [Debug](/docs/skills/woostack-debug);
an authorized bounded correction belongs directly to [Execute](/docs/skills/woostack-execute).
[Plan](/docs/skills/woostack-plan) produces a plan when requested. None requires an extra skill handoff.
