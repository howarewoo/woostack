---
title: Parallelism with worktrees
description: How woostack runs many builds, changes, fixes, and executions at once by isolating each in its own git worktree.
---

woostack isolates tracked implementation writes so multiple assigned issues can proceed without
sharing a checkout. Every implementation worktree is bound to one verified Linear issue; Linear
owns the work identity and Git, Graphite, and GitHub own branches, ancestry, PRs, and merge truth.
Design, specification, planning, assignment, and gate mutations create no Git worktree.

## A worktree per issue

The worktree path is derived from the issue's immutable native Linear ID, not its title or branch:

```text
.woostack/worktrees/issues/<native-issue-id>
```

Branch names remain readable, but they are not recovery identity:

| Run | Branch | Worktree directory |
| --- | --- | --- |
| [woostack-change](/docs/skills/woostack-change) | `change/<slug>` | `.woostack/worktrees/issues/<native-issue-id>` |
| [woostack-fix](/docs/skills/woostack-fix) | `fix/<slug>` | `.woostack/worktrees/issues/<native-issue-id>` |
| [woostack-execute](/docs/skills/woostack-execute) increment | the verified issue branch | `.woostack/worktrees/issues/<native-issue-id>` |

Before creating or reattaching a worktree, the controller verifies the issue's repository,
contract, owner, assignment receipt, dependency ancestry, branch/PR state, and complete local
inventory. It then creates an atomic machine-local claim under
`.woostack/worktrees/.registry/<native-issue-id>/claim.json`. The claim prevents competing local
worktrees; it never replaces remote assignment, scope, dependency, evidence, or lifecycle
authority.

The base branch is never hard-coded. `resolve-base.sh` resolves the integration branch, while the
issue's verified role and relations determine the exact start commit and Graphite parent:
standalone issues use the retained integration commit, project roots use the feature's frozen base
SHA, and dependency children use their declared Git parent's exact branch/head.

## The primary tree stays clean

This is the invariant that makes parallel runs safe:

<Callout type="info">
  A run does all its writes in its own worktree. The primary checkout stays on the base branch,
  clean. It is the stable point every run branches from. Two runs never touch the primary tree, so
  runs with disjoint branch sets never collide.
</Callout>

Stacked increments build on verified issue ancestry rather than the primary checkout. A root starts
from the frozen base SHA. A dependency child starts from its declared Git parent's finalized head;
a parent already marked `done` additionally requires verified merge evidence. Non-parent
dependencies must be accepted, merged, and represented in the child's permitted ancestry.

## Teardown, and what survives

- **Success:** after the commit, push, canonical PR attribution, Linear relation, and `inReview`
  receipts all read back, the controller removes that issue's worktree and exact registry claim.
  The branch, commits, PR, and remote evidence remain.
- **Failure or unknown:** preserve the worktree and claim. Report the exact issue, path, branch,
  observed boundary, and safe next action; a timeout proves neither success nor absence.
- **Review reopen:** after successful teardown, a sweep may reattach the existing branch only from
  the canonical verified review-reopen state and one current bounded `restackAuthorized`. It cannot
  use generic release/reclaim or invent an ad hoc worktree.

The registry is disposable administration, but unexplained branch/worktree state is a collision,
not permission to delete or adopt it. See the
[canonical worktree authority](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/worktrees.md)
for exact create, resume, review-reopen, and teardown rules.

Parallelism is allowed only across dependency-independent issues with distinct owners, runs,
responsibility surfaces, claims, branches, worktrees, and PRs. Native Linear relations and verified
Git ancestry—not issue order or branch naming—decide whether two tracks may proceed.
