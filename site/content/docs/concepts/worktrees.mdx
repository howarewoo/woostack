---
title: Parallelism with worktrees
description: How woostack isolates bounded implementation work independently from artifact storage.
---

A Git worktree is a separate checkout of the same repository. It lets a task edit its own branch
without changing files in the primary checkout. A worktree does not grant scope, approval, status,
or acceptance. The
[workspace guidance](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/worktrees.md)
defines identity, collision, writer ownership, base evidence, and recovery.

Use an approved existing workspace and branch or a host/repository-selected isolated checkout. A
fresh worktree is not mandatory. Inspect the selected index, dirty state, branch, base, and diff;
preserve unrelated changes. Concurrent writers need distinct, independently owned workspaces and
responsibility surfaces. Before reuse, inspect native writer state and current Git/PR facts. If a
former writer may still be active, stop affected work until exit is proved; serialization cannot
prove it stopped. Instructions do not enforce locks or sandboxing.

Required predecessor changes must actually be available in the chosen base. Git ancestry proves
commit-preserving containment, while a squash landing requires checking the native landing and
integrated content rather than assuming the former PR head is an ancestor. Conflicting bases or
unknown outcomes preserve work and block the affected task, not unrelated work.

## Recovery and lifecycle

After a lost response, rediscover the selected workspace, writer, branch/diff, and matching PR
before repeating a mutation. Do not adopt, reset, clean, stash, overwrite, or remove another
owner's checkout. Publication does not authorize workspace teardown. A verified code delivery
remains valid if optional metadata is unavailable; explicitly required registration is reported
incomplete, not claimed as done.
