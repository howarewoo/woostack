---
title: Status board reference
description: Repository inputs, identity rules, derived states, and failure behavior for the status board.
---

[woostack-status](/docs/skills/woostack-status) builds a fresh board from Git and
the verified GitHub repository, with Graphite evidence only when selected. It does not save a
separate board or development ledger. Exact caller-supplied GitHub Project, issue, or PR records
can add read-only context after identity verification.

## Display shapes

The board groups work in two ways:

- Stacks/features: connected branches and PRs above the integration base, the branch into which
  work will eventually land. Verified plans and dependencies can supply grouping context.
- Standalone work: a branch, PR, or bounded task outside a stack, supported by repository evidence.

An artifact alone cannot create a row. The repository, branch reference, commit SHA, PR number,
head and base branches, and Git ancestry identify the work. Titles and branch display names do not
establish ownership or permission.

## Derivation

Each status run:

1. Identifies the repository, integration base, branches, worktrees, and verified parent relationships.
2. Reads all relevant PRs, reviews, unresolved threads, merge evidence, and timestamps.
3. Derives each row's work, review, and merge state from that snapshot. Available CI checks are
   displayed separately; missing, pending, or failed checks do not change the row's state.
4. Optionally reads exact caller-supplied GitHub Project, issue, or PR records and attaches them only
   after verifying their repository or PR identity.
5. Prints the board with completion counts, blockers, stale-work labels, and one next action per row.

The
[canonical status conventions](https://github.com/howarewoo/woostack/blob/main/skills/woostack-status/references/conventions.md)
own the precise state derivation and output contract.

## Authority and failure boundaries

- The user's request and explicit decisions authorize the workflow and define its scope.
- Git and GitHub show source-control, PR, review, and merge state.
- Linked GitHub records may explain the specification, plan, or fix. They cannot create a row, grant
  permission, or override repository evidence. Project Status remains separate from delivery state.
- Local diagnostic reports provide supporting evidence only.

Missing or incomplete required Git or GitHub evidence leaves affected facts unknown and
can make a row `unknown` or `blocked`; Graphite evidence is required only in Graphite mode.
Unavailable CI checks are excluded from this rule.
Missing GitHub context affects only the requested enrichment. Status never mutates GitHub records and
does not derive local state from an unverified context.

<Callout type="info">
  Re-run the board when branches, commits, or reviews change. It reports a fresh view of the
  repository and does not maintain its own status records.
</Callout>
