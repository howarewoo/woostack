---
title: Tracking work with Linear
description: How Linear development records join GitHub implementation and PR truth.
---

[woostack-status](/docs/skills/woostack-status) builds a fresh view from two authorities:
development records read through the [official Linear MCP](https://mcp.linear.app/mcp), and
implementation evidence read from Git and GitHub. It does not maintain a separate tracked status
snapshot.

Linear owns scope, contracts, gates, assignments, dependencies, decisions, progress, and
acceptance. Git and GitHub own source, branches, commits, pull requests, reviews, checks, and merge
state. Status joins the two by exact verified identities without treating either one as a fallback
for the other.

## The two tracked shapes

### Standalone work items

A bounded fix or change has one repository-owned standalone issue and no feature project. The
issue description and comments carry its contract, decisions, evidence, review, and acceptance,
while its attributed GitHub PR proves the implementation and merge state.

Status renders the issue directly. It never invents project progress for a standalone work item.

### Multi-issue projects

A multi-issue feature has one Linear project, specification-bearing project updates, and a complete
ordered set of increment issues. Those specification-bearing updates carry the written
specification and lifecycle; status derives phase and progress from their verified event chain,
current issue records, relations, ownership, and GitHub evidence. No Linear document is created.

Each issue represents one independently shippable increment and one attributed PR. Project
progress is based on the complete managed issue set. The project can reach completion only after
every increment has reached its verified terminal condition.

## How the board is derived

Each status run:

1. discovers the host-exposed MCP tools by capability and preflights authenticated read access to
   the configured Linear workspace and team;
2. fully reads the repository-owned projects and standalone issues, their current updates,
   comments, ownership, relations, and states;
3. independently reads the matching GitHub PRs and merge evidence;
4. validates the exact Linear-to-PR joins, complete histories, ownership, dependencies, and
   repository attribution; and
5. renders the current board or stops with an actionable ambiguity instead of guessing.

The
[canonical status conventions](https://github.com/howarewoo/woostack/blob/main/skills/woostack-status/references/conventions.md)
define event validity, state derivation, PR attribution, reconciliation, stale work, and next
actions. They are linked here rather than copied into an authored page.

## Terminal truth

Status may reconcile only narrowly eligible terminal state, and it must read each change back.
An issue is not done merely because its PR merged: the relevant acceptance authority must also
have accepted the verified evidence. Conversely, a Linear completion claim cannot prove a merge
that GitHub does not report.

For an engineer pair, the decision-maker remains the acceptance authority. The implementing coder's
self-check is implementation evidence, not independent review. Only an explicit user invocation
of [woostack-review](/docs/skills/woostack-review) may delegate analysis to independent reviewers,
and their findings do not replace the decision-maker's verdict.

## Fail-closed boundaries

Status reports a blocker instead of a clean board when required MCP capability, pagination,
identity, ownership, event history, relation, PR attribution, Git ancestry, review evidence, or
read-back is missing, partial, stale, foreign, or ambiguous. It never derives a successful result
from titles, branch resemblance, unchecked remote prose, or cached local output.

Local `.woostack/memory/` and `.woostack/wisdom/` remain reusable knowledge only. Audit, QA, and
production-response reports remain non-authoritative diagnostics. None of them can set a phase,
assign an issue, clear a dependency, approve execution, accept work, or mark it complete.

<Callout type="info">
  The status table is a current narration of Linear and GitHub truth, not a third record system.
  Re-run it whenever either authority changes.
</Callout>
