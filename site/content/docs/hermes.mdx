---
title: How to use Hermes as an external engineer
description: Drive one persistent OMP coding session from Hermes without giving Hermes implementation authority.
sidebar: { order: 4 }
---

Hermes can coordinate decisions and review evidence as an external engineer. Install woostack in
OMP or another supported coding harness, the application that runs the coding agent and its tools.
Hermes is not a supported woostack host. It must not edit implementation source or substitute its
own conclusions for repository evidence.

## Before you start

You need:

- an approved task with a defined scope and acceptance criteria;
- an isolated worktree, a separate checkout for that task;
- an interactive OMP profile with woostack installed; and
- a process or PTY (pseudo-terminal) interface that passes arguments safely and retains a handle
  for sending input to the running process.

The OMP session manages the worktree, implementation, workers, and focused verification.
Hermes checks that the work stays within the approved task and reviews the returned evidence.

## 1. Start one persistent OMP session

A persistent session keeps the same OMP process running between messages. Use one process for
each active task conversation, and do not switch processes while that conversation is in progress.

Pass the profile, working directory, and initial prompt as separate argument values so prompt text
cannot become shell syntax. Confirm the installed CLI flags with `omp --help`. The launch form is:

```text
omp --profile <profile> --cwd <worktree> <prompt>
```

Do not add `-p` or `--print`. Those flags select non-interactive mode and exit after one response.
If the process interface cannot set a working directory, put the exact canonical worktree path
in the prompt and require OMP to verify it before reading or writing. Stop if the profile,
working directory, repository, branch, current commit, or allowed paths do not match the task.

## 2. Keep using the same process

Keep the interactive process handle. Send every correction and response from the responsible user
as new input through that handle. Never insert task descriptions, artifact text, issue text, or
user responses into a shell command.

Keep the same process attached to the same isolated worktree during retries, approval relay,
and any request for a bounded correction.

## 3. Keep decisions inside the approved contract

Hermes may interpret the approved task, inspect OMP's diff and command results, review the
evidence, accept a result that meets the contract, or request one correction within that scope.
It may not expand scope, edit source, run implementation commands, commit, push, open a pull
request, or guess missing context.

OMP workers return observations, changes, commands, results, and blockers. Hermes checks that
evidence independently. Stop if evidence is missing, contradictory, or stale.

## 4. Escalate contract changes

Ask the responsible user about any new path, changed acceptance criterion, unresolved decision,
or question outside the approved scope. Keep OMP at the last verified point while waiting.
A question from the user does not itself approve a change.

## 5. Relay the user's response verbatim

An Ask is a question or approval choice that OMP needs the responsible user to decide. During an
active conversation, relay only that user's live response, verbatim and unmodified, through the
same OMP process that asked the question. Do not summarize, rewrite, splice, or replay it.

A provider record, status, assignment, label, cached transcript, or Hermes-authored message cannot
make that decision. If the process restarts during the conversation, present a fresh Ask, obtain
a fresh response, and continue through the new process.

## 6. Review evidence before accepting or redispatching

Check the exact worktree, branch and current commit, changed paths, complete diff, commands,
observed results, focused verification, and blockers. Compare them with the approved task and
its acceptance criteria.

If the evidence is complete and meets the contract, accept the result or send one correction within
the approved scope through the same process and worktree. Read the complete evidence again after
a correction. Do not silently change the profile, worktree, process, or contract.

Git and GitHub remain authoritative for source, branch ancestry, commits, pull requests,
reviews, and merges. Hermes accepting a result does not prove any of those source-control facts.

## 7. Resume a retained run later

Build and project-backed Fix retain `project-spec.md`, `execution-plan.md`, and the run manifest,
which records recovery state, under `.woostack/tmp/runs/<run-id>/`. A later OMP process may resume
unchanged approved artifacts with:

```text
/woostack-execute --run <exact-run-id> [--recheck]
```

Resume validates the retained run before continuing. Execute rejects abandoned runs and verifies
completed runs without starting more work. Resume does not permit switching processes during an
active conversation or reusing a previous live response.

## 8. Clean up legacy launchers when safe

Cleanup is optional and manual. Legacy installations may contain host-owned `launch-omp` or
`bind-engineer-unit` files. Before removing any, verify that no active session or recovery path
depends on them and preserve needed evidence. Remove only the files the owner selects.
Woostack does not install, invoke, repair, or delete those launchers.
