---
title: Hermes as an external engineer
description: Use Hermes outside woostack to drive one persistent OMP coding session safely.
---

Hermes is an **external engineer**, not a supported woostack host or installed woostack runtime.
Woostack is installed only in OMP or another supported coding harness. Hermes may coordinate
decisions and review evidence from outside that installation, but it never receives implementation
authority and must not be installed as a coding harness for this collection.

## One persistent OMP session per live interaction

Keep one OMP process identity for each active bounded interaction. Do not switch processes during a
retry, approval relay, or redispatch. The OMP session owns the isolated worktree, project-scoped
worker routing, implementation, and focused verification; the external engineer owns the contract
boundary and synthesis. A later session may resume retained unchanged approved local artifacts only
through the exact run admission described below.

Use the harness's argument-safe interactive `process` or PTY interface with an argument vector.
Arguments are values, not shell source: pass the profile, cwd, and initial prompt as values. Confirm
the installed CLI's exact flags with `omp --help` before starting it. For current OMP releases:

```text
omp --profile <profile> --cwd <worktree> <prompt>
```

Do not add `-p` or `--print`: those select non-interactive mode and exit after one response. Retain
the interactive process handle and send every later correction or responsible-user response as a
new input through that same process. Never interpolate task, artifact, issue, or user-response prose
into a shell command. If the process API cannot set a working directory, put the canonical worktree
in the prompt and require OMP to verify it before reading or writing. A profile, cwd, repository,
branch, head, or allowed-path mismatch stops the session.

## In-contract decisions

Hermes can decide only questions already inside the approved bounded contract. It may interpret the
contract, inspect OMP's returned diff and command results, review the evidence, accept a bounded
result, and redispatch one in-contract correction through the same persistent OMP process. It may
not edit implementation source, run implementation commands itself, commit, push, open a PR, or
replace Git/GitHub evidence with its own statement.

OMP workers remain harness-local and isolated. They return observations, changes, commands, and
observed results; they do not expand scope, review or accept their own work, or infer hidden
context. Hermes reviews the complete evidence independently before accepting or redispatching. A
missing, contradictory, or stale handback is a failure, not permission to guess.

## Escalation and approval relay

Escalate any contract change, new path, changed acceptance criterion, unresolved decision, or
question outside the approved task to the responsible user. Do not turn a user question into an
implicit approval. Stop OMP at the last verified boundary while waiting.

Build and project-backed Fix workflows write plain Markdown `project-spec.md` and `execution-plan.md`
files, with optional matching Linear mirroring when enabled (`artifacts.provider: "linear"`). When Hermes
presents an Ask in an active conversation, only the responsible user's response may decide it. Relay that
response **verbatim and unmodified** through the same persistent OMP process that presented the Ask. Hermes
may transmit the response but may not author, summarize, rewrite, splice, or replay it. A Linear
record, status, assignment, label, cached transcript, or Hermes-authored message is not a decision.

Live user responses must travel verbatim through the active session. Retained run artifacts in
`.woostack/tmp/runs/<run-id>/` persist safely across process restarts and distinct processes. Resuming a
run with `/woostack-execute --run <exact-run-id> [--recheck]` validates the retained manifest and plain
artifacts without requiring the original OMP process to remain alive.

In contrast, during an active conversation, a restarted or different OMP process, copied response,
summarized response, or replayed transcript fails closed. Present a fresh Ask in the active conversation,
obtain a fresh responsible-user response, and only then continue through that same process.
## Evidence review and bounded redispatch

Review OMP's exact worktree and branch/head identity, changed paths, complete diff, commands and
observed results, focused verification, and blockers. Compare the handback with the approved
contract and acceptance criteria. If the evidence is complete and in contract, Hermes may accept
the result or request one bounded correction. Redispatch that correction through the same
persistent OMP process and the same isolated worktree; re-read the complete evidence afterward.
Do not silently switch profiles, worktrees, processes, or contracts.

The external engineer's decision is not source-control evidence. Git, Graphite, and GitHub remain
the authorities for source, ancestry, branches, commits, pull requests, reviews, and merges. A
review or acceptance claim without direct evidence stops at the last verified boundary.

## Optional legacy launcher cleanup

Legacy installations may contain host-owned `launch-omp` or `bind-engineer-unit` files under a
per-engineer launcher directory. Cleanup is optional and manual: first verify that no active session
or recovery path depends on them, preserve any needed evidence, then remove only the files the owner
intentionally selects. Woostack does not install, invoke, repair, or automatically delete those
legacy launchers. Keep the persistent OMP process and its worktree usable until the task has reached
a verified handback.
