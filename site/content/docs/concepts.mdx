woostack is a multiperson development workflow built around the
[official Linear MCP](https://mcp.linear.app/mcp). Linear is the only development-record
authority: it owns goals, written contracts, approvals, assignments, dependencies, decisions,
progress, and acceptance. The sole pre-issue exception is `/woostack-bootstrap`'s approved
project-first scaffold: its verified Linear project authorizes the initial scaffold before
planning creates increment issues. Every later implementation run, and every non-bootstrap
repository-changing run, binds to one exact Linear issue.
Git and GitHub remain authoritative for code, branches, commits, pull requests, reviews, and
merge evidence. Local memory and wisdom can help an engineer reason, and diagnostic commands can
produce local reports, but neither can authorize or describe the current state of development
work.

## The build loop

[woostack-build](/docs/skills/woostack-build) handles work expected to require multiple
independently shippable increments. It chains a fixed sequence:

> ideate → **approve design** → create the Linear project and initial specification update →
> harden the written spec → **approve spec** → plan and order increment issues →
> **execution handoff** → execute, review, and accept one issue at a time

The project is the feature-level coordination surface. Its updates hold the written specification,
approved decisions, phase, and progress, while ordered increment issues carry implementation
contracts, dependencies, ownership, and evidence. The
[canonical build procedure](https://github.com/howarewoo/woostack/blob/main/skills/woostack-build/references/linear-procedure.md)
owns the operational details.

Bounded one-PR work takes a smaller route. [woostack-fix](/docs/skills/woostack-fix) and
[woostack-change](/docs/skills/woostack-change) bind or create one standalone Linear issue. That
issue carries the complete contract and chronological decision/evidence record; no wrapper project
is created.

## Three hard gates

The multi-issue build loop advances past exactly three points only after an explicit answer:

1. **Design approval** accepts the proposed design and permits creation of the project and its
   initial specification update.
2. **Written-spec approval** accepts the hardened specification before increment planning begins.
3. **Execution handoff** chooses Go, Run overnight, or Hand off after the ordered issue set is
   ready.

Persistence, read-back, planning, implementation checks, review, and progress updates are work
steps, not additional approval gates. Silence never clears a gate.

## Two development-record shapes

| | Standalone work | Multi-issue work |
| --- | --- | --- |
| Use when | One bounded fix or change can ship in one PR | A feature needs multiple independently shippable increments |
| Linear records | One bound standalone issue | One project, specification-bearing project updates, and ordered increment issues |
| Planning | Scope and acceptance criteria live on the issue | The issue order and dependency relations form the implementation plan |
| Evidence | Decisions, implementation evidence, review, and acceptance stay with the issue | Project updates carry feature decisions/progress; issue comments carry increment evidence |
| Code delivery | One attributed GitHub PR | One attributed GitHub PR per increment |

The shapes are alternatives chosen by work size, not storage options. A one-PR request never gains
a synthetic project. A multi-issue feature never splits into competing feature records. In both
cases, Linear supplies the development record while Git/GitHub proves what code actually changed
and whether it merged.

[Status tracking](/docs/concepts/status-tracking) explains how those two authorities are joined
without copying the canonical event or attribution schemas into this page.

## Context economy

<ContextEconomy />

The working context is scarce. A window stuffed with material the current step does not need
reasons worse and runs out sooner. woostack keeps it focused through scoped recall, compact tool
output, isolated coding sessions, and independent review.

### Reusable knowledge is not development state

woostack keeps two reusable knowledge stores under `.woostack/`:

- **`memory/`** holds scoped, per-fact notes. Recall loads only notes whose scope matches the files
  in play, plus one hop of linked notes.
- **`wisdom/`** holds generalized, cross-cutting findings and loads as a small shared corpus when a
  workflow needs it.

<Callout type="info">
  Memory and wisdom may inform a hypothesis or implementation choice, but they cannot establish
  scope, assignment, phase, approval, dependency, acceptance, or completion. Those facts must be
  read from Linear and verified against Git/GitHub where code or PR evidence is involved.
</Callout>

Diagnostic outputs from audit, QA, or production-response workflows are similarly
non-authoritative. They may support a decision, but every repository-changing handoff must bind
the work to its exact Linear issue. The only earlier boundary is bootstrap's approved project-first,
project-owned initial scaffold before increment planning; all later implementation remains
issue-bound.

### Tools compute, agents read compact results

Small helpers gather and compress deterministic repository context so agents consume a result
rather than every input:

- `build-index.sh` reduces memory notes to an index used for scoped recall.
- `recall.sh` performs scope matching and emits only the reusable knowledge that matched.
- review prefetch gathers the relevant diff, metadata, rules, and knowledge once for independent
  analysis.

Development-record access is different: skills use the host's authenticated official Linear MCP
connection directly. They discover the available tool names by capability, preflight the exact
reads and mutations the workflow needs, and independently read every mutation back. Missing or
ambiguous capability stops the workflow; it never creates an alternate record.

### Decision-makers and coders stay isolated

An engineer unit separates judgment from implementation:

- The **decision-maker** owns the authority envelope, in-contract decisions, assignment checks,
  independent code and PR review, comments, acceptance, redispatch, handoff, and escalation. It
  does not edit source, run implementation tests, commit, push, or open implementation PRs.
- The **isolated coder** receives exactly one assigned issue and one worktree. It analyzes,
  implements, verifies, and returns evidence for that bounded issue, but it does not change scope,
  accept its own work, or act as its own independent reviewer.

Hermes as decision-maker plus OMP as coder is the first published adapter. Hermes dispatches with
exactly `omp --profile <engineer> -p --cwd <repo> <prompt>`, then independently inspects the
result. Only an explicit user invocation of
[woostack-review](/docs/skills/woostack-review) permits delegation to independent reviewer
profiles; the decision-maker still owns the verdict and acceptance.

See [Engineer agents](/docs/concepts/engineer-agents) for the provider-neutral boundary and
[Hermes](/docs/harnesses/hermes) for the concrete setup.
