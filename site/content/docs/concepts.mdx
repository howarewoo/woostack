woostack is a multiperson development workflow with two distinct truth domains. Linear owns the
current product specification and execution contracts for builds and post-diagnosis fixes. Git and
GitHub own source, branches, commits, pull requests, reviews, and merge evidence. A build always
uses one project containing its high-level specification plus one direct issue per increment;
native issue dependencies encode the plan. After proof, a Fix uses one project for its complete
specification plus a strict direct-issue chain. Other workflows remain artifact-optional.

Default init may make authenticated read-only Linear setup calls to validate non-secret defaults,
but that narrow exception permits no provider write. Exact responsible-user Linear approval events
clear only the matching fix/build content-revision gates.

## The build loop

[woostack-build](/docs/skills/woostack-build) handles work expected to require multiple
independently shippable increments. It chains a fixed sequence:

> resolve or create one canonical Linear project → admit its exact baseline → ideate and harden the
> specification in a secure local draft → stream the complete verified `project-spec.md` bytes and
> full identity (or a verified same-process byte-complete diff with old/new identities) immediately
> before a body-free `Accept`/`Abandon` Ask → synchronize, read back, and receipt that revision →
> plan and harden locally keyed direct increment issues → stream the complete verified
> `execution-plan.md` bytes and full identity immediately before a body-free `Accept`/`Abandon` Ask
> → synchronize native issues and dependencies, read them back, receipt the graph, clean up, and
> present the verified project handoff

Ordered increments remain independently shippable and map to reviewable PRs. Build has no
artifact-free fallback.

Bounded one-PR work takes a smaller route. [woostack-fix](/docs/skills/woostack-fix) proves a root
cause, resolves or creates one project for the complete fix specification, synchronizes its strict
direct-issue chain after both streamed content approvals, then presents the same user-controlled
handoff. [woostack-change](/docs/skills/woostack-change) executes one explicit bounded
enhancement/refactor without contacting Linear.

Explicit build or project-backed Fix abandonment stops repository work and moves the existing
project to configured canceled status, with independent read-back. Source issues are preserved; no
project is created solely to cancel anything. Normal handoff, replanning, and blockers leave the
project open.

## Two hard gates

Build and project-backed Fix advance past exactly two content-bound Linear approvals:

1. **Project-spec approval** streams the exact verified owner-only `project-spec.md` bytes and full
   identity immediately before a body-free Ask whose explicit options are exactly `Accept` and
   `Abandon`. A same-process revision streams one byte-complete unified diff with old/new full-file
   identities; otherwise the complete artifact is streamed. Only acceptance of that immediately
   preceding identity permits one bounded synchronization and the matching receipt.
2. **Execution-plan approval** streams every complete verified `execution-plan.md` byte and full
   identity (or a verified same-process revision diff) immediately before the same body-free
   `Accept`/`Abandon` Ask. Complete issue contracts and dependencies remain in the streamed file,
   never in the Ask. Only acceptance permits one bounded graph synchronization, exact read-back, and
   the matching receipt.

After gate 2, Build/Fix display the exact project URL or UUID, both approval receipts and canonical
fingerprints, stable task mappings, dependencies, approved parent branch, last admitted tip, and
`/woostack-execute --project <exact Linear URL-or-UUID>`. A body-free handoff Ask offers exactly
`Stop here`, `Execute`, and `Abandon`: Stop here returns without mutation, Execute dispatches normal
Execute once, and Abandon closes the existing project without dispatch. Unknown or custom input asks
again and fails closed.

The local manifest and its two run-scoped gate files are permission-restricted working state, never
product authority. Material baseline drift, file identity mismatch, read-back mismatch, process loss,
or content changes require reconciliation, regeneration, and a fresh concise Ask. Synchronization,
read-back, planning, implementation checks, review, and progress updates are work steps, not
additional gates.

## Two delivery shapes

| | Standalone work | Multi-increment work |
| --- | --- | --- |
| Use when | One bounded fix/change can ship in one PR | A feature needs multiple independently shippable increments |
| Active contract | Fix: approved project-spec revision plus approved direct-issue graph. Change: one explicit goal | Approved project-spec revision plus approved direct-issue graph |
| Linear plan | Fix: one project after root-cause proof → direct issues + native dependencies. Change: none | One project → one direct issue per increment + native dependencies |
| Evidence | Linear owns fix specification/plan; Git/GitHub prove delivery | Linear owns spec/plan; Git/GitHub prove delivery per increment |
| Code delivery | One GitHub PR | One GitHub PR per increment |

These shapes are chosen by work size. Linear is required for fix/build product authority but never
replaces direct repository delivery evidence.

## Context economy

<ContextEconomy />

The working context is scarce. A window stuffed with material the current step does not need
reasons worse and runs out sooner. woostack keeps it focused through compact tool output, isolated
coding sessions, and independent review.

### Session reflection becomes instruction suggestions

At an ordinary final-reply boundary, [woostack-reflect](/docs/skills/woostack-reflect) is loaded only
when the session already contains a concrete observed preventable instruction gap that could yield a
durable instruction finding. Its candidate gate is canonical; a qualifying reply runs one report-only
pass, while a reply with no candidate emits no reflection headings.


Diagnostic outputs from audit, QA, or production-response workflows are similarly
non-authoritative. They may support a decision; remediation enters the appropriate fix, change, or
build workflow and obtains its own approval contract.

### Tools compute, agents read compact results

Small helpers gather and compress deterministic repository context so agents consume a result
rather than every input. Review prefetch gathers the relevant diff, metadata, and repository rules
once for independent analysis. Status and development workflows retain only the verified MCP
identities and receipts required for the current decision.

Automatic init setup and every required or selected artifact access uses the host's authenticated
official Linear MCP connection. Init needs only read capability and validates local config writes
independently; it never reads a development artifact or probes a provider write. Fix/build
operations verify the canonical repository association and resolved workspace/team, prove the exact
capabilities they need without reading credentials, and independently read mutations and approval
events back. Tracked policy supplies validated defaults only after a workflow requires or selects
Linear and cannot authorize unrelated provider writes.

### External engineers and coding harnesses

Hermes is an external engineer, not a supported coding harness or installed woostack runtime. If
used, it drives one persistent OMP process. Woostack remains installed in OMP or another coding
harness, where project-scoped workers implement and verify bounded tasks.

Hermes may make in-contract decisions, review OMP evidence, escalate contract changes to the
responsible user, relay exact approval responses verbatim through the same OMP process, and
redispatch bounded corrections. It may not edit implementation source, run implementation
commands, or replace direct Git/GitHub evidence. See the [Hermes guide](/docs/hermes) for the
external boundary and fail-closed approval relay.
