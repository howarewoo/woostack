The user decides what woostack may change. Git and GitHub show what code changed, which branches and
commits it came from, and whether its pull requests (PRs) have been reviewed or merged.

## Planning before implementation

- **Bounded work** fits one PR. Execute handles a non-bug enhancement or refactor after its bounded
  contract is admitted. Execute is the explicit implementation and draft-PR path for one complete
  task.
- **Prepared work** needs a specification, evidence, and a reviewable issue graph. Prepare composes
  Debug for defects, Ideate for user-owned decisions, Harden for repository reconciliation, and Plan
  for the sole GitHub parent/child publisher. It stops before source edits, branches, workers, or PRs.
- **Execution** is separate. The user may pass the verified parent to Orchestrate as a separate next
  command, or select one complete bounded task for Execute. Issue lifecycle alone never proves code
  delivery, review, acceptance, or merge.

See [Workflow maps](/docs/concepts/workflows) for the sequences and
[Building rules](/docs/concepts/building-rules) for the planning and delivery boundaries.

## Complete user understanding

Ideate is a public planning conversation. Invoke it as `/woostack-ideate <goal-or-specification>` with
complete plain content and the exact repository/evidence identity when repository-grounded decisions
are needed. The user verifies goals, behavior, exclusions, architecture, data models, API details,
and verification expectations that matter to the work. Ideate returns the complete specification,
confirmed decisions, evidence, and unresolved questions.

Harden is also directly callable: `/woostack-harden <specification-or-issue-plan>`. It checks supplied
content against bounded repository evidence, raises material discrepancies before changing approved
decisions, and returns complete reconciled content. Neither phase requires a Prepare run, writable
checkout, or GitHub Project configuration. Existing conventions and plausible defaults never replace
the user's decision.

Prepare is the thin composition for feature and defect planning:
`/woostack-prepare <goal-or-defect> [--parent-issue new|<exact-url>]`. Complete input may start at
any relevant phase without repeating settled approval. A defect must carry Debug's observed/expected
behavior, causal chain, exact evidence, correction boundary, risks, and verification. Missing or stale
causal proof blocks before Plan; Prepare never guesses a fix.

Plan consumes one complete approved packet and publishes one exact GitHub parent/child hierarchy or
explicit Project graph with native prerequisite edges. It independently reads every identity and
relationship back. A partial graph is a recoverable planning result, not Orchestrate-ready success.
The suggested `/woostack-orchestrate --issue <verified-parent-url>` is separate and is never invoked by
Prepare or Plan.

Plans describe outcomes and acceptance criteria: the conditions the finished work must meet. They
leave coding steps to the implementer without changing the agreed scope.

## Retained records and direct GitHub publication

Existing `.woostack/tmp/runs/<run-id>/` records from retired planning wrappers remain readable
historical user data. They are never migrated or mutated. A caller may supply a complete retained
packet and exact identity for fresh validation, but a record does not authorize publication,
implementation, assignment, or ownership. Plan's GitHub issue publication is direct; legacy
managed-provider records remain opaque and inactive.

## Context economy

<ContextEconomy />

Keep only the workflow and references needed for the current decision in the agent's context.
Choose inline or delegated implementation using the
[delegation guidance](/docs/concepts/context-management#isolated-agents-receive-bounded-envelopes),
which weighs speed, cost, isolation, overhead, and risk. Verification and independent review still
check implementation.

### Session reflection becomes instruction suggestions

[woostack-reflect](/docs/skills/woostack-reflect) always runs exactly once for an explicit
`/woostack-reflect` invocation. An ordinary final reply loads it only when the session already
contains a concrete observed preventable instruction gap; otherwise it has no reflection headings.
Its candidate gate defines that condition, and the first pass is report-only.

Diagnostic outputs from QA or production-response workflows can support a decision but cannot
authorize a correction. Repairs first use Debug for causal proof, then Prepare for a verified issue
graph, or Execute for an admitted bounded non-bug change.

### Tools compute, agents read compact results

Helpers gather and check evidence that can be processed mechanically. Historical run-store operations
protect retained files; they are not a new Prepare authority. The user still verifies workflow
decisions.

### External engineers and coding harnesses

Hermes is an external engineer, not an installed coding harness. It may drive a persistent OMP
session, review evidence, and relay the responsible user's live decisions verbatim; it does not gain
implementation authority. See the [Hermes guide](/docs/hermes) for that boundary and cross-session
resume.
