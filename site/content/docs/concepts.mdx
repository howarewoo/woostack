woostack is a multiperson development workflow with repository-first evidence and optional Linear
capability. The user's approved workflow contract defines scope and approval. Git and GitHub own
source, branches, commits, pull requests, reviews, and merge evidence. When repository Linear
availability is proved, build/fix plans are persisted as projects with a parent plan issue and one
native child issue per increment. Those artifacts never authorize repository work.

## The build loop

[woostack-build](/docs/skills/woostack-build) handles work expected to require multiple
independently shippable increments. It chains a fixed sequence:

> ideate → **approve design** → harden specification → **approve spec** → build a dependency-aware
> increment plan → persist the available Linear project hierarchy → **execution handoff** → execute
> and review one increment at a time

Ordered increments remain independently shippable and map to reviewable PRs. Without configured,
authenticated Linear capability, the specification and plan remain in the active workflow.

Bounded one-PR work takes a smaller route. [woostack-fix](/docs/skills/woostack-fix) proves a root
cause, approves one fix contract, and persists its one-increment plan project when Linear is
available. [woostack-change](/docs/skills/woostack-change) executes one explicit bounded
enhancement/refactor without contacting Linear.

An explicit fix/build abandonment stops repository work and moves any existing plan project to the
configured canceled status, with independent read-back. Normal handoff, replanning, and blockers do
not close the project, and no project is created merely to record an artifact-free abandonment.

## Three hard gates

The multi-issue build loop advances past exactly three points only after an explicit answer:

1. **Design approval** accepts the proposed design.
2. **Written-spec approval** accepts the hardened specification before increment planning.
3. **Execution handoff** chooses Go, Run overnight, or Hand off after the plan is ready.

Persistence, read-back, planning, implementation checks, review, and progress updates are work
steps, not additional approval gates. Silence never clears a gate.

## Two delivery shapes

| | Standalone work | Multi-increment work |
| --- | --- | --- |
| Use when | One bounded fix/change can ship in one PR | A feature needs multiple independently shippable increments |
| Active contract | Approved goal/fix contract | Approved specification plus dependency-aware plan |
| Linear plan | Fix: project → parent plan issue → one increment child. Change: none | Project → parent plan issue → one child per increment |
| Evidence | Direct repository/PR evidence | Direct repository/PR evidence per increment |
| Code delivery | One GitHub PR | One GitHub PR per increment |

These shapes are chosen by work size, not by storage provider. Linear persistence never changes the
approval, implementation, verification, or review gates.

## Context economy

<ContextEconomy />

The working context is scarce. A window stuffed with material the current step does not need
reasons worse and runs out sooner. woostack keeps it focused through compact tool output, isolated
coding sessions, and independent review.

### Session learning becomes instruction suggestions

At the end of each session, woostack reviews the completed conversation and tool evidence for
durable project rules. It suggests only novel rules that are likely to help future sessions and
targets each suggestion to the global or narrowest applicable `AGENTS.md`.


Diagnostic outputs from audit, QA, or production-response workflows are similarly
non-authoritative. They may support a decision; remediation enters the appropriate fix, change, or
build workflow and obtains its own approval contract.

### Tools compute, agents read compact results

Small helpers gather and compress deterministic repository context so agents consume a result
rather than every input. Review prefetch gathers the relevant diff, metadata, and repository rules
once for independent analysis. Status and development workflows retain only the verified MCP
identities and receipts required for the current decision.

Repository-enabled artifact access uses the host's authenticated official Linear MCP connection.
Skills prove capability without reading credentials and independently read mutations back. An
unavailable preflight keeps automatic fix/build planning artifact-free; a failure after availability
was proved blocks that plan before execution.

### Decision-makers and coders stay isolated

An engineer unit separates judgment from implementation:

- The **decision-maker** owns the contract, in-scope decisions, independent code/PR review,
  acceptance, redispatch, handoff, and escalation. It does not edit source or run implementation.
- The **isolated coder** receives one approved task and one worktree. It analyzes, implements,
  verifies, and returns evidence, but does not change scope or accept its own work.

Hermes as decision-maker plus OMP as coder is the first published adapter. Hermes dispatches with
exactly `omp --profile <engineer> -p --cwd <repo> <prompt>`, then independently inspects the
result. Only an explicit user invocation of
[woostack-review](/docs/skills/woostack-review) permits delegation to independent reviewer
profiles; the decision-maker still owns the verdict and acceptance.

See [Engineer agents](/docs/concepts/engineer-agents) for the provider-neutral boundary and
[Hermes](/docs/harnesses/hermes) for the concrete setup.
