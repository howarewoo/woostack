The user decides what woostack may change. Git and GitHub show what code changed, which branches and
commits it came from, and whether its pull requests (PRs) have been reviewed or merged.

## Planning before implementation

- **Bounded work** has one authorized outcome. Execute chooses routine implementation details,
  establishes the cause before correcting a defect, and runs relevant verification. Local work
  need not commit or publish. Explicit `/woostack-execute` requests a draft PR unless narrowed;
  related authorized issues may share requested delivery without changing an explicit mapping.
  It requires no preparatory project or planning workflow.
- **Planning** starts from a goal or an ordinary amount of task context. Plan inspects the relevant
  source, surfaces the decisions that still matter, and writes GitHub issues only when the request
  asks for them. It stops before source edits, branches, workers, or PRs.
- **Execution** is separate. The user may hand Orchestrate the published issues or other
  understandable multi-task context, or select one complete bounded task for Execute. Orchestrate
  interprets the available repository and tracker evidence; issue lifecycle alone never proves code
  delivery, review, acceptance, or merge.

See [Workflow maps](/docs/concepts/workflows) for the sequences and
[Building rules](/docs/concepts/building-rules) for the planning and delivery boundaries.

## Optional exploration and review

Ideate is a public requirements conversation. Invoke it as `/woostack-ideate <goal-or-specification>`.
It returns the explored specification, relevant evidence, technical details it filled in, and
unresolved decisions. No complete packet or exact baseline supplied by the user is required
when the checkout can answer repository questions.

Harden is also directly callable: `/woostack-harden <specification-or-issue-plan>`. It checks
supplied content against bounded repository evidence, raises material discrepancies, and returns
reconciled content. Both are optional, and neither needs a writable checkout or GitHub Project
configuration. Verified schemas and interfaces are observations, and agents fill in routine
technical details consistent with the requested outcome. Unresolved product behavior, breaking
compatibility, security and data boundaries, irreversible effects, cost, and scope still need a
user decision.

Plan is the complete planning workflow:
`/woostack-plan <goal-or-specification>`. A planning-only request returns the plan and makes no
GitHub writes. A request to file issues already supplies publication intent, so Plan inspects the
relevant existing issues, creates or reuses the requested issues, and verifies their actual content
back. It resolves an unambiguous destination from the request and its context, and asks one focused
question when that destination is ambiguous. Native sub-issue and dependency links are used when
they are available and requested; when they are not, the written issues and an explicit readable
index are preserved, the missing relationships are reported, and an explicitly required native
graph is never called complete. A partial publication preserves exact confirmed identities and
resumes at the first unproved step. An unknown defect cause stays with Debug.

The result can be passed to Orchestrate, which interprets the published issues or other
understandable tracker context into executable tasks and a bounded dependency DAG; native links are
evidence when present, not a universal admission requirement. A suggested
`/woostack-orchestrate --issue <exact canonical GitHub issue URL>` is a convenience hint and is
never invoked by Plan.

A plan describes outcomes and acceptance criteria: the conditions the finished work must meet. It
leaves coding steps to the implementer without changing the agreed scope.

## Retained records and direct GitHub publication

Existing `.woostack/tmp/runs/<run-id>/` records from retired planning wrappers remain readable
historical user data. They are never migrated or mutated. A caller may supply a record's exact
identity and content for fresh validation, but a record does not authorize publication,
implementation, assignment, or ownership. Plan's GitHub issue publication is direct; legacy
managed-provider records remain opaque and inactive.

## Context economy

<ContextEconomy />

Keep only the workflow and references needed for the current decision in the agent's context.
Choose inline or delegated implementation using the
[delegation guidance](/docs/concepts/context-management#isolated-agents-receive-bounded-envelopes),
which weighs speed, cost, isolation, overhead, and risk. Run relevant verification; use independent
review when the task or repository requires it.

### Session reflection becomes instruction suggestions

[woostack-reflect](/docs/skills/woostack-reflect) runs one report-only pass for an explicit
`/woostack-reflect` invocation or an unambiguous request to reflect on the conversation. Ordinary
work never loads it.

Diagnostic outputs from QA or production-response workflows can support a decision but cannot
authorize a correction. Repairs first use Debug for causal proof, then Plan when the correction
needs published issues, or Execute for an authorized bounded correction.

### Tools compute, agents read compact results

Helpers gather and check evidence that can be processed mechanically. The historical run-store
reader returns retained record bytes without changing them; it is not a publication authority. The
user still decides what work may start.

### External engineers and coding harnesses

Hermes is an external engineer, not an installed coding harness. It may drive a persistent OMP
session, review evidence, and relay the responsible user's live decisions verbatim; it does not gain
implementation authority. See the [Hermes guide](/docs/hermes) for that boundary and cross-session
resume.
