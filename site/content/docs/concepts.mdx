The user decides what woostack may build. Git and GitHub show what code changed, which branches and
commits it came from, and whether its pull requests (PRs) have been reviewed or merged.

## Two delivery shapes

- Bounded work fits one PR. Execute handles a complete enhancement, refactor, test-only task, or
  authorized understood correction. Fix first proves the cause of a defect and gets explicit
  approval of the complete correction and verification plan. Goal-only Execute and bounded Fix make
  no artifact-provider calls unless an exact issue association or requested provider operation is
  selected. Execute with an explicit exact canonical GitHub issue input performs the required read
  of that issue through host-authenticated `gh`; it still requires no provider configuration, project,
  mirror, or persisted plan.
- Project-backed work needs a specification and an ordered plan. Build and larger, uncertain, or
  explicitly project-backed fixes keep those files and a manifest under
  `.woostack/tmp/runs/<run-id>/`. The manifest records the run's tasks and recovery state. These local
  records are the source of truth for the plan; Linear, Plane, or GitHub can hold optional copies.

See [Workflow maps](/docs/concepts/workflows) for the sequences and
[Building rules](/docs/concepts/building-rules) for the approval and delivery boundaries.

## Complete user understanding

Ideate is the planning conversation. The user verifies the goals, behavior, exclusions, architecture,
data models, API details, and verification expectations that matter to the work. Harden checks
those decisions against the repository and raises one discrepancy at a time. Existing conventions
and plausible defaults never replace the user's decision.

Plans describe outcomes and acceptance criteria: the conditions the finished work must meet. They
leave coding steps to the implementer without changing the agreed scope.

## Retained artifacts and optional mirrors

Project-backed workflows keep `project-spec.md`, `execution-plan.md`, and recovery state across
completion, interruption, and abandonment. The
[artifact contract](https://github.com/howarewoo/woostack/blob/main/skills/woostack-init/references/artifact-backends.md)
defines storage, resuming an exact run, mirroring, and lifecycle details. A provider mirror is a
remote copy; it cannot authorize repository work or override the local run.

Build and project-backed Fix present the verified artifacts before the user chooses whether to
execute, stop, or abandon. Clear natural-language intent is accepted; changed scope returns to
explicit verification. The [Build handoff](/docs/skills/woostack-build#verified-handoff) is canonical.


## Context economy

<ContextEconomy />

Keep only the workflow and references needed for the current decision in the agent's context.
Choose inline or delegated implementation using the
[delegation guidance](/docs/concepts/context-management#isolated-agents-receive-bounded-envelopes),
which weighs speed, cost, isolation, overhead, and risk. Verification and independent review
still check the implementation.

### Session reflection becomes instruction suggestions

[woostack-reflect](/docs/skills/woostack-reflect) always runs exactly once for an explicit
`/woostack-reflect` invocation. An ordinary final reply loads it only when the session already
contains a concrete observed preventable instruction gap; otherwise it has no reflection headings.
Its candidate gate defines that condition, and the first pass is report-only.
Diagnostic outputs from QA or production-response workflows can support a decision but cannot
authorize a fix. Repairs use the appropriate Fix, Execute, or Build workflow and its rules.

### Tools compute, agents read compact results

Helpers gather and check evidence that can be processed mechanically. Run-store operations protect
the files used to resume work. The user still verifies workflow decisions.


### External engineers and coding harnesses

Hermes is an external engineer, not an installed coding harness. It may drive a persistent OMP
session, review evidence, and relay the responsible user's live decisions verbatim; it does not gain
implementation authority. See the [Hermes guide](/docs/hermes) for that boundary and cross-session
resume.
